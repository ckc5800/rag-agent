# rag-agent

![CI](https://github.com/ckc5800/rag-agent/actions/workflows/ci.yml/badge.svg)

포트폴리오와 기술문서를 지식 베이스로 쓰는 로컬 RAG Agent.
LangGraph 기반이며, 검색 품질을 스스로 평가해 부족하면 질문을 재작성하는
corrective 루프 위에 도구(검색/계산/날짜)를 골라 쓰는 tool-calling 레이어,
멀티홉 질문을 분해 처리하는 multi-agent 오케스트레이션 레이어,
도구를 MCP 서버에서 가져오는 MCP 클라이언트 레이어를 얹은 구성임.

Ollama + FAISS 조합이라 전부 로컬에서 동작하며 외부 API 불필요.

### RAG 흐름

```mermaid
graph LR
    Q[질문] --> RS[route_strategy<br/>유형별 컨텍스트 전략]
    RS --> R[retrieve<br/>FAISS + BM25 RRF]
    R --> G[grade<br/>검색 품질 평가]
    G -->|충분| GEN[generate<br/>근거 기반 답변 + 출처]
    G -->|부족| RW[rewrite<br/>질문 재작성]
    RW --> R
    GEN --> V[verify<br/>근거성 확인]
    V --> A[답변]
```

`route_strategy`는 질문 유형(집계·열거 등)에 맞는 컨텍스트 전략을 State에 실어 보냄.
예전에는 이 라우팅이 그래프 밖에서 전역 `config`를 잠깐 바꾸는 방식이었는데,
FastAPI가 동기 핸들러를 스레드풀에서 돌리는 탓에 동시 요청끼리 서로의 설정을
덮어쓰는 문제가 있었음(코드 주석에 "알려진 한계"로 기록돼 있던 부분).
노드로 옮기면서 이 경합이 사라졌고, 스트리밍 엔드포인트가 따로 감싸던 특례도 제거함.

검색은 FAISS(의미)와 BM25(키워드)를 RRF로 융합함.
'Jenkins', 'Pyannote' 같은 고유명사 질문에서 벡터 검색이 엉뚱한 청크를 가져오는
문제가 반복돼 BM25를 결합했고, 효과가 컸음.
답변은 문서 근거가 없으면 모른다고 답하도록 프롬프트를 구성함.

### Tool-Calling 레이어

```mermaid
graph LR
    U[질문] --> AG[agent<br/>LLM + bind_tools]
    AG -->|tool_calls| T[search_portfolio / calculate / get_current_date]
    T --> AG
    AG -->|답변| E[END]
```

RAG 검색을 `search_portfolio` 도구로 감싸고, 계산(`calculate`, AST 기반이라 eval 미사용)과
날짜 조회 도구를 추가함.
"TTFB가 2292ms에서 334ms로 줄었는데 몇 % 개선이야?" 같은 질문이 들어오면
모델이 검색과 계산을 스스로 조합함.

```bash
python src/agent.py "TTFB가 2292ms에서 334ms로 줄었는데 몇 퍼센트 개선이야?"
# 사용한 도구: ['calculate'] → 약 85.43% 개선
```

### Multi-Agent 레이어 (멀티홉 질문)

단일 RAG는 "A와 B 중 어느 게 먼저야?" 같은 멀티홉 질문에 약함.
한 번의 검색으로 서로 다른 두 사실을 모두 가져오기 어렵기 때문.

```mermaid
graph LR
    Q[질문] --> P[planner<br/>사실 단위 sub-질문 분해]
    P --> W1[RAG worker 1]
    P --> W2[RAG worker 2]
    W1 --> S[synthesizer<br/>sub-답변 종합]
    W2 --> S
    S --> A[답변]
```

- planner가 질문을 문서에서 찾을 수 있는 사실 단위의 의문문으로 분해
  (최대 3개, JSON 파싱 실패 시 원 질문 단일 처리로 폴백)
- 각 sub-질문은 기존 Corrective-RAG가 worker로 처리.
  planner가 이미 질의를 정제했으므로 worker의 자체 재작성은 끔 (이중 가공 방지)
- sub-질문이 1개면 synthesizer 호출을 생략해 불필요한 LLM 호출 제거

```bash
python src/team.py "TTS 프로젝트와 Kubernetes 프로젝트 중 어느 것을 먼저 시작했어?"
# sub-질문: ["TTS 프로젝트는 언제 시작했어?", "Kubernetes 프로젝트는 언제 시작했어?"]
# → "먼저 시작한 것은 Kubernetes 프로젝트입니다. TTS는 2025년 9월, Kubernetes는 2024년 3월부터..."
```

### MCP 클라이언트 레이어

tool-calling 레이어의 도구는 이 저장소 안에 하드코딩돼 있음.
`mcp_agent.py`는 같은 에이전트 구조에서 도구만 MCP로 바꾼 버전.
별도 저장소인 [portfolio-mcp](https://github.com/ckc5800/portfolio-mcp) 서버를
stdio로 띄우고, 서버가 광고하는 도구 4개(프로필/프로젝트/논문/BM25 검색)를
`langchain-mcp-adapters`로 변환해 에이전트에 연결함.

```mermaid
graph LR
    U[질문] --> AG[agent<br/>LLM + MCP tools]
    AG -->|tool_calls| C[MCP Client] -->|stdio| S[portfolio-mcp 서버]
    S --> C --> AG
    AG -->|답변| E[END]
```

도구 정의가 에이전트 밖(서버)에 있으므로, 서버에 도구가 추가되면 에이전트는
코드 수정 없이 그대로 사용 가능함.
MCP 서버(제공자)와 클라이언트(소비자)를 양쪽 다 만들어 본 것이 포인트.
무응답 폴백 등 소형 모델 대응은 agent.py와 동일한 패턴을 사용함.

```bash
# 형제 디렉토리에 portfolio-mcp 클론 필요 (경로는 PORTFOLIO_MCP_SERVER로 변경)
python src/mcp_agent.py "우수 논문상을 받은 논문 제목이 뭐야?"
# MCP 서버가 광고한 도구: ['portfolio_search', 'portfolio_list_projects',
#                          'portfolio_get_publications', 'portfolio_get_profile']
# 사용한 도구: ['portfolio_get_publications']
# 답변: 이윤선의 우수 논문상을 수상한 논문 제목은 "국방 데이터 확보를 위한
#       생성모델 Latent Diffusion 실험"입니다. ...
```

3B 모델이 폴백 없이 스스로 `portfolio_get_publications`를 선택함.
질문 성격에 맞는 도구 선택까지 MCP 도구 스키마만으로 동작한다는 확인.

### 문서를 추가·갱신했을 때

인제스트는 **증분이 아니라 전량 재구축**임(`vectorstore.build`가 인덱스 디렉터리를
지우고 다시 임베딩). 그래서 옛 벡터가 남아 섞이는 사고는 구조적으로 없음. 대신
**라벨과 기대값이 낡음** — 손이 가는 곳은 거기.

```bash
git show HEAD:data/chunks.jsonl > /tmp/old.jsonl   # 라벨 재부착 기준
python src/ingest.py                               # 전량 재임베딩 + 매니페스트 갱신
python eval/relabel_retrieval.py --old /tmp/old.jsonl --write
python eval/audit_coverage.py                      # 앵커가 아직 해소되는가
python -m pytest -q tests
```

각 단계가 무엇을 막는지:

- **`ingest.py`** — 확장자로 갈림(`.md`는 다이어그램·표 분리 + 노션 정제,
  `.pdf/.docx/.hwpx`는 `loaders.py`). 그 외 확장자는 인덱싱에서 빠지며 경고를 찍음.
  텍스트가 안 뽑히는 스캔 PDF도 경고 대상(`warn_empty_sources`). 둘 다 "넣었는데
  검색이 안 된다"의 단서.
- **`relabel_retrieval.py`** — 문서가 늘거나 길이가 바뀌면 뒤쪽 청크의
  `chunk_index`가 전부 밀림. 재부착을 빠뜨리면 검색 평가가 엉뚱한 청크를 정답으로
  셈.
- **`audit_coverage.py`** — 앵커 문자열이 어느 청크에도 없으면 `[FAIL] 앵커 미해결`로 잡음.
  문서 내용이 바뀌어 근거 문장이 사라진 경우를 잡는 그물.
- **`pytest`** — 커밋된 `chunks.jsonl`이 현재 인제스트 코드의 산출물인지 청킹을
  다시 돌려 대조함. 재인제스트를 빠뜨리고 커밋하면 여기서 잡힘(실제로 표 청킹 때
  이걸 몰라 7b 측정이 통째로 옛 청킹 위에서 돌았음).

커밋에는 **`data/chunks.jsonl`과 `eval/retrieval_set.json`을 포함** — 둘 다 추적
파일이고 위 게이트가 둘의 일치를 강제함.

자동으로 따라오는 것: BM25는 별도 인덱스 없이 기동 때 `chunks.jsonl`에서 재구축되고,
응답 캐시는 키에 인덱스 지문이 들어 있어 코퍼스가 바뀌면 저절로 무효가 됨. **다만
돌고 있는 서버는 재시작해야 함** — `api.py`는 lifespan에서 `warmup()`을 한 번
부르고 인덱스를 모듈 전역에 캐시하며, 재적재 엔드포인트가 없음.

#### 문서 버전을 함께 보관하기 (`VERSION_FILTER`, 기본 켜짐)

개정 전 판을 남겨 두고 싶으면 `archive/<판>/` 아래에 둠. **보관 위치가 곧 버전
표시** — 파일명 규칙이나 front-matter 대신 폴더를 쓰는 이유는, 규칙은 지켜야 하고
폴더는 지켜진 상태로 보이기 때문.

```
data/docs/resume.md                  현행본
data/docs/archive/2024-06/resume.md  2024-06판 (superseded)
```

보관본도 **같은 인덱스**에 들어가고, 청크에 `version`·`superseded`가 붙음. 출처
이름도 `resume.md@2024-06`으로 달라진다 — 이름이 같으면 인용이 어느 판인지 못
가리고, 이웃 확장의 "같은 문서 안에서만" 조건이 두 판을 한 문서로 착각함.

**기본 검색은 현행본만 봄.** 버전을 그냥 쌓으면 같은 사실의 사본이 여러 개가 되어
RRF가 그것들을 나란히 올리고 top-5 슬롯을 잡아먹음 — `resume-original.docx`를
넣었다가 기존 질문들이 깨져 코퍼스에서 뺀 그 손해(근중복 절 참고). 그래서 **보관은
하되 기본은 거름.**

거를 때는 후보를 두 배로 뽑아 거른 뒤 TOP_K를 채움. FAISS는 메타데이터 필터가 없어
사후 필터링이 유일한 방법이고, 한계도 `vectorstore.search(source=...)`와 동일(거르고
나면 k를 못 채울 수 있음). Qdrant로 띄우면 필터를 검색에 넣을 수 있으므로, 보관본이
많아지면 그때 갈아끼우면 됨.

**보관본은 시점을 묻는 질문에서만 열림.** 판정은 LLM이 아니라 규칙(route.py와 같은
원칙 — 탐지는 결정적으로, 정밀도 우선). "이전 버전", "예전", "당시", "2024년 기준",
"수정 전" 같은 확실한 신호만 봄. 오탐(현재 질문을 과거로 봄)은 보관본이 후보에 섞여
답이 흔들리는 손해라 비대칭이 큼.

열렸을 때는 컨텍스트에 판을 표시:

```
[2024-06판 보관본] 이력서 본문 …
```

안 붙이면 모델이 현행본과 옛 판의 사실을 구분 없이 섞고, 답변만 봐서는 어느 시점
기준인지 알 수 없음.

**보관본이 없는 코퍼스에서는 이 경로를 아예 안 탐.** 후보를 넓혔다 걸러내면 RRF 입력
길이가 달라져 순위가 미묘하게 바뀌므로, `archive/`가 비어 있으면 검색은 예전과 한
글자도 다르지 않음(`_has_superseded`).

**아직 안 잰 것**: 보관본을 실제로 넣었을 때의 근중복 손해와, 시점 질문의 정답률.
지금 평가셋 100문항에 버전을 묻는 문항이 0개라 **측정 대상이 없음** — 보관본을 처음
넣을 때 그 문항들을 같이 만들어야 이 손잡이의 값을 잴 수 있음(`trap` 유형과 같은
가족). `VERSION_FILTER=0`으로 끄면 현행본·보관본을 구분 없이 검색하므로, 근중복
손해를 재는 A/B가 바로 됨.

#### 같은 파일명으로 문서가 개정된 경우

파일명이 같아도 전량 재구축이라 인덱스 쪽은 자동으로 맞음.
위험은 **라벨과 정답 기준이 조용히 낡는 것**이고, 개정 폭에 따라 셋으로 갈림.

| 개정 폭 | 무슨 일이 나는가 | 어떻게 잡히는가 |
|---|---|---|
| 오타·문장 다듬기 | 청크 내용 md5가 바뀌어 gold가 무효화 | `relabel_retrieval.py`가 n-gram 포함도로 새 청크에 재부착(대개 1.00) |
| 단락 추가·삭제 | 위 + `chunk_index` 이동, 경계가 재배치 | 같은 스크립트. 매칭 점수가 **0.35 미만이면 반영을 거부**하고 사람에게 넘긴다 |
| 사실 자체가 변경 (논문 7편 → 8편) | 라벨은 붙는데 **정답 기준이 틀려진다** | 자동으로 안 잡힌다. `audit_coverage.py`가 앵커 미해결만 잡고, `answer_patterns`의 숫자는 사람이 고쳐야 한다 |

즉 **세 번째 줄이 유일하게 위험한 칸**. 검색은 새 문서를 정확히 가져오는데 채점기가
옛 답을 정답으로 들고 있으면, 고쳐야 할 것은 시스템이 아니라 평가셋인데 지표는
"성능이 떨어졌다"고 말함. 이 저장소가 반복해서 경계해온 **지표가 조용히 거짓이
되는** 형태.

그래서 사실이 바뀌는 개정에서는 순서가 하나 더 있다 — 재인제스트 전에
`eval/eval_set.json`에서 그 문서에 걸린 문항의 `answer_patterns`·`gold_anchors`를
먼저 손보고, `python eval/audit_patterns.py --strict`로 패턴이 실제 청크에 걸리는지
확인함.

마지막으로 근중복을 확인함. 개정본을 넣으면서 구본을 안 지우면 같은 사실이 두 문서에
남아 RRF가 둘 다 올려 top-5 슬롯을 잡아먹음 — `resume-original.docx`를 넣었다가
기존 질문들이 깨져 코퍼스에서 뺀 기록이 아래 "DOCX를 코퍼스에 넣었다가 뺀 이야기"에
있음.

## 평가와 삽질 기록

평가셋으로 정답률 / 재작성률 / 지연시간을 측정함.
변경이 생길 때마다 돌려서 회귀 여부를 확인하는 용도.
아래 v1~v7은 10문항 시절의 기록이며, 이후 51문항으로 확장하면서 일부 결론이
뒤집힘 — [평가셋 확장 및 실패 원인 분석](#평가셋-확장-및-실패-원인-분석-측정-보고) 참고.

| | v1 | v2 | v4 | v5* | v6* | v7* |
|---|---|---|---|---|---|---|
| 정답률 | 50% | 60% | 60% | 70% | 70% | **90%** |
| 재작성률 | 100% | 30% | 30% | 30% | 40% | 30% |
| 검색 때문에 틀린 것 | 3건 | 3건 | 1건 | 1건 | 1건 | **0건** |

*v5부터는 더 엄격한 패턴 채점(아래) 기준이라 앞 열과 직접 비교 불가.
3B 모델의 런 간 편차(±10%p)를 감안하면 60→70은 개선이라기보다 같은 수준.
v6는 검색 개선(아래 4번) 후, v7은 데이터 검수(아래) 후의 런.

v7의 90%는 10문항 중 9개라 숫자 자체에 의미를 두기 어려움.
의미 있는 것은 검색 기인 실패가 0건이 된 쪽.
남은 실패 1건은 CI/CD 도구 열거인데, gold 청크가 rank 1로 검색됐는데도
모델이 "GitLab CI/CD와 Jenkins"라고 답해 ArgoCD를 누락함.
검색이 아니라 생성의 문제이며, 검색/생성을 분리해 측정하기 때문에
이 구분이 지표에서 바로 읽힘.

수치보다 과정에 배운 것이 많았고, 커밋 로그에 전부 남아 있음.

1. 첫 평가에서 재작성률 100%. 프롬프트 문제로 보고 한참 수정했으나,
   실제 원인은 grade 노드가 반환하는 키가 `AgentState`에 정의돼 있지 않아
   LangGraph가 값을 조용히 버리던 것. 판정 결과와 무관하게 매번 재작성으로
   빠지고 있었음. 스키마에 키 하나 추가로 해결.
2. 이후에도 재작성이 남아 있었는데, 'yes/no'로 답하라는 프롬프트에 모델이
   '예/아니오'로 답해 파싱이 실패하던 것. 한국어 응답까지 받도록 수정.
3. 고유명사 질문('Jenkins', 'Pyannote')은 벡터 검색이 계속 누락.
   BM25를 섞은 하이브리드로 바꾼 뒤 검색 기인 실패가 3건에서 1건으로 감소.
4. RRF 중복 제거 키를 청크 앞 100자로 잡았다가, 같은 접두어로 시작하는
   청크들이 합쳐지는 문제를 코드 리뷰에서 발견. 전체 내용 해시로 교체.
5. 시스템 프롬프트를 길게 쓰면 3B 모델의 tool calling이 아예 죽는 것을
   실험으로 확인. 프롬프트를 최소로 줄이고, 그래도 무응답이면 검색을
   강제 호출하는 폴백을 추가.
6. 멀티홉 답변이 같은 코드로 됐다 안 됐다 하는 문제. temperature 0.1의
   미세한 샘플링 차이가 원인이었는데, 이 상태로는 추적이 불가능해
   temperature를 0으로 고정해 재현 가능하게 만든 뒤 통제 실험으로 변수를
   하나씩 분리함.
7. 그렇게 찾은 원인은 두 가지. 하나는 planner가 정제한 sub-질문을 worker가
   또 재작성해 검색 믹스를 흐트러뜨리던 것으로, 팀 경로에서는 재작성을 끔.
   다른 하나는 3B 모델이 엄격한 거부 지시와 명사형 질문("~의 시작 기간")
   조합에서 답을 거부하는 것으로, 같은 내용을 의문문("언제 시작했어?")으로
   물으면 통과함. planner가 의문문으로 분해하도록 few-shot을 고치고 거부
   지시를 완화해 해결. "(2025.09~)" 같은 압축 날짜 표기를 기간으로 해석하지
   못하는 문제도 표기법 힌트 한 줄로 해결.

남은 오답은 대부분 3B 모델의 답변 편차.
같은 질문도 돌릴 때마다 ±10%p쯤 흔들리며, 모델을 키우면 나아질 영역임
(실제로 이후 7b 전환에서 확인 — 아래 "기본 모델 3B → 7B" 절).

### 검색과 생성을 분리해서 재기

정답률 하나로는 실패가 검색 탓인지 생성 탓인지 알 수 없어 평가를 둘로 분리함.

**1. 검색 단독 평가** (`eval/eval_retrieval.py`) — 질문별로 정답이 담긴
청크를 라벨링해 두고(`retrieval_set.json`, 청크 내용 md5로 고정),
프로덕션과 같은 hybrid_search가 그것을 top-k에 올리는지만 측정.
LLM이 없어 결정적이며 수 초 안에 완료됨.

<details>
<summary><b>gold 청크 선정 기준</b> (이 평가에서 판단이 가장 많이 들어간 부분)</summary>

손으로 라벨링함. 라벨링 스크립트 없음. 질문 10개에 gold 총 23개, 질문당 1~4개.

기준은 하나 — "그 청크만 보고 질문에 정확히 답할 수 있는가".
키워드 포함 여부가 아님. 실제로 키워드는 있으나 gold에서 제외한 사례:

| 청크 | 질문 | 제외 이유 |
|---|---|---|
| `"논문 2편 게재(제1저자)"` | 논문 몇 편? | `제1저자`는 있으나 특정 연구의 2편. 이걸 근거로 답하면 "2편"이라는 오답이 됨 |
| `"학술 성과: … 우수논문상"` | 우수논문상 받은 논문 제목은? | 수상 사실만 있고 제목이 없음 |
| `"동시 처리 채널 확장 및 안정성 확보"` | 몇 개로 확장? | 숫자가 없음 (게다가 STT 프로젝트 내용) |

반대로 문서 위치는 무관함. 같은 사실이 여러 곳에 있으면 전부 gold.
특허 번호는 `patents.md`의 표, `resume.md`의 논문 목록, `portfolio.md`의
프로젝트 상세에 모두 나오고 셋 다 답이 됨.

질문 하나에 정답 청크가 여러 개인 이유는 같은 사실이 여러 문서에 중복되기
때문. TTFB 수치는 `portfolio.md`(원본 로그)와 `resume.md`(이력서 요약)
양쪽에 존재. 그래서 "이 청크만 정답"이 아니라 "gold 중 하나라도 top-k에
오면 성공"으로 정의함. 단일 정답 가정을 버린 것.

라벨은 청크 내용의 md5라서 청킹을 바꾸면 자동으로 무효화됨.
옛 라벨로 새 인덱스를 채점하는 사고를 구조적으로 차단
(변경 후에는 `relabel_retrieval.py`로 재부착).

이 방식의 약점 둘과 대응:

1. 누락 — 편향보다 이것이 먼저 옴. 손으로 35청크짜리 문서를 훑다 보면
   답이 있는데 빠뜨림. 실제로 `portfolio.md`에 `10-2538225-0000`이
   명시돼 있는데 특허 질문의 gold에서 빠져 있었음. 누락은 recall을
   실제보다 낮게 만듦(정답이 상위에 와도 오답 처리되므로).

   그래서 `eval/audit_gold.py`를 제작. 질문별 정답 표현으로 전 청크를
   훑어 gold 밖 후보를 뽑되, 자동으로 넣지는 않음 — 문자열이 있다고 답이
   되는 것이 아니기 때문. 후보 4건 중 진짜 누락은 1건, 나머지 3건은
   위 표의 "키워드는 있으나 답이 아닌" 경우. 판단은 사람이 함.

2. 자기 라벨링 — 시스템을 만든 사람이 라벨을 붙였으니 "검색기가 가져온 것을
   정답이라고 표시한 것 아니냐"는 순환 위험이 있음. 그래서 gold 전부가 실제
   정답 문자열을 담고 있는지 역검증함 — TTFB 질문의 gold 4개가 모두
   `2292`와 `334`를 포함.

3. gold가 많으면 우연히 맞기 쉬움 — 그래서 무작위 기준선을 계산함.
   67청크에서 6개를 뽑을 때 질문별 gold 수(1~4개)를 반영하면
   무작위 검색기의 기대 recall@6은 19%. 당시 시스템은 100%.
   기준선 없는 지표는 혼자서 아무것도 증명하지 못함.

남는 한계는 제3자 라벨링이 아니고 10문항이라는 것.
실무라면 쿼리 로그에서 유형별로 뽑고 클릭·구매 같은 약한 라벨을 섞어
규모를 키우는 것이 맞음.

</details>

| recall@1 | recall@3 | recall@6 | MRR |
|---:|---:|---:|---:|
| 70% | 90% | 90% | 0.767 |

10문항 중 9개는 gold가 3위 안에 옴. 유일한 MISS가 "근무한 회사들" 질문으로,
회사 목록이 모여 있는 청크가 top-6에 아예 들지 못함.
이 질문의 실패는 생성이 아니라 검색 문제라는 것이 처음으로 분리되어 보인 사례.

**2. 채점 엄격화** (`eval/rescore.py`) — 키워드 포함 채점은 "논문 7편"의
'7'이 다른 숫자에 우연히 들어가도 통과시킴. 단위까지 요구하는 정규식
패턴(`7\s*편`)에 전부 일치해야 하고, 거부 답변은 무조건 실패로 변경.
저장된 이전 결과를 재채점한 결과 뒤집힌 케이스 없음(6/10 유지) —
이번 런의 통과는 진짜였고 채점만 단단해진 것.

**3. 전체 재평가 (v5)** — 엄격한 채점으로 70%(7/10). 틀린 3건을 분해하면
1건은 검색 실패(회사 목록, 위에서 확인), 2건은 gold가 1위로 검색됐는데도
생성이 놓친 것으로 3B 모델의 답변 편차 영역.
실패 원인이 "검색 1 + 생성 2"로 딱 떨어지는 것 자체가 분리 측정의 소득.
다음 개선이 각각 어디를 겨냥해야 하는지(회사 목록 질문은 청킹, 나머지는
모델 크기)가 지표에서 바로 읽힘.

**4. 검색 실패 수정** — 원인은 두 가지. 경력 요약이 담긴 About Me 청크가
노션 내보내기의 `$\color{...}$` 장식으로 오염되어 임베딩이 흐려져 있었고,
BM25의 공백 토큰화가 '회사들'(질의)과 '회사'(문서)를 다른 토큰으로 취급함.
인제스트에 마크다운 정제를 넣고 BM25에 한글 문자 bigram 토크나이저를 붙여
재인제스트한 결과:

| | 전 | 후 |
|---|---:|---:|
| recall@1 | 70% | 80% |
| recall@6 | 90% | 100% |
| MRR | 0.767 | 0.875 |

회사 목록 질문은 MISS(top-6 밖)에서 rank 4로 상승.
청크 경계가 바뀌어 gold 라벨은 같은 기준으로 재라벨링함.

다만 rank 4로는 아직 부족함. generate는 lost-in-the-middle 대응으로
top-3만 쓰기 때문에(삽질 6번), 검색에는 잡혀도 생성기에 전달되지 않음.
실제로 개선 후 전체 재평가(v6)에서도 이 질문은 여전히 거부로 실패했고
정답률은 70%로 v5와 동일(실패 구성만 이동: 검색 순위 1건 + 생성 2건 —
논문 편수를 4편으로 잘못 세는 집계 실패와 CI/CD 도구 열거 누락은 3B
편차 영역). recall@6 100%보다 recall@3이 실효 지표라는 것도 이때 확인.
다음 후보: 경력 요약 전용 청크로 rank를 끌어올리거나, generate 컨텍스트를
top-4로 늘려 lost-in-the-middle과의 트레이드오프를 재실험.

### 순서를 잘못 밟았다 — 데이터 검수를 뒤늦게 만든 이야기

위의 "임베딩 오염"을 고치고 나서야 이상한 점을 인지함. 정제가 파이프라인의
마지막에 들어와 있었음. 초기 커밋에는 정제 코드가 아예 없었고,
`clean_markdown`은 일주일 뒤 마지막 커밋에 추가됨. 그것도 검색/생성 분리
평가가 MISS를 짚어준 뒤에야.

"어떤 노이즈가 해로울지 미리 알 수 없다"는 변명은 절반만 유효함.
놓친 것은 노이즈의 예측이 아니라 인덱싱할 텍스트를 한 번 눈으로 보는 일.
청크를 몇 개만 출력해 봤으면 5분이면 보였을 문제.

그래서 그 5분을 강제하는 스크립트를 제작함 (`src/inspect_data.py`).
길이 분포, 가장 짧은 청크, 잔여 노이즈 패턴을 출력.
돌려 보니 이미 고쳤다고 생각한 데이터에 노이즈가 더 남아 있었음:

| 발견 | 청크 | 글자 | 코퍼스 대비 |
|---|---:|---:|---:|
| 노션 내부 링크(퍼센트 인코딩 경로) | 13 | 4,073자 | **9.4%** |
| HTML 태그 (`<aside>`, `<img>`) | 5 | 674자 | 1.6% |

노션은 내부 페이지 링크를 `[Experience](%EC%9D%B4%EC%9C%A4%EC%84%A0%20...)`
처럼 인코딩된 한글 파일명으로 내보냄. 링크 텍스트는 의미가 있지만 경로는
순수 노이즈인데, 그것만으로 인덱싱 대상의 9.4%를 차지하고 있었음.

수정 과정에서 걸린 함정 둘:

1. 외부 URL도 인코딩을 사용함. 논문 링크(`...articleTitle=GAN%EC%9D%84+...`)를
   같이 지우면 "깃허브 주소" 같은 질문에 답할 수 없게 됨. 단순 치환이 아니라
   `http(s)://`로 시작하는 타깃은 보존하도록 함수로 판별.
2. 중첩 링크. `[[A](url)(kisti) ](내부경로)`는 바깥 텍스트에 `]`가 있어
   링크 정규식이 못 잡음. 짝을 잃고 남은 `](경로)` 조각을 지우는 규칙을 추가.

또 `'---'`(3자), `'# 이윤선 이력서'`(9자) 같은 조각이 인덱스 자리만 차지해
`MIN_CHUNK_CHARS = 30` 필터를 추가. 전체 글자의 0.2%라 성능에는 영향이
없지만, 평균 청크 길이를 546자로 끌어내려 분포를 오해하게 만들고 있었음
(중앙값은 694자).

결과 — 청크 79개 → 67개, 중앙값 694 → 711자:

| | 검수 전 | 검수 후 |
|---|---:|---:|
| recall@1 | 80% | **90%** |
| recall@3 | 90% | **100%** |
| recall@6 | 100% | 100% |
| MRR | 0.875 | **0.95** |

recall@1의 10%p는 10문항 중 1문항이라 그 자체로는 통계적 의미 없음.
의미 있는 것은 "근무한 회사들" 질문이 rank 4 → rank 2로 올라온 것.
`generate`는 lost-in-the-middle 대응으로 top-3만 쓰기 때문에 rank 4는
애초에 생성기에 전달조차 안 됐음. 문턱을 넘은 것이라 성격이 다름.

실제로 전체 평가(v7)에서 이 질문이 처음으로 통과함.
프로젝트 시작부터 계속 실패하던 유일한 검색 기인 실패였음:

```
PASS  이윤선이 근무한 회사들을 알려주세요.
  → AICESS (2025.04~재직중) / 인피닉 (2022.08~2025.04) /
    이든티앤에스 (2022.04~2022.08) / 큐헷지 (2020.09~2021.09)
```

정답률은 70% → **90%**, 검색 기인 실패는 1건 → **0건**.

> 이 결론은 10문항 기준. 51문항 확장 후 recall@3이 83%로 하락함.
> [평가셋 확장 및 실패 원인 분석](#평가셋-확장-및-실패-원인-분석-측정-보고) 참조.

마지막으로 두 가지를 구조로 남김. `inspect_data.py --strict`를 CI에 걸어
정제가 놓친 노이즈가 있으면 빌드가 실패하게 했고(임베딩·LLM 불필요, 수 초),
청킹이 바뀌면 md5 라벨이 무효화되므로 이전 청크와 대조해 gold를 다시 붙이는
`eval/relabel_retrieval.py`를 제작. 자동 매칭이 조용히 틀리면 평가가 통째로
거짓이 되므로 매칭 점수를 전부 출력하고 임계 미만이면 반영을 거부함.

한 가지는 일부러 안 고침. mermaid 다이어그램 3청크는 문법(`graph`,
`subgraph`, 화살표)이 노이즈지만 노드 라벨은 실제 기술 키워드라 지우면
키워드까지 잃음. 검수기는 이것을 "결함"이 아니라 "판단 필요"로 분류해
보고만 하고 통과시킴. 검수기의 역할은 후보 제시이지 대신 판단하는 것이 아님.

### 도구 체이닝은 어디서 깨지나

`agent.py`는 구조적으로 multi-step(agent → tools → agent).
그러나 "구조가 지원한다"와 "이 모델이 해낸다"는 별개 문제라,
필요한 도구 수를 늘려가며 각 3회씩 측정함
(`eval/eval_tool_chain.py`, 성공 횟수 · 중앙값):

| 단계 | qwen2.5:3b | qwen2.5:7b |
|---|---|---|
| 1단 계산만 | **3/3** · 13s | **3/3** · 22s |
| 2단 검색→계산 | **0/3** · 72s | **3/3** · 197s |
| 3단 검색→날짜→계산 | **0/3** · 16s | **0/3** · 19s |

2단에서 갈림. 3B는 검색 결과를 받고 "이제 계산하겠습니다"라고 말만 하고
tool call을 내지 않아 `tools_condition`이 END로 보냄 — 버그가 아니라
모델이 주문서 대신 소감문을 낸 것. 3단은 둘 다 `get_current_date`만 부르고
입사일 검색을 건너뜀. 그리고 7B의 2단은 1단보다 9배 느림(22s→197s).

측정 방법에서 틀렸던 점 — 처음엔 셀당 1회로 재고 결론을 냄. 다음 1회에서
3B가 성공하길래 결론을 철회했는데, 3회씩 재보니 그 1회가 이상치였고 원래
결론이 맞았음. n=1은 양방향으로 위험함 — 잘못 확신하게도, 맞는 결론을
잘못 철회하게도 만듦.

3단 실패를 모델 탓으로 단정하지는 않음. 도구 설명에 "입사일·재직 기간"이
없고, 질문의 "올해 기준으로"가 날짜 도구를 먼저 부르게 유도하며, 도구 결과
후 "더 필요한가"를 묻는 장치가 없음. 셋 다 코드 쪽 책임.

### FAISS와 Qdrant를 둘 다 붙여봤다

"왜 FAISS인가"에 답하려면 다른 것을 써봐야 함. `VECTOR_STORE` 환경변수로
교체되게 하고(`src/vectorstore.py`), 같은 평가를 양쪽에 실행함.
Qdrant는 서버 없이 로컬 경로로 띄우는 임베디드 모드를 사용.

```bash
VECTOR_STORE=qdrant python src/ingest.py
VECTOR_STORE=qdrant python eval/eval_retrieval.py
python eval/compare_stores.py     # 둘을 나란히 비교
```

검색 결과는 완전히 동일함. recall@1 90% / @3 100% / MRR 0.95, 10문항의
순위까지 한 문항도 다르지 않음. 같은 임베딩에 같은 exact 검색이니 당연한
결과이며, 달랐다면 어딘가 틀린 것.

차이는 메타데이터 필터에서 나옴. FAISS는 필터를 못 받아 넉넉히 뽑아
파이썬에서 걸러야 하는데, "몇 배로 뽑을지"를 정할 근거가 없음.
`"이윤선이 근무한 회사들"` 질의에 source 필터를 걸어 측정:

| 조건 (전체 67청크 중) | 1배(6개) | 2배(12) | 5배(30) | 10배(60) | Qdrant |
|---|---|---|---|---|---|
| `resume.md` (8개) | 1/6 | 4/6 | 6/6 | 6/6 | **6/6** |
| `publications.md` (3개) | 0/3 | 0/3 | 1/3 | 3/3 | **3/3** |
| `patents.md` (1개) | 0/1 | 0/1 | 0/1 | 1/1 | **1/1** |

조건이 좁을수록 FAISS는 거의 전수를 뽑아야 함. 67청크라 60개를 뽑는 것이
가능했을 뿐, 코퍼스가 커지면 성립하지 않는 방식.
Qdrant는 필터를 검색 단계에 넣으므로 배수라는 개념 자체가 없음.

정리 — 이 규모에서는 FAISS로 충분하고(파일 2개, 의존성 하나, 서버 없음),
가격·재고처럼 선택적인 필터가 필요해지는 순간 Qdrant가 맞음.
로드는 FAISS가 조금 빨랐고(1.0s vs 2.1s) 검색 속도는 사실상 동일(0.34s vs 0.36s).

### 평균 594자가 커 보인다는 지적 — 원인은 다이어그램

산문만 보면 청크 평균이 545자로 정상 범위인데 전체 평균은 594자.
그 차이를 추적하니 `portfolio.md`의 ASCII 아키텍처 다이어그램
(```` ```markdown ```` 펜스 안의 박스 그림)이 원인.
코퍼스의 25%를 차지했고, 800자 텍스트 스플리터가 다이어그램 도중에 상한을
그어 박스가 반토막 나는 청크가 존재(예: 파이프라인이 `text_processor.py ← ITN`
줄에서 끊김). 다이어그램은 문장 단위가 없는 콘텐츠라 문자 기준 분할이
애초에 맞지 않는 케이스.

(같은 이유로 마크다운 표도 통짜 청크로 분리 — §13 참고.)

`src/ingest.py`의 `extract_diagrams()`가 인덱싱 전에 다이어그램 펜스를
본문에서 떼어내 각각 하나의 통짜 청크로 만듦. 박스 그림 문자
(`┌┐└┘│─┼┬┴` 등) 밀도가 5%를 넘는 펜스만 다이어그램으로 판정하고, API
경로 예시(```` ```POST /api/... ``` ````)처럼 짧고 검색 가치가 있는 펜스는
본문에 유지.

```
전: 67청크 — 산문 평균 594자 (다이어그램이 섞여 부풀려짐)
후: 51청크 — 산문 48개(평균 512자) + 다이어그램 3개(4,395~5,079자, 상한 미적용)
```

정답 청크(gold)에 다이어그램이 하나도 걸려 있지 않아 recall·정답률은
그대로(recall@1 90%, 정답률 90%). 수치가 안 바뀐 것이 실패는 아님 —
이 결함은 애초에 gold가 못 보는 지점이었고, 그래서 당시 평가셋만으로는
검증이 안 된다는 의미이기도 함.

### 청크 크기를 스윕해봤다

800자는 튜닝한 값이 아니라 합리적인 기본값이었고 실제로 재본 적이 없어,
300~1600자로 바꿔가며 검색 성능을 측정함 (`eval/sweep_chunk_size.py`).

문제가 하나 있었음 — gold 라벨이 청크 md5라 크기를 바꾸면 전부 무효화됨.
그래서 이 스윕만은 크기와 무관한 정답 앵커 문자열로 gold를 정의
(예: TTFB 질문 → `"2292"`, 회사 목록 → `"Experience Overview"`).
앵커는 각각 당시 인덱스에서 1~4청크에만 등장하도록 좁게 선정.

| 크기 | 청크수 | 중앙값 | recall@1 | recall@3 | recall@6 | MRR |
|---:|---:|---:|---|---|---|---:|
| 300 | 170 | 239 | 70% (기준선 2%) | **100%** (5%) | 100% (10%) | 0.833 |
| 500 | 103 | 440 | 60% (3%) | **100%** (7%) | 100% (14%) | 0.783 |
| 800 | 67 | 711 | 90% (4%) | **100%** (11%) | 100% (21%) | 0.950 |
| 1200 | 46 | 1007 | 90% (5%) | **100%** (15%) | 100% (28%) | 0.933 |
| 1600 | 37 | 1490 | 100% (6%) | **100%** (19%) | 100% (34%) | 1.000 |

recall@3이 전 구간 100%. `generate`가 top-3만 쓰므로, 생성기에 전달되는
범위에서는 이 코퍼스에서 청크 크기가 병목이 아니라는 판정.
top-3 밖으로 밀린 질문도 어느 크기에서든 0건.

> recall 수치는 10문항 기준이며 51문항에서는 83%.
> 다만 "청크 크기가 병목이 아니다"라는 결론은 유지됨 — 51문항 진단에서도
> 근거 손실 문항은 0건.

recall@1은 클수록 좋아 보이지만 그대로 믿으면 안 됨. 청크가 커지면 개수가
줄어 무작위 기준선이 2%에서 6%로 상승(top-6 기준으로는 10%→34%).
그리고 10문항이라 60~100%는 1~4문항 차이.

무엇보다 이것은 검색만 잰 것. 1600자 청크 3개를 프롬프트에 넣으면
4,500자가 되어 lost-in-the-middle과 3B의 컨텍스트 한계에 걸림.
검색은 잘게 자를수록, 생성은 크게 자를수록 유리해서 방향이 반대.
하나의 크기로 둘 다 잡는 대신 parent-child(작은 청크로 검색, 부모 청크로
생성)로 가는 것이 맞다는 근거가 됨.

### 후속(2026-08) — 65문항·정본 의미론 재스윕: 결론이 절반 뒤집혔다

위 표는 10문항·"gold를 하나라도 회수" 기준. 한계 절에 "10문항이 이미 두 번
잘못된 결론을 만들었다"고 적어 둔 채였고, 집계·열거처럼 근거 전수가 필요한
질문에서 recall류 지표가 실패를 숨긴다는 것도 eval_coverage.py를 만들며
이미 알고 있었음. 그래서 같은 스윕에 `gold_anchor_sets`(정본 의미론 —
어느 한 근거 경로의 전수 충족) 커버리지 65문항을 추가해 재측정.
앵커는 크기 무관이라 재라벨링이 불필요하고, LLM이 없어 결정적.

먼저 부수 발견 — 스윕 스크립트 자체가 죽어 있었음. 인덱스-chunks.jsonl
결속 가드(`check_index_consistency`)를 도입할 때 그 가드가 지키려던 바로 이
스크립트("중단하면 어긋난 상태가 된다")를 갱신하지 않아, 스윕이 덮어쓴
chunks.jsonl과 옛 매니페스트가 어긋나 첫 스텝의 hybrid_search에서 죽는 상태.
가드 도입 이후 아무도 이 스크립트를 다시 돌리지 않아 잠복해 있던 결함이며,
스윕이 매니페스트를 같이 갱신하도록 수정함.

| 크기 | 청크수 | sat@1 | sat@3 | **sat@5** | sat@6 | 근거손실 |
|---:|---:|---:|---:|---:|---:|---:|
| 300 | 136 | 49% | 69% | **77%** | 78% | 0건 |
| 500 | 86 | 54% | 74% | **89%** | 91% | 0건 |
| 800 | 58 | 46% | 78% | **88%** | 94% | 0건 |
| 1200 | 40 | 52% | 71% | **88%** | 91% | 0건 |
| 1600 | 32 | 58% | 78% | **85%** | 91% | 0건 |

(sat@5가 실효 지표 — generate가 top-5를 받음. 800자 열이 당시 프로덕션
커버리지 실측(46/78/88/94)과 정확히 일치해 측정기 자체의 교차 검증이 됨.
10문항 recall 표도 같은 실행에서 함께 측정했고 `results_chunk_sweep.json`에
있음 — 이번에도 recall@1은 1600자에서 100%로 "클수록 좋아 보이는" 착시를
만듦.)

뒤집힌 것과 유지된 것:

- **300자는 절벽**(sat@5 77% vs 88~89%, −7문항). 옛 10문항 표에서는
  300자도 recall@3 100%로 "문제없음"이었음 — "하나라도 회수" 정의가
  집계·열거의 전수 실패를 숨긴 것. 작은 청크는 같은 근거를 더 많은 청크에
  흩어 놓으므로, top-5 슬롯 안에 전부 들어와야 하는 질문일수록 불리해짐.
  위 본문의 "검색은 잘게 자를수록 유리"는 이 평가셋에서 기각됨 —
  parent-child(child 300자)가 base를 못 이겼던 결과와 뒤늦게 앞뒤가 맞음.
- **"청크 크기가 병목이 아니다"는 500~1200 구간에서만 유지**(sat@5
  88~89%로 평평). 800은 그 구간 안이고 sat@6은 오히려 최고(94%)라 기본값
  유지. 1600은 sat@5가 85%로 밀리기 시작 — 큰 청크는 개수가 줄어
  "이 중 5개" 슬롯 경쟁이 빡빡해지는 쪽의 비용.
- **근거 손실(청킹이 앵커 문자열을 반토막) 0건 — 어떤 크기에서도.**
  하락은 전부 검색 순위 문제이지 청킹의 정보 파괴가 아님. 이 구분을
  세지 않았다면 300자의 절벽을 "청킹이 근거를 부순다"로 오독했을 것.

수치보다 남는 것은 이번에도 정의. 같은 스윕, 같은 코퍼스에서 지표 정의
하나("하나라도" → "전수")가 300자의 판정을 "문제없음"에서 "절벽"으로 바꿈.
10문항 recall만 보고 "작게 잘라도 된다"고 결론 냈다면 집계·열거 7문항을
조용히 버리는 선택이었을 것.

### 재재스윕(2026-08-12) — 표를 빼내고 나니 800이 단독 최고가 됐다

800자는 표·다이어그램을 통짜로 빼내기 **전** 코퍼스에서 정한 값.
긴 블록이 산문에서 전부 빠져나갔으니 산문 분포 자체가 달라졌고, 다시 잴 값이 있었음.
평가셋도 65 → 88문항이 됨(경로 기반 커버리지 기준).

| 크기 | 청크수 | 중앙값 | sat@3 | **sat@5** | sat@6 | cov@5 |
|---:|---:|---:|---:|---:|---:|---:|
| 300 | 128 | 243자 | 70% | 83% | 86% | 86% |
| 500 | 81 | 385자 | 73% | 86% | 92% | 88% |
| **800** | 54 | 666자 | **80%** | **92%** | **95%** | **93%** |
| 1200 | 40 | 790자 | 73% | 85% | 91% | 88% |
| 1600 | 32 | 1017자 | 74% | 86% | 92% | 88% |

직전 재스윕에서 "500~1200 구간이 평평하다(88~89%)"였던 것이, **800 단독 최고(92%,
이웃과 +6%p)**로 바뀜. 통짜로 빠져나간 표·다이어그램이 예전엔 어떤 크기에서든 산문
청크를 오염시키며 차이를 뭉개고 있었다는 해석과 맞음. 근거 손실은 어떤 크기에서도
0건.

10문항 앵커 표는 이번에도 반대로 말함 — 1200·1600이 recall@1 100%·MRR 1.000. 같은
줄의 **무작위 기준선이 4% → 8%로 같이 오르는 것**이 답. 청크가 줄면 아무거나 찍어도
맞을 확률이 오름. "10문항이 이미 두 번 잘못된 결론을 만들었다"는 기록이 세 번째로
재현됨.

#### 스윕이 프로덕션과 다른 코퍼스를 재고 있었다

이번 스윕 전에 고친 것. 청킹 파이프라인이 세
군데(`ingest.main`·`sweep_chunk_size`·테스트)에 각각 적혀 있었고, 스윕 쪽만 통짜
청크 배치와 위치 메타데이터를 빠뜨리고 있었음 — **청크 크기 결론을 내는 바로 그
스크립트가 다른 코퍼스를 재고 있었음.** `ingest.build_chunks()` 하나로 합침.

#### 캐시 키에는 청크 크기가 아예 없었다

`_config_fingerprint`가 `config.knobs()`만 쓰는데,
`CHUNK_SIZE`·`CHUNK_OVERLAP`·`MIN_CHUNK_CHARS`는 `_env()`를 안 거친 일반 상수라
knobs()에 없음. 표 분리 같은 **코드 변경**이나 `data/docs` 편집은 애초에 손잡이가
아님. 즉 청킹을 바꿔 재인제스트해도 `/ask`가 옛 코퍼스 시절 답을 그대로 돌려줌.

§12에서 잡은 "손으로 적은 목록이 드리프트한다"와 같은 사고가, 이번엔 목록이 아니라
**'손잡이'라는 범주 자체의 구멍**으로 남아 있었음. 목록을 늘리는 대신 인덱스
지문(`chunks_md5`) 하나를 키에 넣음 — 코퍼스가 1바이트라도 다르면 다른 키가 되므로
청크 크기·정제 규칙·문서 편집·인제스트 코드 변경을 전부 덮음.

### 멀티홉 비교 평가에서 배운 것

멀티홉 3문항으로 단일 RAG와 팀을 비교함 (`eval/evaluate_team.py`).
수치보다 실패 패턴에 정보가 많았음.

- 단일 RAG는 사실 수집 단계부터 무너짐 — "TTS는 2022년부터 시작"처럼
  없는 사실을 지어내거나 아예 못 찾음.
- 팀은 sub-사실 수집은 정확했음 (두 프로젝트의 기간을 모두 정답으로 회수).
  그러나 synthesizer 단계에서 3B 모델의 비교·집계 추론이 흔들림 —
  "2024.03과 2025.09 중 무엇이 먼저인가"를 실행에 따라 맞히기도 틀리기도
  하고, 청크에 흩어진 논문 편수를 세는 것도 실패.
- 키워드 채점은 이런 '근거는 맞는데 결론이 틀린' 답을 잡지 못한다는 것도
  확인함 (양쪽 다 false-pass 발생). LLM-judge나 결론 필드 구조화가 필요한 지점.

정리: planner-worker 구조는 검색·수집 문제를 풀었고, 남은 병목은 소형
모델의 산술·비교 추론. 날짜/수량 비교를 모델에 맡기지 않고 결정적 코드로
처리하거나 모델을 키우면 해결될 영역.

## 평가셋 확장 및 실패 원인 분석 (측정 보고)

위 기록은 모두 10문항 평가셋 기준. 51문항으로 확장한 뒤 재측정한 결과와
그 과정에서 드러난 결함을 정리함.

측정 환경: qwen2.5:3b / bge-m3 / RTX 5080. 위쪽 측정(CPU 폴백)과 지연
수치는 비교 불가하며, 정확도·recall은 하드웨어와 무관.

### 1. 평가셋 확장 (10 → 51문항)

10문항에서는 1문항이 10%p이므로 정답률 90%의 95% 신뢰구간이 약 60~98%.
개선 여부를 판정할 해상도가 없어 51문항으로 확장하고 유형을 부여함.

| 유형 | fact | enumeration | aggregation | temporal | comparison | trap | refusal |
|---|---:|---:|---:|---:|---:|---:|---:|
| 문항 수 | 19 | 8 | 6 | 4 | 2 | 2 | 10 |

> **후속(63문항):** 위 표에서 `comparison`·`trap`이 각 2문항인 것이 그대로
> 남아 있었음. 10문항 평가셋을 버린 이유(1문항이 결과를 좌우)가 이 두
> 유형 안에서는 해소되지 않은 것 — 실제로 1문항이 50%p를 움직여 유형별
> 수치를 인용할 수 없었음. 각 8문항으로 늘려 63문항이 됨.
>
> **재작업(71문항):** 그때 넣은 trap 6문항은 함정이 아니었음 — 14B 8/8,
> 3B도 5/6을 맞힘. 설계 원리를 뽑지 않고 늘린 탓. 기존 2문항을 분석하니
> 공통 구조가 있었음: *한정어가 가리키는 값이, 코퍼스가 압도적으로
> 강조하는 값과 다르다*("제2저자 논문 몇 편" → 문서는 "논문 7편(제1저자)"를
> 반복 강조). 실패한 6문항은 지우지 않고 실제 성격대로 재분류하고
> (trap → fact·aggregation·temporal), 그 원리로 새 trap 6문항을 제작 —
> 전부 개선 "전" 값을 묻는 형태. 성과 문서라 개선 후 수치는 반복되고
> 개선 전 수치는 배경에 한 번씩만 나오기 때문.
> 여기에 `should_use_team()` 가드 검증용으로 comparison∩aggregation
> 2문항을 더해 71문항이 됨.
>
> | 유형 | fact | enumeration | aggregation | temporal | comparison | trap | refusal |
> |---|---:|---:|---:|---:|---:|---:|---:|
> | 문항 수 | 23 | 8 | 7 | 5 | 10 | 8 | 10 |
>
> **확장(75 → 100문항, 2026-08-11):** 목적은 두 가지. (1) 유형별 표본이
> 5~10이라 유형별 수치가 "방향성 참고용"에 머무름 — 특히 temporal
> 5문항은 1문항이 20%p. (2) 심판(LLM-judge) 측정에 오답 표본이 부족 —
> verify 실측에서 실질 오답이 6건뿐이라 검출률의 분모가 없었음.
> 원칙은 기존 것을 그대로 따름: trap은 설계 원리("한정어가 가리키는 값 ≠
> 코퍼스가 강조하는 값" — 제2저자 논문의 제목, 구버전 엔드포인트의
> TTFB)로만 늘리고, comparison은 결론을 구별 가능한 값으로 묻고(더 오래
> 근무한 회사의 "근무 기간"), 신규 문항 전부 앵커 라벨(md5 없음),
> 집계·비교는 앵커로 검증. PDF 코퍼스 겨냥 문항도 확대(손실 함수 조합
> 수·융합 방식 열거·Dice vs Focal MIoU 비교). 추가 직후
> `audit_patterns --strict`·`audit_coverage` FAIL 0 확인.
>
> | 유형 | fact | enumeration | aggregation | temporal | comparison | trap | refusal |
> |---|---:|---:|---:|---:|---:|---:|---:|
> | 문항 수 | 26 | 13 | 13 | 11 | 15 | 10 | 12 |
>
> **새 기준선(qwen2.5:7b × 2회): 85/100, 83/100.** 기존 75문항 부분이
> 65·64/75로 이전 기준선(85%)과 일치하고, 신규 25문항은 20·19/25(78%)로
> 의도대로 더 어려움. 양쪽 모두 실패한 신규 문항 검수에서 나온 것 둘:
>
> - **채점기 미스 1건** — "조합 몇 가지?"에 모델이 5개를 전부 나열하고
>   결론을 "总共比较了5种"이라고 중국어 단위로 말해 한국어 단위
>   패턴(가지/개)에 안 걸림. 전각 문장부호(§10)에 이은 qwen 중국어
>   혼입의 새 변형(단위어). 패턴에 `5\s*[종种]`을 추가하고 저장된 두 런을
>   재채점 — 그 문항만 뒤집힘(84→85, 82→83).
> - **새 실패 모드 포착** — "우수논문상 몇 회?"에 "두 차례": 같은 상이
>   여러 문서에 중복 서술된 것을 이중 계산. 중복 코퍼스가 세기를 깨는
>   실패로, DOCX 근중복이 top-N 슬롯을 잠식하던 것과 같은 뿌리.
>   "첫 특허 등록 vs 수상" 비교에서는 특허 등록 연도를 2018로 환각 —
>   심판(judge) 측정에 필요했던 실질 오답 표본이 실제로 늘어남(6건 →
>   두 런 합산 기준 두 자릿수).

주요 변경 두 가지.

- **거부 문항 10개 추가.** 기존 `is_pass()`는 거부 답변("찾을 수 없습니다")을
  무조건 오답 처리. 따라서 코퍼스에 답이 없는 질문을 평가셋에 넣을 수
  없었고, 환각을 측정하는 지표가 존재하지 않았음. `expect_refusal`
  플래그를 추가해 해당 케이스만 채점을 반전.
- **gold를 앵커 문자열로 지정.** 신규 문항은 md5 대신 청크 크기 스윕에서 쓰던
  앵커 방식을 적용. 재청킹 시 무효화되지 않고 수작업 라벨링이 불필요.

비교 문항은 설계를 수정함. "인피닉과 이든티앤에스 중 어디에 더 오래
근무했나요?" 형태는 두 회사명이 답변에 모두 등장하므로 오답도 패턴을
통과함(멀티홉 평가에서 지적한 false-pass와 동일). "더 오래 근무한 회사의
근무 기간은?"으로 바꿔 결론을 구별 가능한 값으로 답하게 함.

### 2. 채점기 결함 — 정답 4건을 오답으로 집계

51문항 실행 결과 67%. 실패 답변을 검토한 결과 4건이 정답이었음.
4건 모두 모델이 사용한 표현이 원본 문서에 실재하는 표기.

| 문항 | 모델 답변 | 기존 패턴 |
|---|---|---|
| 팝 노이즈 | 잉여 버퍼 | `Residual Buffer` (문서: 영문 4회, 한글 1회) |
| 웹소켓 | `pwd_changed_at` | `password_changed_at` (문서: 각 3회, 1회) |
| AICESS 입사일 | 2025년 **04**월 | `4월` (앞자리 0 미고려) |
| 레퍼런스 음성 | 24**,**000 Hz | `24000` (천단위 콤마 미고려) |

거부 판정 정규식도 좁았음. "정보는 전혀 포함되어 있지 않습니다"를 거부로
인식하지 못해 거부 문항을 실패로 집계함. 정규식 확장 전 저장된 51건을
재채점해 1건만 FAIL→PASS로 바뀌고 나머지는 불변임을 확인(`rescore.py` 방식).

수정 후 동일 답변 재채점 결과 67% → 73%. 6%p가 채점기 결함이었음.

재발 방지를 위해 `eval/audit_patterns.py`를 추가하고 CI에 연결.
기계가 확정 가능한 항목(코퍼스와 매치되지 않는 패턴 = 영구 실패 문항)만
빌드를 실패시키고, 동의 표기 여부는 스니펫만 출력하고 판단은 사람에게
맡김(`audit_gold.py`와 동일 방침).

이 과정에서 검증 규칙 자체의 오류도 발견함. "패턴은 코퍼스와 매치돼야
한다"는 불변식은 원문 인용형에만 성립함. "2023년 논문 몇 편?"의 정답
`3편`은 표의 행을 집계해야 나오는 값이라 코퍼스에 존재하지 않음.
집계·비교 유형은 패턴 대신 앵커로 검증하도록 분리함.

### 3. 실패 원인 분해 (`eval/diagnose.py`)

수십 초에 완료됨.

**청킹 층 — 결함 없음.** 근거 앵커를 담은 청크가 0개인 문항: 0건.
청킹이 근거를 손실시킨 사례 없음. 위 청크 크기 스윕의 결론은 51문항에서도
유지됨. 단, 근거가 3청크 이상에 분산된 문항이 8건(TTS 엔진 관련 문항은
10청크)으로, 열거·집계 유형의 난이도를 높이는 요인.

**검색 층.**

10문항에서 100%였던 recall@3이 83%로 하락. 위의 "검색 기인 실패 0건"은

근거가 검색되고도 생성기에 전달되지 않는 것이 병목.

### 4. BM25 토크나이저 결함

진단 중 BM25 미검출 문항이 다수 확인되어 토크나이저를 점검함.

```
질의 'Throughput은'  → ['throughput은', 'th','hr','ro','ou',…]
문서 'Throughput:'   → ['throughput:']
```

구두점·조사가 토큰에 결합되어 공통 토큰 `throughput`이 양쪽 모두에서
생성되지 않음. 또한 어절에 한글이 포함되면 ASCII 구간까지 문자 bigram으로
분해되어 노이즈가 됨. 이 코퍼스의 질의는 대부분 "gRPC로", "자격증을"처럼
혼합 형태라 BM25가 실질적으로 동작하지 않는 상태였음.

기존 10문항이 이를 검출하지 못한 이유는, BM25 도입 계기였던 `Jenkins`·
`Pyannote`가 조사가 붙지 않는 고유명사였기 때문.

문자 종류별 런 단위 분해로 수정(`0.68`·`password_changed_at`·
`10-2538225-0000`은 단일 토큰 유지). 수정 후 지표 변화는 미미함 —
bm25 recall@3 68% → 71%, hybrid 83% 유지. 41문항에서 3%p는 약 1문항으로
편차 범위. 결함은 실재했으나 병목은 아니었음. 해당 질의를 임베딩이 이미
처리하고 있었기 때문.

**후속(2026-08, 한국어 전처리 재점검 중 발견)**: 같은 방식의 결함이 천단위
콤마에도 있었음 — `.`·`-`·`_`는 토큰을 잇는 구두점으로 처리했지만 `,`는
빠져 있어, 코퍼스의 "2,292"와 질의의 "2292"가 토큰을 하나도 못 겹침
(코퍼스 전수 검사: `portfolio.md`에 `24,000`·`32,768`·`9,600`·`2,048` 등
천단위 콤마 4건 확인). `.`·`-`·`_`와 달리 콤마는 지워야 같은 숫자가 됨
(잇는 것이 아니라). 토큰화 전에 `\d,\d{3}` 패턴만 좁혀서 콤마를 삭제
(공백이 있는 열거 콤마 "Jenkins, ArgoCD"는 유지). 코퍼스에 목록 용도의
무공백 콤마 나열은 0건임을 확인 후 반영 — 이번에도 재정형 검사(NFC·전각문자·
자소분리)는 전부 깨끗했고, 결함은 코퍼스가 아니라 토크나이저 쪽에 있었음.

**후속 2(2026-08, 같은 재점검에서 발견)**: "많이 쓰이는·요즘 추세" 전처리를
다시 훑다가 NFKC 정규화 누락을 발견. 코퍼스에 `unicodedata.
normalize("NFKC", text)`를 통과시켜 보니 133곳이 변경됨 — 전부
`segmentation-paper.pdf`의 loss function 수식(pypdf가 수식을 이탤릭
유니코드로 그대로 추출: "𝐼𝑜𝑈"·"𝐿𝑓𝑜𝑐𝑎𝑙" 등)과 resume.md의 원문자 글머리
("①②③④⑤")·위첨자("O(N²)"). 이 문자들은 `[0-9A-Za-z]`에 안 걸려
`_RUNS`가 통째로 건너뛰므로 "IoU"와 "𝐼𝑜𝑈"가 겹치는 토큰 0개였음 — 앞선
콤마 결함과 같은 유형(호환 유니코드가 ASCII 표준형으로 안 좁혀짐).
토큰화 전에 NFKC 정규화를 한 번 통과시키는 것으로 수정. 완성형 한글
음절은 NFKC에서도 NFC와 동일해(정준 분해 후 재조합 결과가 같음) 기존
한글 토큰화에는 영향이 없음을 회귀 테스트로 확인.

당시 평가셋에는 이 결함만으로 실패하는 문항이 없었음(`Focal`/`Dice`
패턴은 같은 청크의 평문 "Focal loss" 텍스트로 이미 통과 중) —
콤마 결함과 마찬가지로 실재했으나 병목은 아니었던 사례.
`eval_retrieval.py` 재실행 결과 지표 변화 없음(recall@1 64%, recall@3
79%, recall@6 93%, MRR 0.731).

### 5. `GENERATE_TOP_N` 스윕 (`eval/ab_top_n.py`)

51문항 × 2회.

| | top-3 | top-4 | top-5 | top-6 |
|---|---:|---:|---:|---:|
| 정답률 | 68% | 70% | 75% | 75% |
| 지연 중앙값 | 0.8s | 0.9s | 1.0s | 1.1s |

진단이 지목한 문항이 실제로 개선됨. rank 4·5 문항 3건은 전부 0/2 → 2/2.
rank 6 문항은 개선되지 않거나 악화됨. `generate`가 랭크 역순으로 배치하므로
rank 6 근거는 약 4천 자 컨텍스트의 선두, 즉 소형 모델의 주의가 가장 약한
위치에 놓이기 때문.

top-5와 top-6은 정답률이 동일하나 top-6에서 부작용이 나타남. 거부 20/20 →
19/20(환각 발생), temporal 8/8 → 6/8. **기본값을 top-5로 변경.**

유형별로 트레이드오프가 양방향 모두 관측됨. comparison 0/4 → 4/4(두 사실을
모두 받아야 비교가 성립), enumeration 8/16 → 9/16, temporal 8/8 → 7/8
(lost-in-the-middle 비용). 위에서 "다음 후보"로 기록한 실험이며 예상한
트레이드오프가 실측됨.

런 편차가 ±6%p이므로 top-5와 top-6은 사실상 동률. 확정적인 결론은
"top-3이 가장 낮다"이며, 독립적인 두 차례 스윕에서 동일하게 나타남.
`GENERATE_TOP_N` 환경변수로 되돌릴 수 있음.

### 6. grade 판정기 측정 (`eval/eval_grade.py`)

검색은 recall, 답변은 정답률로 측정했으나 판정기 자체의 지표가 없었음.
`retrieval_set.json`의 gold에서 라벨을 구조적으로 유도해(positive는 실제
top-3의 gold 포함 여부, negative는 타 문항의 top-3 결합) 판정기만 측정.

```
판정 정확도  87.0%      기준선('항상 통과') 43.5%
오탐 20.0%   미탐 7.7%   파싱 실패 0.0%   판정 흔들림 0/23
```

파싱은 병목이 아니었음. 3B는 `yes`/`no`만 출력함. "파싱 견고화가 개선을
가져올 것"이라는 가설을 측정으로 기각. 다만 파서는 3값(yes/no/unparsed)
으로 변경 — 기존 2값 구조에서는 파싱 실패가 fail-open에 흡수되어 발생률을
측정할 방법이 없었기 때문.

수정 과정에서 기존 파서의 결함도 확인함. `"아니" in verdict`로 부정을
판정했으나 `아닙니다`는 아+닙+니+다이므로 매치되지 않음. 반대로 `아니면`은
부정이 아님에도 매치되어 불필요한 재검색을 유발함.

이 측정으로 기존 지표 하나가 설명됨. 재작성률 30%는 검색 품질 지표가
아니라 판정기 오탐률이었음. 검색은 gold를 rank 1로 반환했으나 판정기가
2문항을 `no`로 오판해 재작성이 발동한 결과.

### 7. RAGAS 도입 검토 — 미도입

채점기 결함 4건과 비교 문항의 구조적 한계를 근거로 RAGAS 도입을 검토하고
실측함.

- **설치**: `pip install ragas` 후 임포트 실패(`langchain_community.chat_models
  .vertexai` 부재). `langchain-community<0.4` 고정 필요 → 본체(0.4.x)와 충돌 →
  venv 분리 필요.
- **심판 정확도**: 프로젝트 전제(전부 로컬)에 따라 `qwen2.5:3b`를 심판으로
  사용. 저장된 51건에 faithfulness를 계산하고, 패턴 채점이 신뢰 가능한
  유형(fact·temporal)에서 일치율을 측정함.

| 임계 | 0.3 | 0.5 | 0.7 | 0.9 |
|---|---:|---:|---:|---:|
| fact·temporal 일치율 | 45% | 50% | 36% | 36% |

정답이 확정된 문항에서 심판이 절반만 일치함. 51건 중 1건은 구조화 출력
파싱이 재시도 후에도 실패했고, 정답에 0.0을 오답에 1.0을 부여하는 등 오류
방향도 일관되지 않음. 정확도가 낮은 것이 아니라 정보량이 없는 것.

RAGAS 자체의 문제가 아니라 심판을 도입할 조건이 아님. faithfulness는 주장
분해 후 주장별 검증을 요구하므로 yes/no 단일 토큰 판정(정확도 87%)보다
난도가 높음. 도입 조건을 다음과 같이 정의함.

> 로컬 7B 이상 모델로 동일 검증을 재실행해 일치율 90% 이상일 때
> comparison·aggregation 유형에 한해 도입. 외부 API 심판은 "전부 로컬"
> 전제 및 이력서 데이터의 제3자 전송 문제로 배제.

**후속(2026-08-11) — 위 게이트 정의 자체에 결함이 있었음.** 기본 모델이
7b가 되어 게이트를 실측할 차례였는데, 그 전에 in-repo 심판(`graph.verify`,
yes/no groundedness)을 7b 답변 75건에 돌려 보니(`eval/eval_verify.py`)
심판-채점 일치율이 실질 답변 60건 기준 55/60 = 92%로 "90% 게이트 통과"처럼
보였음. 그런데 아무것도 판정하지 않는 상수 심판("항상 grounded")이 이미
54/60 = 90% — 정답률이 85~90%인 평가셋에서는 일치율의 바닥이 정답률 그
자체라서, "일치율 90%"는 심판이 아니라 평가셋 난이도를 재는 숫자가 됨.
pdm-agent에서 배운 "지표엔 자명한 대조군 필수" 교훈이 심판 게이트에도
그대로 적용되는 것을 놓쳤던 것.

게이트를 재정의함: 절대 일치율이 아니라 **상수 심판 대비 순증**(오답
검출 − 오경보)이 유의미할 때 도입. 그 기준으로 7b 심판은 +2검출/−1오경보로
아직 정보량이 부족 — 자세한 수치는 아래 "verify 판정기 실측" 참고.
심판이 값을 하려면 오답이 흔한 부분집합(저정답률 유형)에서 검출을 재야
하고, 그것은 표본이 커져야 가능함.

### 8. 구조 점검에서 고친 것

전체 구조를 다시 보고 위험도 높은 셋을 수정함.

- **인덱스와 `chunks.jsonl`에 결속이 없었음.** 벡터 검색은 인덱스를, BM25는
  `chunks.jsonl`을 각각 읽는데 같은 인제스트 산출물이라는 보장이 없었음.
  어긋나면 서로 다른 청킹 두 개를 RRF로 섞게 되는데 증상이 없음.
  `sweep_chunk_size.py`가 두 파일을 매 스텝 덮어쓰므로 중단하면 실제로 이
  상태가 됨. 인제스트가 `data/index_manifest.json`에 청크 지문을 남기고
  로드 시 대조해 즉시 실패시키도록 수정.
- **사전 점검이 없었음.** `src/` 전체에 `except`가 2개뿐이라 Ollama 미기동·
  인덱스 없음·모델 미보유가 전부 스택트레이스로 노출. `preflight.py`가
  표준 라이브러리만으로 셋을 확인하고, `/ask`는 추론 실패를 503으로 변환.
  요청 길이 상한(2000자)도 추가.
- **결과 파일에 환경 지문이 없었음.** 위의 "90% vs 74%"가 비교 불가였던
  구조적 원인. `runmeta.py`가 모델·Ollama 버전·인덱스 해시·파라미터·
  하드웨어를 `results.json`에 함께 저장.
  > **후속(2026-08): 그 교훈이 절반만 적용돼 있었음.** `runmeta`를 쓰는 건
  > `evaluate.py` 하나뿐이었고, A/B·스윕 스크립트 9개 전부가 환경을 기록하지
  > 않았음. 병합 후 결과 파일들을 훑다가 `model` 필드가 `?`로 비어 있는 것을
  > 보고 발견 — 3B로 잰 결과와 14B로 잰 결과가 한 폴더에 섞여 있는데
  > 파일만 보고는 구분할 수 없는 상태였음(이 저장소가 정확히 그 문제로
  > 데였는데도). 8개 스크립트에 지문을 붙였고, 조건 루프가 `config`를
  > 변형하기 전에 찍도록 위치를 맞춤(끝에서 찍으면 마지막 조건 값이
  > 기록돼 오히려 오해를 만듦). `audit_docs.py`가 이 관례를 강제함.

또한 청크에 위치 메타데이터(`chunk_index`, `doc_index`, `doc_total`)를
부여함. 섹션 헤딩 기반 부모(parent-child)는 이 코퍼스에서 불가능 —
`resume.md`·`publications.md`·`patents.md`에 마크다운 헤딩이 각 1개(제목)
뿐이고, 가장 자주 검색되는 문서가 평문. `page_content`를 바꾸지 않으므로
gold 라벨 무효화는 0건.

### 9. 시도했으나 채택하지 않은 것들

`GENERATE_TOP_N` 외의 레버는 전부 정답률로 이어지지 않았음. 기록해 둠.

| 시도 | 검색 지표 | 정답률 | 판정 |
|---|---|---|---|
| `TOP_K` 6 → 15 | recall@5 90% → 95% | 76% → 74% | 미채택 |
| BM25 토크나이저 수정 | recall@3 68% → 71% | 변화 없음 | 코드는 유지(실재한 버그) |
| 이웃 확장 (`N=3 W=1`) | — | 80% / 75% (재현 실패) | 기본 꺼둠 |
| 컨텍스트 배치 순서 | — | 역순 74% / 정순 74% / 샌드위치 78% | 기본 유지 |
| 다이어그램 제외 | 컨텍스트 −41% | 74% → 74% | 기본 유지 |

세 번 반복된 패턴 — 검색 지표는 오르는데 정답률이 안 따라옴.
원인은 동일함. `generate`가 랭크 역순으로 배치하므로 새로 들어온 하위 랭크
근거는 프롬프트 맨 앞, 소형 모델의 주의가 가장 약한 자리에 놓임.
**근거를 컨텍스트에 넣는 것과 모델이 그것을 쓰는 것은 다른 문제.**

두 번 관측된 것이 하나 더 있음. 컨텍스트를 키우면 환각 저항이 먼저 무너짐 —
top-6에서 거부 20/20 → 19/20, `N=5 W=1`(컨텍스트 2배)에서 17/20,
샌드위치에서 19/20. 각각 단일 실행이라 확정은 아니나 방향이 같음.

유형별로는 방향이 갈림. 집계는 문맥이 이어져야 세므로 이웃 확장에서 두 번
모두 개선(6/12 → 10/12, 9/12)됐고, 열거는 항목이 여러 청크에 흩어져 있어
개수가 필요함(샌드위치 7/16 → 12/16). 하나의 설정으로 둘을 동시에
만족시키지 못함 — 질문 유형별 라우팅이 다음 후보가 된 배경.

실험용 손잡이는 전부 환경변수로 유지함. 모델·인덱스 쪽이 `LLM_MODEL`,
`EMBED_MODEL`(임베딩, 기본 `bge-m3` — `compare_embeddings.py`로 대안과
비교), `VECTOR_STORE`. 검색 쪽이 `TOP_K`, `RRF_K`, `RERANK`, `HYDE`,
`HYDE_MODE`. 컨텍스트 쪽이 `GENERATE_TOP_N`, `NEIGHBOR_WINDOW`,
`CONTEXT_ORDER`, `EXCLUDE_DIAGRAMS`, `GENERATE_PROMPT_VARIANT`. 흐름 쪽이
`MAX_REWRITES`, `TYPE_ROUTING`, `TEAM_ROUTING`, `VERIFY_GROUNDING`.
기본값의 근거는 `config.py` 주석에 측정치와 함께 기록해 둠.

손잡이는 전부 `config._env()` 한 통로로만 읽음. `config.knobs()`가 항상
완전하므로 캐시 키(`cache.py`)·실행 지문(`runmeta.py`)·문서화 검사
(`audit_docs.py`)가 손으로 유지하는 목록 없이 자동으로 따라옴 — 예전엔
셋 다 각자 목록을 들고 있다가 드리프트함(§12).

### 10. 채점 기준 변경 이력

v5(패턴 채점)에 이어 두 번째 변경(동의 표기 인정, `expect_refusal` 추가,
거부 정규식 확장). 위 v1~v7 표와 직접 비교 불가.

여섯 번째 변경(2026-08-31): 숫자 패턴 앞에 `(?<!\d)` 추가 — **오답이 통과하는
경로를 막은 것**. `50\s*ms` 는 "250ms" 안에서도 매치되므로, 캐시 히트 TTFB를
묻는 문항에 모델이 "250ms"라고 답해도 통과함. 코퍼스에 실재하는 값으로
검사하니 5개 패턴이 같은 병이었음(`50ms`↔150·250·450·1850ms, `2초`↔102·512초,
`5분`↔15·25분, CER `3~5`, 폴백 TTL `5초`). 저장된 세 런(140문항·100문항×2)을
재채점한 결과 **뒤집힘 0건** — 결함은 실재했으나 기록된 실행에서는 발현하지
않았음. 전각 문장부호(세 번째 변경)와 같은 성격의 순수 안전망이며, 그래서
이전 수치와의 비교 가능성도 깨지지 않음.

다섯 번째 변경(2026-08-12): 단위어 `가지|종류` 인정
(`32\s*(개|개국|가지|종류|[Ll]anguages)`). 한자 가드가 붙으면서 "32**가지**
언어를 지원합니다"라는 정답이 오답으로 세어지고 있었음 — 패턴이 `개|개국`만
허용. 저장된 런 재채점 결과 가드 런만 +1(87 → 88)이고 가드 이전 런은 89 → 89로
불변(그 런은 "가지"를 쓴 적이 없음). 패턴을 넓혀 점수가 오른 것이 아니라
오채점 1건이 고쳐진 것이라는 근거.

네 번째 변경(2026-08-11): 100문항 확장 검수에서 중국어 단위어 1건 허용
(`5\s*[종种]` — "总共比较了5种"이 정답 내용을 담고 있었음). 저장된 두 런
재채점 결과 해당 문항만 뒤집힘. 자세한 경위는 확장 절 참고.

세 번째 변경(2026-08): "한글 데이터 전처리가 더 필요하지 않냐"는 질문을 계기로
코퍼스(NFC 정규화·전각문자·PDF 자소분리)를 전수 스캔했는데 전부 깨끗했음 —

학습 데이터 흔적으로 전각 문장부호(。：)를 섞어 낼 때가 있음(55문항 중 3건).

### 11. 팀 라우팅 — 멀티에이전트는 언제 손해인가 (`eval/ab_team_routing.py`)

`team.py`(Planner→Workers→Synthesizer)를 만든 근거는 "단일 RAG는 멀티홉에
약하다"였는데, 그 주장을 `eval_team.json` 3문항으로 판정하고 있었음.
1문항이 33%p라 어느 쪽이 이겨도 의미가 없음. comparison을 8문항으로
늘린 뒤 세 조건을 같은 채점기로 재측정 (22문항×2회, qwen2.5:14b).

| 조건 | 정답 | 평균 지연 | 델타 |
|---|---:|---:|---:|
| `single` (전부 단일) | 34/44 (77%) | 2.9s | 기준 |
| `routed` (멀티홉만 팀) | **42/44 (95%)** | 3.1s | **+18%p** |
| `all_team` (전부 팀) | 30/44 (68%) | 3.8s | −9%p |

| 유형 | single | routed | all_team |
|---|---:|---:|---:|
| aggregation | 10/12 | 10/12 | **6/12** |
| comparison | 9/16 | **16/16** | 14/16 |
| enumeration | 15/16 | 16/16 | **10/16** |

전부 팀으로 보내면 기준선보다 나쁨. 두 조건(single vs routed)만 쟀다면
"멀티에이전트가 +18%p 좋다"로 끝났을 텐데, 세 번째 조건이 결론을 뒤집음 —
멀티에이전트 자체는 손해이고, 이득은 언제 쓰지 않을지를 아는 데서 나옴.

원인은 일관됨. 분해는 서로 다른 청크의 사실을 엮을 때 이기고, 한 청크에
요약이 이미 있을 때 그 근거를 잃음.

```
"제1저자 논문 편수와 등록 특허 건수 중 더 많은 쪽은 몇 편인가요?"
  단일 2/2 — 요약 청크("논문 7편(제1저자), 특허 2건")를 받아 바로 답
  팀   0/2 — 하위 질문으로 쪼개 목록을 직접 세다가 5편으로 오답
     ↳ 분해: ['제1저자 논문은 몇 편인가?', '등록 특허는 몇 건인가?']
```

이 문항은 "중 더"(comparison)와 "몇 편"(aggregation) 신호를 동시에 가짐.
그래서 `should_use_team()`에 "aggregation 신호가 있으면 팀으로 보내지
않는다"는 가드를 넣었고 routed가 40/44 → 42/44가 됨. 근거가 1문항뿐이라
가설로 표시해 뒀는데, 겹치는 문항을 2개 더 만들자 뒤집힘 (3문항×2회):

| 문항 | 단일 | 팀 |
|---|---:|---:|
| 제1저자 논문 vs 등록 특허 | **2/2** | 0/2 |
| 제1저자 논문 vs 제2저자 논문 | 0/2 | **1/2** |
| 등록 특허 vs 2023년 논문 | 0/2 | **2/2** |
| 합계 | 2/6 | **3/6** |

원래 근거였던 문항만 두 사실이 한 청크에 같이 있었음("논문 7편(제1저자),
특허 2건(제1발명자)"). 나머지 둘은 흩어져 있어 분해가 이김. 즉 진짜 기준은
"집계 신호"가 아니라 "두 사실이 한 청크에 모여 있는가"이고, 그것은 질문
문자열이 아니라 검색 결과의 성질이라 어휘 규칙으로 판정 불가.
**가드는 철회함.**

n=1로 만든 규칙이 n=3에서 무너진 사례. 규칙을 넣을 때 근거의 크기를 코드에
같이 적어두지 않았다면 이 검증을 하지 않았을 것.

가드 철회 후 comparison 10문항 재측정(10문항×2회): 단일 9/20(45%) →
팀 16/20(80%), +35%p. 이 부분집합에서는 routed와 all_team이 정의상
같으므로(전부 comparison), all_team의 손해는 위 22문항 표를 볼 것.

부수적으로 규칙 분류기의 결함도 드러남. comparison이 2문항일 때는
`중\s*(더|먼저|어느|어떤|무엇)`가 2/2를 맞혀 만점이었는데, 8문항으로 늘리자
"중 나중에" 형태 2건을 놓침(비교의 방향이 뒤쪽인 경우). 오탐이 0이므로
리콜만 넓혀 `나중|늦게`를 추가했고, 재검증에서 comparison 8/8·오탐 0.
작은 표본의 만점은 실력이 아니라 표본의 성질이었음.

#### 배선과 3B 재현 — 이번에도 대조군이 결론을 바꿨다

위 측정은 배선 없이 이루어져 있었음. `should_use_team()`을 부르는 건
평가 스크립트뿐이었고 `api.py`·`cli.py`는 단일 그래프로만 감 — 값이
증명된 기능이 제품에 없던 셈. `config.TEAM_ROUTING` + `graph.uses_team()`
으로 연결하고, 응답에 `route`(`"single"`|`"team"`) 필드를 넣어 어느 경로로
답했는지 로그에서 구분되게 함.

기본을 켜기 전에 당시 기본 모델(3b)에서 재측정했고, 켜지 않기로 함.
(그 뒤 기본이 7b로 올라감 — 아래 3b 수치는 그 시점 기록이고, 7b 재측정은
"7b 재측정" 절을 볼 것.)

1차(75문항×2회)는 routed 121/150 vs single 108/150으로 +9%p처럼 보였음.
그런데 `should_use_team()`은 comparison만 팀으로 보내므로 나머지 유형은
single과 완전히 같은 코드 경로 — 그 자리가 대조군이 됨:

| 구분 | single → routed | |
|---|---|---|
| 대조군 (comparison 외 전 유형, 코드 동일) | 100 → 109 | **+9판정 = 노이즈** |
| 전체 | 108 → 121 | +13판정 |
| 변수 (comparison) | 8 → 12 | +4판정 |

헤드라인 +13 중 9가 노이즈. comparison만 격리해 5회로 재측정:

| 조건 | 정답 | 지연 | |
|---|---|---|---|
| single | 20/50 (40%) | 2.9s | 기준 |
| routed | 22/50 (44%) | 3.9s | +2판정 |
| all_team | 20/50 (40%) | 3.8s | routed와 정의상 같은 조건 |

comparison만 돌리면 routed와 all_team은 같은 설정인데 22 vs 20으로 갈림 —
효과(+2)와 노이즈(2)가 같은 크기. 지연은 34% 증가.

문항별 분산이 큼. 팀이 고치는 것도 있고(`등록특허 vs 2023년 논문`
0/5 → 5/5) 부수는 것도 있음(`석사와 학사 중 나중에 취득한 학위` 5/5 → 0/5).
3b는 planner가 하위 질문을 잘 못 쪼개고 synthesizer도 약해서, 분해가
만드는 오류가 분해로 얻는 이득을 상쇄함.

**결론: 멀티에이전트의 값어치는 모델 크기에 의존함.** 14b에서 +18%p는
진짜였지만 3b에서는 0. "멀티에이전트를 붙였다"가 아니라 "언제 값을
하는지 안다"가 이 실험의 산출물이며, 그래서 기본은 꺼 둔 채 손잡이만
유지(`TEAM_ROUTING=1`).

#### 7b 재측정(2026-08-11) — 지도의 가운데 점이 아래로 꺼져 있었다

기본 모델이 7b가 되면서(위 "기본 모델 3B → 7B" 절) 이 손잡이를
재측정함(26문항×2회, comparison·aggregation·enumeration):

| 조건 | 정답 | 평균 지연 |
|---|---:|---:|
| single | 33/52 (63%) | 4.0s |
| routed | 29/52 (56%) | 3.7s |
| all_team | 22/52 (42%) | 4.5s |

**7b에서는 routed가 오히려 −8%p 짐.** routed가 single과 갈리는 건
comparison 10문항뿐인데 거기서 14/20 → 10/20이고, 깨진 3문항이 모두
양쪽 반복에서 재현됨(2/2 → 0/2) — 셋 다 "두 사실이 한 청크에 요약돼
있는" 비교 질문(논문 편수 vs 특허 건수 류)으로, 3b 시절 문서화한 바로 그
실패 패턴. 구제는 1문항.

모델 크기별 지도가 완성됐고, 단조가 아님:

    3b ≈ 0   →   7b −8%p   →   14b +18%p

해석: 3b는 단일도 팀도 약해서 상쇄, 7b는 단일 RAG의 비교 추론이 충분히
좋아져(14/20) 분해의 이득은 줄고 실패 모드(요약 청크 상실)만 남고, 14b는
planner·synthesizer가 그 손해를 뒤집을 만큼 강함. "모델을 키우면
멀티에이전트도 점점 값을 한다"가 아니라 중간 크기에 골짜기가 있다는 것이
이 지도의 내용. 기본은 계속 꺼둠 — 14b를 기본으로 올리는 날 켤 것.

### 12. 손으로 유지하던 목록 셋이 전부 드리프트했다 (캐시 키 버그)

`cache.py`는 독스트링에서 이렇게 선언함 — "캐시 키에 답에 영향을 주는
설정 전부의 지문을 넣어, 설정이 바뀌면 자동으로 다른 키가 되게 한다
(수동 무효화 불필요)". 그런데 구현은 손으로 적은 목록이었고, 환경변수
손잡이 17개 중 10개만 포함돼 있었음.

    빠진 것: HYDE  HYDE_MODE  VERIFY_GROUNDING  TEAM_ROUTING
             EMBED_MODEL  RRF_K  VECTOR_STORE

즉 `HYDE=1`로 API를 띄우면 `HYDE=0` 시절 캐시 답이 그대로 나옴.
캐시 모듈이 막겠다고 선언한 바로 그 사고이며, 이 프로젝트가 가장 경계해온
"지표가 조용히 거짓이 되는" 유형.

같은 병이 둘 더 있었음. `runmeta.py`는 `params`에 5개만 기록해 결과 파일만
보고는 HyDE 실행인지 구분할 수 없었고(실행 지문의 존재 이유가 비교
가능성인데 그것이 반만 됨), `audit_docs.py`는 17개 중 4개만 대조하고 있었음.

셋 다 원인이 같음 — 목록을 손으로 유지한다는 것. `cache.py` 주석에는
"새 손잡이를 추가하면 여기도 같이 추가할 것"이라고 적혀 있었는데, 그 규칙이
이미 두 번 깨진 뒤였음. 규칙을 더 강조하는 대신 목록이 없는 구조로 변경함.

```python
# config.py — 손잡이를 읽는 통로 하나
def _env(name, default, cast=str):
    value = cast(os.environ.get(name, default))
    _KNOBS[name] = value          # 읽는 순간 등록 → knobs()는 항상 완전
    return value

TOP_K = _env("TOP_K", "6", int)   # 17개 전부 이 형태
```

`cache._config_fingerprint()`·`runmeta`의 `params`·`audit_docs`의 대조는
전부 `config.knobs()` 한 줄이 됨. 새 손잡이는 자동 반영되므로 드리프트가
구조적으로 불가능해짐.

`tests/test_knobs.py`가 고정함 — `_env` 우회 금지, 선언과 등록 일치,
손잡이를 하나씩 바꿔가며 캐시 키가 전부 달라지는지(원래 버그의 직접 재현),
실행 지문 누락 없음. 그리고 `audit_docs`를 전수 검사로 바꾸자마자
`EMBED_MODEL`이 README에 없다는 것을 잡아냄.

### 13. 집계 실패의 원인은 산술이 아니라 잘린 표였다 — 절반만 맞았다

남은 실패가 집계·열거에 몰려 있다는 것까지는 위에서 확인했고, 원인을
"3B의 산술·비교 추론 한계"로 적어 뒀음. 결정적 계산 노드를 붙이려고 실제
문항을 열어 보다가 원인이 다른 데 있다는 것을 발견함.

집계 7문항 중 4문항이 `publications.md`의 표를 세야 답이 나옴.

| 질문 | 필요한 계산 |
|---|---|
| 제1저자 논문은 몇 편인가요? | `1저자` 행 세기 (7) |
| 2023년에 게재한 논문은 몇 편인가요? | `2023.` 행 세기 (3) |
| 한국자동차공학회에 게재한 논문은 몇 편인가요? | 게재지명 행 세기 (2) |
| 한국항공우주학회에 게재한 논문은 몇 편인가요? | 게재지명 행 세기 (1) |

그런데 그 표가 청크 3개로 쪼개져 있었음(행 2·2·8개). 표 전체가 있어야
셀 수 있는데 검색은 그중 일부만 가져옴. 모델이 산수를 못 한 것이 아니라
근거가 애초에 잘려 있었던 것. 표가 온전할 때 필터어를 포함한 행을 세면 위
넷을 포함해 5/5가 정답(`2저자` 1편까지 확인).

같은 문제를 이 저장소는 이미 한 번 풀었음 — 다이어그램이 800자 상한에
잘려 박스가 반토막 나던 것을 "문장 단위가 없는 콘텐츠라 문자 기준 분할이
애초에 안 맞는다"며 통짜 청크로 분리함. 표도 정확히 같은 경우라
`extract_diagrams` 옆에 `extract_tables`를 같은 방식으로 추가.

구현하면서 걸린 것 하나 — 표 블록을 `^\|`로 잡으면 안 됨. 셀 안에
줄바꿈이 있으면 이어지는 줄이 들여쓰기된 채 `|`로 시작해서
(`publications.md`의 2021.03·2018.04 행) 한 표가 두 조각으로 끊김. 줄 앞
공백을 허용해야 13줄짜리 표가 온전히 잡힘. 구분선(`| --- |`)이 있는
블록만 표로 보고, 파이프가 우연히 이어지는 본문은 건드리지 않음.

여기까지가 측정 없이 확인한 것. 코퍼스의 표 3개가 전부 통짜로
분리되고(295·415·1,773자), 청크는 58 → 54개가 됨. `gold_anchors` 78개는
전부 생존, md5 gold 라벨은 27개 중 1개가 무효화되므로
`relabel_retrieval.py`로 재부착 필요.

아직 안 잰 것: 이것이 실제로 집계 정답률을 올리는지. 표가 온전해도 검색이
그 청크를 top-N에 올려야 하고, 3B가 표를 보고 실제로 셀 수 있어야 함.
둘 다 실측 대상. 확인 절차:

```bash
python src/ingest.py                                  # 재인제스트 (표 분리 반영)
git show HEAD~1:data/chunks.jsonl > /tmp/old.jsonl
python eval/relabel_retrieval.py --old /tmp/old.jsonl --write
python eval/diagnose.py                               # 표 청크가 검색되는가
python eval/evaluate.py                               # 유형별 정답률 (집계 7문항)
```

집계가 안 오르면 다음 갈래가 갈림 — `diagnose.py`에서 표 청크가 top-N에
안 들어오면 검색 문제이고, 들어오는데도 틀리면 그때야 "3B가 표를 못 센다"가
근거 있는 결론이 됨. 지금까지는 그 구분을 할 수 없었음.

**측정 결과 (2026-08-12 · qwen2.5:7b · 100문항 · 각 조건 2회)**

청킹만 바꾸고 나머지 설정은 그대로 두고 두 조건을 각각 2회 실행함.

| 유형 | base (58청크) | table (54청크) |
|---|---|---|
| **전체** | 83% / 83% | **86% / 86%** |
| aggregation | 8/13 | **8/13** |
| comparison | 10/15 | 12/15 |
| temporal | 10/11 | 11/11 |
| enumeration | 12/13 | 12/13 |
| fact · refusal · trap | 24/26 · 12/12 · 7/10 | 동일 |
| 지연 평균 | 2.0s | 1.9s |

전체 +3%p, 지연 비용 없음 — 채택. 그런데 이 절이 예측한 집계는 한 칸도
움직이지 않았음. 표 안에서 구제와 악화가 정확히 상쇄됨. 네 문항 전부 두
런에서 같은 방향으로 재현.

- **구제** 한국자동차공학회 3편 → 2편(정답). 예측이 맞은 유일한 케이스.
- **악화** 2023년 논문 3편(정답) → 2편. 표 청크가 top-N에 들어왔는데도 틀림.
- **악화** 국제 학술대회 논문. 내용은 맞는데 `论文有1篇`처럼 중국어로 써서
  채점에서 탈락 — 계산 실패가 아님.
- **악화(enumeration)** "근무한 회사들". 통짜 표 3개가 top-6 슬롯을 밀어내
  근거 청크가 아예 안 들어옴. 통짜 청크가 무료가 아니라는 첫 실측.

§14 ①이 갈래로 적어 둔 두 결론 중 후자로 확정됨 — 근거가 잘려서가 아니라
모델이 온전한 표를 보고도 못 셈. 남은 집계 실패 3건이 전부 산술(2023년
3→2, 2022년 1→2, 제1저자 논문+특허 9→10). "3B의 산술 한계"라던 옛 설명도
같이 틀림 — 7B에서 그대로 재현됨. 세는 일을 결정적 코드로 옮길 근거는
이제 확보됨.

부수 관측 — 7b는 이 조건에서 사실상 결정론적. 100문항 답변이 두 런에서
98개(table)·92개(base) 글자까지 동일함. 이 저장소가 "편차 ±6%p 안이라
채택 불가"로 미뤄 둔 판정들(CONTEXT_ORDER=sandwich, targeted 프롬프트,
NEIGHBOR_WINDOW 유형 라우팅)은 전부 3b·CPU 시절 기준이므로 다시 잴 값이 있음.

측정 전에 걸린 것 하나 — 이 저장소의 `data/chunks.jsonl`은 표 분리 이전
산출물(58청크)이었음. 코드에는 `extract_tables`가 있는데 인덱스는 옛 것이라,
그 사이에 낸 7b 측정은 전부 옛 청킹에서 나온 숫자. `index_manifest.json`은
인덱스↔chunks 일치만 보고 코드↔chunks는 안 봄. 해당 커밋에 재인제스트
산출물을 함께 포함함.

응답의 `timings`로 노드별 배분도 함께 확인 가능.

#### 측정 결과를 남길 때

`results*.json`에는 `runmeta`가 모델·Ollama 버전·인덱스 해시·손잡이 전부·
하드웨어를 함께 기록함(개수를 적지 않는 이유는 `config.knobs()`가 자동으로
따라오기 때문 — §12). 이 저장소는 예전에 "README 90% vs 재측정 74%"가 비교
가능한지 판단할 근거가 없었던 적이 있음(§12) — 지금은 파일만 봐도 갈림.
측정 환경이 다르면 지연 수치는 나란히 놓지 말 것.

### 15. 답변의 10%가 중국어로 새고 있었다

표 청킹 측정(§13)의 부산물로 발견함. 집계 실패 하나를 열어 보니 내용은
맞는데 채점에서 떨어져 있었음 — `国际学術大会上发表的论文有1篇`.

100문항을 전수 조사하니 답변 10개에 한자가 섞여 있었고, 그중 3개는 숫자를
중국어로 써서 틀린 것(`共有2项` / `论文有1篇` / `共计1年1个月`). 채점기
결함이 아니라 제품 결함 — 한국어 포트폴리오 안내가 중국어로 답하고 있던 것.

이탈 방식이 일정함. 한글 단어를 쓰다가 한자 한 글자가 나오고(`특許`,
`언语`) 거기서부터 문장 전체가 중국어로 넘어감. 코퍼스는 결백함 — 54청크
중 한자가 있는 것은 `resume.md`의 `古語` 하나뿐.

프롬프트에는 이미 "한국어로 답하세요"가 있었음. 문장 단위 지시로는 글자
단위 이탈을 못 막음. 실패 문항 5개로 수단을 먼저 가름:

| 수단 | 결과 |
|---|---|
| 현재(t0.0) | 한자 3/5 |
| 같은 온도로 재생성 + 교정 지시 | 그대로 이탈 — 무의미 |
| 온도만 0.5 / 0.8로 | 여전히 4/5 재발 |
| **"한자를 쓰지 말고 한글과 숫자로만"** | **5/5 깨끗** |

`temperature=0.0`이라 재생성이 같은 자리에서 똑같이 이탈한다는 것이 핵심.
가드를 먼저 짰다면 통하지 않았을 것 — 5분짜리 비교가 설계를 바꿈.

#### 100문항 실측 (7b, 각 조건 2회)

| | 표 청킹 | +한자 금지 한 줄 | +가드(최종) |
|---|---|---|---|
| 전체 | 86 / 86 | 89 / 89 | 88 / 86 |
| 한자 섞인 답변 | 10 | 6 | **0 / 0** |
| comparison | 12/15 | 14/15 | 14/15 |
| trap | 7/10 | 8/10 | 8/10 |
| 지연 | 1.8~2.1s | 1.6s | 1.6s |

한 줄로 +3%p. 대가도 있었음 — 영어 OPIc 문항은 답이 짧아지면서 원문 인용
(`OPIc IM1`)이 빠져 채점 기준을 놓침(내용 "중급"은 맞음). 프롬프트를 늘리면
어딘가가 짧아진다는 targeted 변형(§9)의 교훈이 같은 형태로 반복됨.
6:1로 순증이라 채택.

#### 재생성은 어떤 온도로도 안 됐다

남은 6건은 전부 채점을 통과함 — 정확도로는 안 보이는 결함이라 가드를 추가함.
처음 설계는 "한자가 보이면 다시 생성"이었고, 온도 0.5 한 번으로 6 → 2,
0.5·0.8 두 번으로 0~3(실행마다 다름)까지 감. 재생성이 샘플링이라 평가 자체가
흔들리기 시작함.

가장 질긴 문항을 5회씩 다시 재보니 재생성이라는 방향 자체가 틀렸음.

| 수단 | "몇 개 언어" 문항 |
|---|---|
| 문맥 재생성 t0.5 | 깨끗 0/5 |
| 문맥 재생성 t1.0 | 깨끗 0/5 |
| **답변을 넣고 고쳐쓰기 t0.0** | **깨끗 3/3** |

같은 문맥·같은 질문이면 매번 같은 자리(`32개 언` 다음)로 되돌아옴. 이탈은
샘플링 운이 아니라 그 문맥에서 그 토큰으로 가는 경로이고, 온도를 올리는
것은 그 경로를 흔들 뿐 없애지 못함. 입력을 망가진 답변으로 바꾸면 경로
자체가 사라짐. 온도 0이라 결정론도 돌아옴.

#### 교정 출력도 이탈한다 — 결정적인 겹이 하나 필요하다

고쳐쓰기로 한자 답변이 1~2건까지 줄었지만 0이 되지 않음. 남은 것을 열어
보니 교정 호출이 같은 자리에서 또 넘어감(`데이터를清理和预处理…`).
LLM을 거치는 수단은 전부 같은 벽에 부딪힘.

그래서 LLM 없는 겹을 제작 — 중국어로 넘어간 문장만 버리고 한국어 문장을
남김. 문장 하나에 한자가 3자 이상이면 이탈로 판정(이탈은 문장을 통째로
중국어로 쓰므로 수십 자가 나오고, 코퍼스의 정당한 인용 `古語`는 두 자).

#### 순서가 결과를 바꿨다

처음엔 교정을 먼저, 문장 필터를 폴백으로 배치. 그 배치에서 TTFB 문항이
`2292ms → 334ms`를 잃고 "대략 85% 단축"만 남음 — 교정이 답을 요약하면서
숫자를 흘린 것. 같은 답변을 문장 필터에 넣으면 이탈 문장만 빠지고 숫자가
그대로 남음.

**결정적이고 무손실인 겹이 먼저.**

    한자 없음                        → 그대로
    문장 필터로 건질 한국어 문장 있음 → 그것 (LLM 호출 없음)
    첫 문장 중간에서 샌 경우          → 고쳐쓰기
    고쳐쓰기도 이탈                  → 그 출력에 다시 필터, 그래도 없으면 원본

순서를 뒤집자 6건 중 3건이 LLM 호출 없이 끝나고(지연 1.7 → 1.6s), 잃었던
숫자가 돌아옴. 같은 두 함수인데 배치만 바꾼 결과.

#### 값: 1~3%p, 그리고 그중 하나는 채점기였다

공짜가 아님. 89% → 88·86%로 하락. 내려간 문항들의 성격이 다름.

| 문항 | 무슨 일 |
|---|---|
| 몇 개 언어 | 가드 후 "32**가지** 언어" — 정답인데 패턴이 `개\|개국`만 허용. 채점기 결함이라 수정(§10 다섯 번째 변경) |
| TTFB | 교정이 숫자를 흘림 → 순서를 바꿔 회수 |
| 손실 함수 조합 | 개수(5)를 중국어 문장만 들고 있었음. 한국어 답변은 5개를 나열해 놓고 "4가지"라고 셈 |

셋 중 둘은 수정했고, 남은 하나는 원래부터 한국어 답변이 틀렸다는 사실이
드러난 것. 이 실험의 결론이 거기에 있음 — 중국어 이탈이 한국어 쪽 실패를
가리고 있었음. 같은 뿌리를 §13에서도 확인(표가 온전해도 못 셈).

포트폴리오 데모라서 "한국어 안내가 중국어로 답한다"가 채점 지표 1~2%p보다
먼저 보이는 결함이라 판단해 가드를 켬. 되돌리려면 `_drop_hanja` 호출 한
줄만 제거하면 됨.

### 16. 인덱싱·검색 재점검 — 통짜 청크가 문서 위치를 잃고 있었다

표 통짜 청킹(§13)을 넣고 나서 인제스트와 검색을 처음부터 다시 읽음. 셋이 나옴.

#### ① 통짜 청크가 리스트 끝에 몰려 있었다

`extract_tables`는 본문에 `[표: 1]` 플레이스홀더를 남기고, 통짜 청크는 `main()`에서
리스트 **끝에** 이어붙이고 있었음. 그래서 `chunk_index`·`doc_index`가 문서 내 실제
위치와 달랐음.

    #48 patents.md       table
    #49~51 portfolio.md  diagram ×3
    #52 portfolio.md     table
    #53 publications.md  table

메타데이터가 거짓말을 하는 것 자체도 문제지만(정밀 인용의 근거), 이웃 확장이
`chunk_index ± w`를 같은 source 안에서 찾기 때문에 **본문에서 표로 도달할 수 없음.**
하필 TYPE_ROUTING이 이웃 확장을 켜는 유형이 aggregation·enumeration. 플레이스홀더가
있는 청크 바로 뒤에 실물을 끼우도록 고침(`place_whole_chunks`).

**기대했던 집계 개선은 없었음.** 이유가 분명 — publications.md와 patents.md는
본문이 각각 30자·14자(제목 + 플레이스홀더)라 `MIN_CHUNK_CHARS`에 걸려 사라짐. 붙일
자리가 없으니 두 표는 여전히 고아로 끝에 남음. 순서가 바뀐 것은 portfolio.md의
다이어그램 3개와 표 1개뿐.

#### ② 그 순간 이웃 확장이 다이어그램을 빨아들이기 시작했다

`expand_with_neighbors`는 통짜 청크를 **확장 출발점**에서만 제외하고, 이웃으로 딸려
들어오는 것은 막지 않았음. 통짜 청크가 끝에 몰려 있을 때는 우연히 문제가 안 됐음.
문서 위치에 맞게 놓자마자 물림:

| | 컨텍스트 | 결과 |
|---|---|---|
| 순서 고정 전 | 5,871자 | 정답 |
| 순서 고정 후 | **10,182자** | 오답 (두 실행 모두) |
| 이웃 유입 차단 후 | 5,102자 | 정답 (두 실행 모두) |

"재직한 회사 네 곳" 문항. 최대 5,079자짜리 다이어그램이 옆 청크에 통째로 붙음.
조건 하나(`not n.metadata.get("kind")`)로 막았고, 이 계약을 테스트로 잠금.
**고친 것이 다른 것을 깨는 전형**이라 두 변경을 한 커밋에 묶음.

100문항 × 2회: 순서 고정 전 88·86% → 고정 후 87·87%(enumeration 12 → 11) → 이웃
차단 후 **88·87%**(enumeration 12 회복). 정확도는 결국 제자리. 이 변경의 값은
정확도가 아니라 **메타데이터가 문서 위치를 정직하게 가리키게 된 것**.

#### ③ 코드↔산출물 드리프트를 아무도 안 보고 있었다

오늘 실제로 물린 문제. 매니페스트는 `chunks.jsonl ↔ 지문`만 대조하고, **커밋된
`chunks.jsonl`이 현재 인제스트 코드의 산출물인지는 아무도 안 봄.** 표 통짜 청킹이
코드에 들어간 뒤에도 저장소의 청크는 표 분리 이전(58청크)인 채였고, 그 사이 낸 7b
측정이 전부 옛 청킹 숫자였음.

재계산 비용을 재보니 2.6초(임베딩 불필요, 청킹만). CI에서 돌 수 있는 비용이라
테스트로 넣음 — 커밋된 docs로 청킹을 다시 돌려 `chunks.jsonl`과 글자까지 비교함.
넣자마자 빨간불이 떴고(위 ① 순서 변경분), 재인제스트로 해소됨.

검색 쪽은 다시 읽어도 별도로 고칠 것이 없었음 — RRF 중복 판별(내용 md5 + 상위 랭크
출처 유지), 질의 시점 `bm25.k` 설정, 두 인덱스가 모두 준비된 뒤 전역 공개하는 지연
초기화, HyDE의 목록 대체 아닌 추가, `search(kind=...)`가 전역을 안 읽는 것까지 전부
이유가 주석에 남아 있고 의도대로 동작함.

### 17. 세는 일을 코드로 옮기려 했다 — 두 번 실패 (미채택)

§13에서 집계 실패의 원인이 검색도 청킹도 아닌 **세기**로 확정됨. 표가 top-N에 온전히
들어와 있는데 7B가 2023년 논문 3편을 2편으로, 제1저자 7편 + 특허 2건을 10개로 셈.
모델을 키워 풀 문제가 아니므로(3B·7B 동일) 결정적 코드로 옮기는 것이 다음
수순이었음.

**설계** — 답을 대신 쓰지 않음. `retrieve` 뒤에 `tally` 노드를 두고, 검색된 표의
행을 코드가 세어 **사실 몇 줄만** 컨텍스트 끝에 얹음. 문장으로 만드는 것은 모델이
함. 세는 질문(`몇`·`개수`·`합치면`)일 때만 붙이고, 질문의 단어가 걸린 표만
적음(route.py와 같은 원칙 — 탐지는 결정적으로, 정밀도 우선).

**드라이런에서 숫자는 전부 맞음.**

| 질문 | 집계 결과 | 정답 |
|---|---|---|
| 2023년 논문 | publications 3행 | 3 |
| 2022년 논문 | 1행 | 1 |
| 한국자동차공학회 | 2행 | 2 |
| 제1저자 논문 | `'1저자' 7행` | 7 |
| 등록 특허 | patents 데이터 2행 | 2 |

(`제1저자`는 표에 `1저자`로 적혀 있어 서수 표기를 같이 봄. 조사도 뗌.)

#### 그런데 100문항 실측은 두 번 다 손해였다

| | 전체 | aggregation | trap |
|---|---|---|---|
| 집계 노드 없음 | **88 / 87** | 7·6/13 | **8·8**/10 |
| 1차 (기계 표기 `[표 집계] '1저자' 포함 7행`) | 86 / 86 | 5·6/13 | 7·7/10 |
| 2차 (문장 + "이 숫자를 그대로 쓸 것") | 85 / 86 | 6·7/13 | **6·6**/10 |

**목표였던 집계는 안 오르고, trap이 지시 강도에 비례해 단조 감소**(8 → 7 → 6).

1차에서는 모델이 주입된 줄을 **아예 안 씀**.
숫자가 다 맞는데도 제1저자 7행 → "2편", 제2저자 1행 → "7편"으로 답변함.
기계 로그 형태가 "몇 편"의 답으로 안 읽힌 것으로 보임.

2차에서 문장으로 바꾸고 쓰라는 지시를 붙이자 이번엔 **엉뚱한 숫자를 확신 있게** 집음.
결정적인 것은 이 답변:

    질문: 동시 처리 채널은 확장하기 전에 몇 개였나요?  (trap)
    전: "확장하기 전에 동시 처리 채널은 12개였습니다"  → 정답
    후: "12"                                        → 오답 처리

내용은 맞는데 **맨 숫자로 퇴화**해 단위를 요구하는 채점을 못 넘김.
"이 숫자를 그대로 쓸 것"이 문장까지 지워버린 것.
프롬프트를 늘리면 어딘가가 짧아진다는 §9·§15의 교훈이 세 번째로 같은 모양으로 나옴.

**배운 것: 근거를 정확히 주입하는 것과 모델이 그것을 쓰는 것은 다른 문제.** 이
프로젝트에서 "검색이 근거를 못 준다"는 실패는 여러 번 고쳤지만, 이번은 근거가 100%
정확하게 들어갔는데도 실패함. 결정적 계산을 붙이는 것만으로는 안 되고, 모델이 그
사실을 답으로 옮기는 경로까지 설계해야 함.

#### 되돌리면서 남기는 것

코드는 되돌림(`tally` 노드·상태 키·주입 로직 전부).
측정 결과 파일 4개는 남김 — 다시 시도할 때 같은 자리를 두 번 파지 않기 위해서.

시도해 볼 만한 것으로 남은 것:

- **문장 형태 + 지시 없음** (1차와 2차 사이). 1차의 "안 읽힘"과 2차의 "맨숫자 퇴화"

- **집계 질문만 코드가 직접 답변 문장을 작성.** RAG가 아니라 규칙 기반 QA로 넘어가는
  것이라, 채택하려면 유형 분류의 오탐 대가를 먼저 재야 함.

#### 곁가지로 확인한 표 양식의 한계

`행 = 항목` 가정은 단순한 표에서만 성립함. 실제로 만들어 확인함.

| 양식 | 통짜 청크 | 행 세기 |
|---|---|---|
| 단층 머리글·한 줄 행 (현 코퍼스) | O | O |
| 다층 머리글(2줄) | O | X — 첫 행만 버려 데이터가 1행 많아진다 |
| 병합 셀(빈 칸으로 표현) | O | X — 이어짐 행을 별개 항목으로 센다 |
| 셀 안 줄바꿈 | O | 줄 단위라 불안정 |
| HTML 표(`<table>`) | X | X — 태그째 본문에 남고 표로 인식되지 않는다 |

앞의 셋은 고칠 수 있음(구분선 위치로 머리글을 가르고, 첫 셀이 빈 행은 이어짐으로
봄). 그러나 **병합 여부는 마크다운에 정보가 없음**(노션·워드가 내보낼 때 빈 셀로
펴버리기 때문). 정확히 하려면 `.docx`/`.hwpx` 로더가 `gridSpan`·`vMerge`를 읽어야
함. 위 실측이 "그 작업을 지금 할 이유가 없다"고 말해 주므로(세기를 고쳐도 모델이 안
씀) 함께 보류함.

|---|---|

새 문서에 대한 질문을 기존 문항보다 **더 잘 답함.** 82%는 확장의 대가만 보여주는

문항을 만드는 과정 자체가 두 가지를 잡음.

- **내 문항이 틀리고 모델이 맞은 경우 1건.** "TTS 캐시의 기본 TTL"을 1시간으로 두고
  채점했는데 모델이 24시간이라 답변함. 확인해 보니 **문서끼리 값이 다름** —
  `기능_명세.md`는 "기본 TTL 1시간", `DB_ERD.md`·`데이터_정의서.md`는
  `tts:audio:<sha1>`을 "24h"로 적음. 모델은 더 구체적인 근거를 고름. 질문을 모호하지
  않은 사실로 교체했고(IP별 요청 카운터 60분), **문서 간 모순은 코퍼스 쪽에서 정리할
  일**로 남음. RAG 평가셋을 만들다 원본 문서의 불일치를 찾은 셈.
- **남은 실패 1건은 진짜 실패.** "WebSocket heartbeat는 몇 초마다 오나요"의
  근거("30초마다 서버가")가 코퍼스에 있는데 거부함. 위 기전 ①(밀려남)의 재현 가능한
  사례라 고치지 않고 남김.

#### 2차 배치 — 13문항은 너무 적었다 (113 → 140문항)

13문항은 밀도로 보면 100배 부족함. 포트폴리오는 54청크에 100문항인데 TTS는
**788청크에 13문항**이고, 무엇보다 **`comparison`·`trap`이 0개**였음 — 코퍼스
확장으로 가장 나빠진 유형이 정확히 그 둘인데(11/15, 6/10) 새 문항은 그 실패를 볼 수
없었음. 27문항을 더해 문항 0개였던 문서 5개를 채우고 두 유형을 넣음.

| | 점수 |
|---|---|
| 포트폴리오 100문항 | 82% |
| TTS 1차 13문항 | 92% |
| **TTS 2차 27문항** | **81%** (trap 3/3 · comparison 2/3) |
| 전체 140문항 | **82.9%** |

2차가 더 어려웠고, 실패 5건이 전부 다른 종류였음.

- **인접한 파라미터를 맞바꿈.** 문서의 한 줄이
  `상담원 30명 · 문장 20~40개/agent · Poisson 3s · warmup 5분`인데, Poisson을 "5s",
  warmup을 "3분"이라 답변함. **두 문항이 동시에 틀림** — 우연이 아니라 나열된 값이
  붙어 있으면 교차한다는 신호.
- **열거를 일반 상식으로 채움.** 전송 방식 3종(`Batch·Stream·WebSocket`)을
  `WebSocket·HTTP POST·HTTP GET`이라 답변함.
- **비교의 방향이 뒤집힘.** 앞(200ms)·뒤(250ms) 중 긴 쪽을 물었는데 "앞쪽이 더 길며 200ms".
- **한자 가드의 사각지대.** `M1~M5共计5种` — 답변이 한 문장뿐이라 문장 필터가
  그것을 버리면 남는 게 없어 원본을 유지함(§15의 마지막 겹이 짧은 답변에서는
  작동하지 못함).

`trap`은 3/3으로 예상 밖에 좋았음 — "단축 500→200"에서 **단축 전 값**을 정확히
고름. 포트폴리오 쪽 trap이 6/10인 것과 대비되는데, 새 문항의 함정이 "강조된 값 옆에
나란히 적힌 옛 값"이라 근거가 한 청크 안에 있기 때문으로 보임.

#### 실패 5건을 문항 잘못 / 설계 문제로 갈랐다

| 실패 | 판정 | 조치 |
|---|---|---|
| Poisson 3s · warmup 5분 | **문항 잘못** — 문서에 실측이 1·2차 두 번 있고 파라미터가 다르다(1차 `Poisson 3s·warmup 5분` / 2차 `5s·3분`). 모델은 2차 값을 **일관되게** 답했다 | 문항에 "1차" 명시 |
| 전송 방식 3종 | **검색 실패** — 근거 청크가 컨텍스트에 아예 없다(`Batch`·`Stream` 부재). 질문은 "전송 방식", 문서는 `Batch/Stream/WS` — 어휘 격차 | HyDE 재측정(아래) |
| 앞/뒤 무음 패딩 비교 | **생성 실패** — 두 값이 **모두 컨텍스트에 있는데** 방향을 뒤집었다 | 손잡이 없음, 한계로 기록 |
| `M1~M5共计5种` | **가드 한계** — 교정이 한국어 부분만 고치고 중국어 단위 표현은 그대로 둔다(t0.0·0.5·0.8 동일) | 재시도 무용을 실측하고 되돌림 |

문항을 고치자 하나는 통과했고(warmup), 다른 하나는 **더 선명한 결함**이 드러남:

    "1초입니다. 문서에서 '… Poisson 3s' 부분을 보면, 이는 1차 실측의 …"

`3s`를 정확히 인용해 놓고 "1초"라고 답변함. 모호함이 걷히자 남은 것이 **근거를 옳게
집고 값을 틀리는** 실패였음 — CER 사례(정답을 인용하며 거부)와 같은 가족.

#### "코퍼스가 커지면 살아날 것"이라던 손잡이 셋이 모두 기각됐다

| 손잡이 | 54청크 시절 판정 | 842청크 재측정 |
|---|---|---|
| `TOP_K` | "돌릴 대상이 없는 손잡이" | 6이 여전히 최적, 30에서 recall@5 81%로 **손해** |
| `GENERATE_TOP_N` | 5 최적 | 5 유지(200판정 73/**79**/77) |
| `HyDE` | "고칠 게 없어서 미채택" | satisfied@6 90% → 88%(full) / 86%(terms), **지연 6.6배** |

어휘 격차라는 표적이 실제로 생겼는데도 HyDE는 여전히 손해. **54청크에서 정한 값이
842청크에서 하나도 움직이지 않음** — "코퍼스가 작아서 기각했다"는 유보를 처음으로
시험한 결과.

**최종 140문항 84.3%** (포트폴리오 100문항 83% · TTS 40문항 88%).



**이 지표는 아직 손해만 재고 이득은 못 재는 상태.** 평가셋 100문항이 전부 포트폴리오
질문이고 새로 넣은 TTS 문서에 대한 문항은 0개. 어시스턴트가 실제로 얻은 능력(TTS
시스템의 구조·API·성능을 답하는 것)이 측정에 안 잡힘. 다음 순서는 그 문항을 만드는
것 — 이 저장소가 "문서를 늘리면 문항도 같이 늘려야 한다"고 적어 둔 그 자리에
처음으로 실제 사례가 생김.

### 19. 라벨 감사의 경고 11건 — 5건은 무해, 1건은 진짜, 5건은 낡은 파일

코퍼스를 15.6배로 늘린 뒤 `audit_coverage.py` 가 경고 11건을 내고 있었음.
"코퍼스 확장 뒤처리"로 뭉뚱그려 라벨을 손보려다, 경고 하나하나가 같은 종류인지
먼저 갈랐음. 셋 다 다른 이야기였음.

**과잉 앵커 6건 — 판정선이 개수가 아니었다.** 감사는 "앵커 하나가 6청크 넘게
걸리면 질문을 변별하지 못한다"고 경고했는데, 정작 이 문서가 gold 를 정의하며
적어 둔 원칙은 정반대임 — "같은 사실이 여러 곳에 있으면 전부 gold", "흔한
문자열이 청크 10개에 걸려도 벌점이 아니다". 문서 코퍼스는 같은 사실을 여러
문서에 적으므로 넓게 걸리는 것 자체는 정상임.

그래서 개수 대신 **걸린 청크가 실제로 답을 담는가**로 다시 쟀음(채점에 쓰는
`answer_patterns` 를 그대로 적용하면 기계적으로 갈림):

| 앵커 | 걸린 청크 | 정답 패턴 포함 | 판정 |
|---|---:|---:|---|
| `password_changed_at` | 13 | 13 | 무해 |
| `31개 언어` (2문항) | 8 | 8 | 무해 |
| `tinyld` | 8 | 8 | 무해 |
| `POST /v1/tts/synthesize` | 7 | 7 | 무해 |
| **`vLLM-Omni`** | **12** | **5** | **결함 — 7청크가 답이 안 됨** |

5건은 코퍼스의 성질이고, 진짜 결함은 1건이었음. "TTS 추론 엔진은 어떤 모델을
사용하나요?"의 앵커가 `vLLM-Omni`(서빙 스택)였는데, 그 이름만 적힌 7청크는
모델명을 안 담아 회수해도 답이 안 됨. 개수를 세는 규칙은 이 1건을 나머지
5건의 잡음에 묻고 있었음 — **경고가 많아서 못 본 게 아니라, 경고의 기준이
결함과 무관해서 못 본 것.**

고치면서 보니 이 라벨은 **양방향으로 동시에 틀려** 있었음. 경로가
`vLLM-Omni` 또는 `Qwen3-TTS-1.7B` 였는데, 앞은 답이 아닌 청크를 근거로
세고(느슨), 뒤는 `-1.7B` 접미사를 요구해 모델명만 적힌 청크를 근거에서
빼고 있었음(빡빡 — 실제로 이번 검색 결과의 2청크가 그 경우). 두 경로를
`Qwen3-TTS` 하나로 합쳐 둘 다 해소했음. 이 문항은 전후 모두 충족이라
**지표 수치는 안 바뀜** — 걷어낸 것은 잠복 결함이지 점수가 아님.

감사도 같이 고쳤음. 개수 경고를 **겉핥기 청크(정답 패턴이 없는 청크)가
있을 때만** 울리도록 바꿨고, 집계·비교처럼 정답이 원문에 없어 이 검사를
적용할 수 없는 유형은 그 사실을 밝혀 알림. 늘 울리는 경고는 사람이 무시하게
되므로, 경고를 줄이는 게 아니라 **울릴 자격을 주는 것**이 목적임.

**라벨 누락 4건 + 근거 없이 맞음 1건 — 낡은 파일에서 나온 경고였다.**
이 교차검증은 `results_coverage.json`(커버리지)과 `results.json`(답변 평가)을
나란히 놓고 "PASS 인데 커버리지 MISS"를 찾는데, 두 파일의 출처를 대조하지
않고 있었음. 확인해 보니 `results.json` 은 **58청크 시절 100문항 실행분**
(`index_chunks_md5` 9f76f7a2)이고 커버리지는 842청크·125문항이었음. 서로 다른
코퍼스의 두 실행을 비교해 낸 경고라, 그대로 믿고 라벨에 경로를 추가했으면
멀쩡한 라벨을 망칠 뻔했음.

인덱스↔`chunks.jsonl` 결속(`check_index_consistency`)과 같은 방식으로 막았음 —
`results.json` 의 인덱스 지문이 현재와 다르면 교차검증을 건너뛰고 왜 건너뛰는지
출력함. 이 저장소가 이미 세 번(캐시 키·실행 지문·코드↔산출물) 겪은 드리프트가
네 번째로 나온 자리이고, 매번 해법은 같았음 — **비교하기 전에 두 쪽이 같은
조건에서 나왔는지 기계가 확인하게 만드는 것.**

결과는 WARN 11 → 0건. 다만 0이 된 이유가 셋으로 다름을 기록해 둠: 5건은
경고 기준을 고쳐서, 1건은 라벨을 고쳐서, 5건은 애초에 비교하면 안 되는
것이라 아예 재지 않게 되어서. 마지막 5건은 사라진 게 아니라 **보류**이며,
현재 인덱스에서 `evaluate.py` 를 다시 돌리면 그때 진짜 판정이 나옴.

#### 보류를 닫았다 — 진짜 라벨 누락은 4건, 그리고 문항이 달랐다

현재 인덱스로 140문항을 다시 재고(79%, 111/140 · 재작성률 14%) 교차검증을
살렸음. 나온 경고는 4건인데 **낡은 파일이 만들던 5건과 겹치는 것이 1건뿐**임 —
가드가 옳았다는 직접 증거이고, 낡은 비교를 믿었으면 엉뚱한 문항 4개의 라벨을
건드릴 뻔했음.

4건 전부 원인이 같았음. 같은 사실을 코퍼스가 **다른 표기로도** 적어 두는데
라벨이 한 표기만 들고 있던 것:

| 문항 | 라벨이 아는 표기 | 코퍼스의 다른 표기 |
|---|---|---|
| 대시보드 프론트 스택 | `React 18, TypeScript` | `React 18 · TypeScript` |
| IP 카운터 TTL | `Redis TTL 60분 자동 삭제` | 표의 `60분 창` |
| 부하 테스트 상담원 수 | `--agents 30` (CLI) | `상담원 30명` (보고서) |
| 캐시 히트 TTFB | `히트 시 TTFB <50ms` | `50ms 미만` |

대안 경로를 추가하니 커버리지가 **satisfied@6 90 → 93%, @5 86 → 89%,
@3 76 → 79%** 로 올랐음. 라벨 누락은 지표를 **낮게** 만든다는 이 문서의
오래된 관찰(gold 선정 기준 절)이 3%p 규모로 재현된 것 — 검색기는 이미 근거를
회수하고 있었는데 라벨이 그 경로를 몰라 실패로 세고 있었음.

곁가지로 채점 패턴의 오답 통과 경로도 5건 나와 막았음(§10 여섯 번째 변경).
`50\s*ms` 가 "250ms"에도 걸리는 유형인데, 라벨 작업 중 근거 청크를 하나씩
열어 보다 발견함 — **경고를 따라가면 경고가 가리키지 않은 것도 같이 나온다.**

## Graph RAG 실험 1 — 원 코퍼스 (미채택, 원인: 코퍼스가 작다)

채용 공고 조사에서 Graph RAG가 반복적으로 요구 기술로 등장함. 이 코퍼스는
"이윤선-근무-회사", "프로젝트-사용-기술" 같은 개체 중심 관계가 많고,
enumeration(열거)·comparison(비교)형 질문 — "근무한 회사들을 알려주세요",
"인피닉과 이든티앤에스 중 더 오래 근무한 곳은" — 은 사실이 여러 청크에
흩어져 있어 하이브리드 검색(청크 단위)이 불리할 수 있다는 것이 가설.

**구현**: `kg.py`가 LLM(`with_structured_output`, grade·rerank와 같은 패턴)로
청크마다 (주어, 관계, 목적어) 트리플을 뽑아 `networkx` 그래프로 구축.
검색은 질의 토큰과 겹치는 노드를 시드로 잡고(`bm25_tokenize` 재사용 —
LLM 없이 결정적으로, eval_retrieval.py와 같은 원칙) 1-hop 이웃 엣지의 출처
청크를 점수순으로 반환. `fused_search`는 이 결과를 하이브리드와
RRF(K=60)로 융합 — `graph.hybrid_search`가 이미 쓰는 방식 그대로.

인제스트(`python src/ingest_kg.py`, qwen2.5:3b): 산문 청크 48개 전부에서
트리플 추출 성공(실패 0%) — 노드 328개, 엣지 271개.

**결과** (`eval/eval_kg_retrieval.py`, retrieval_set.json 10문항):

| 방식 | recall@1 | recall@3 | recall@6 | MRR |
|---|---|---|---|---|
| hybrid (기존) | 90% | 100% | 100% | 0.95 |
| kg 단독 | 10% | 40% | 40% | 0.217 |
| hybrid+kg RRF 융합 | 80% | 100% | 100% | 0.90 |

**판정: 미채택.** 그래프 단독은 하이브리드에 크게 못 미치고, 융합은 오히려
recall@1·MRR을 깎음(90%→80%, 0.95→0.90) — 노이즈 있는 그래프 신호가
RRF에서 정답 순위를 밀어내는 쪽으로 작용함.

원인을 질문별로 분해하면(시드 노드 직접 출력):

- **시드가 아예 안 잡히는 질문 3건** — "특허 번호", "Kubernetes CI/CD 도구",
  "웹소켓 세션 탈취". 그래프에 `특허`·`Kubernetes`·`웹소켓` 같은 노드가 없거나
  질의 표현과 다른 명칭으로 추출됨 — LLM이 트리플을 만들 때 문서마다
  엔티티 명칭을 다르게 부른 것으로 보임(예: "웹소켓 세션"이 아니라 특정
  공격 기법명으로 추출).
- **일반 동사가 유사 엔티티로 새어 들어간 경우** — "팝 노이즈를 어떻게
  해결했나요" 질의가 노드 `해결`을 시드로 잡음. 관계여야 할 서술어가
  트리플 추출 과정에서 주어/목적어 자리에 들어간 것 — 프롬프트에 "관계는
  동사, 주어/목적어는 명사 개체"라고 더 명시했어야 했던 부분.
- **부분적으로만 맞는 경우** — "이윤선의 제1저자 논문"에서 `1`이라는
  숫자 하나가 노드로 분리 추출됨(원인 미상, 트리플 추출 프롬프트가
  숫자를 개체로 오인). "TTS 프로젝트"와 "프로젝트"가 별도 노드로 남아
  마땅히 하나여야 할 개체가 갈라짐 — `normalize()`가 공백·대소문자만
  다루고 부분 문자열 병합은 하지 않기 때문.

**결론**: 51개 문서·48개 청크 규모의 코퍼스에서는 하이브리드 검색이 이미
recall@1 90%로 천장에 가깝고 개선 여지가 적음. Graph RAG가 값을 하려면
(1) 엔티티 정규화를 LLM 추출 직후 한 번 더(동의어 병합·비개체 필터링)
거치거나, (2) 지금보다 더 크고 관계가 조밀한 코퍼스에서 재보는 것이 다음
단계 — 이 코퍼스는 Graph RAG의 강점(개체 간 다단 추론)이 발휘되기엔
너무 작고 청크당 정보 밀도가 이미 높음. parent-child·시맨틱 청킹과 같은
결론: 새 검색 방식보다, generate가 이미 받은 근거를 얼마나 잘 쓰는지가
이 프로젝트 규모에서는 더 큰 병목.

재현: `python src/ingest_kg.py` (그래프 재구축) → `python eval/eval_kg_retrieval.py`
(비교 재실행). 단위 테스트(`tests/test_kg.py`)는 정규화·그래프 구축·시드
매칭·랭킹처럼 LLM 없는 결정적 로직만 검증 — 트리플 추출 자체는 LLM
호출이라 CI 대상이 아님.

## Graph RAG 실험 2 — KLUE-RE 공개 코퍼스에서 재검증 (채택 근거 있음)

실험 1의 "미채택"이 기술 자체의 한계인지, 48청크짜리 코퍼스가 너무
작아서인지를 가르지 못한 채로 끝남. 이 실험은 두 변수를 분리함:

- **코퍼스 규모**: 48청크 → 문장 1,500개(30배)
- **그래프 품질**: LLM 추출(노이즈 있음) →
  [KLUE-RE](https://huggingface.co/datasets/klue/klue)의 전문가 라벨을 그대로
  트리플로 사용(노이즈 제거). KLUE-RE는 위키피디아· 뉴스 문장에 (주어,관계,목적어)
  정답이 붙은 공개 관계추출 벤치마크(3.2만 문장, cc-by-sa-4.0, 관계 라벨 29종).

**구성**: `klue_re.py`가 3.2만 문장 중 계통 표본을 뽑아 고유 문장 1,500개를
청크로 삼고(같은 문장에 여러 관계가 있으면 하나로 병합), 관계 라벨 29종
전부에 한국어 질문 템플릿을 달아(받침 유무로 은/는·이/가·을/를 조사를
맞춤 — `render_question`) 질문 120개를 생성. 정답 그래프는 `kg.py`의
`add_triples`를 그대로 재사용하되 LLM 없이 KLUE-RE의 정답 라벨을 직접
입력. `kg.search`/`fused_search`에 코퍼스별 청크 조회표를 주입할 수 있게
살짝 넓혀(하위호환 유지) 원 코퍼스 코드를 고치지 않고 재사용함.

인제스트(`python src/ingest_klue.py`, LLM 호출 없음 — 임베딩만): 문장
1,500개(트리플 있는 문장 1,069개 + 정답과 무관한 방해 문장 431개) → 그래프
노드 1,729개·엣지 1,083개.

**결과** (`eval/eval_klue_retrieval.py`, 자동 생성 질문 120건):

| 방식 | recall@1 | recall@3 | recall@6 | MRR |
|---|---|---|---|---|
| hybrid (기존) | 71% | 92% | 99% | 0.819 |
| **kg 단독** | **99%** | **100%** | 100% | **0.996** |
| hybrid+kg RRF 융합 | 89% | 100% | 100% | 0.944 |

**판정: 채택 근거 있음.** recall@6(사실상 "top-6 안에 있나")은 셋 다
99~100%로 비슷하지만, recall@1과 MRR에서 그래프가 하이브리드를 크게
이김(71%→99%, MRR 0.819→0.996). 하이브리드가 어디서 밀리는지 질문
6건을 직접 대조하면 패턴이 뚜렷함:

> "김종필의 동료는 누구인가요?" — hybrid 1위는 김종필이 나오는 다른 문장
> (오답), 정답은 2위. "강경준의 배우자는 누구인가요?" — hybrid 1위는
> 강경준·배우자가 둘 다 언급된 문장이지만 관계가 다른 문장(부부 예능 출연),
> 정답은 2위. "리사 디 배나의 국적은?" — hybrid 1위는 리사 디 배나가 나오는
> 축구 관련 다른 문장, 정답은 2위.

같은 개체가 나오는 문장은 텍스트 유사도로 서로 잘 구별되지 않음 —
벡터·BM25는 "이 문장이 그 개체를 언급하는가"까지는 잘 잡지만 "이 문장이
질문이 묻는 그 관계를 담고 있는가"는 다른 문제. 그래프는 엔티티→관계→
출처청크 엣지로 이것을 구조적으로 구분해 거의 항상 정확한 문장을 1위로
올림.

반전 하나: RRF 융합이 그래프 단독보다 오히려 나쁨(recall@1 99%→89%).
그래프가 이미 거의 완벽한데, 상대적으로 노이즈 있는 하이브리드 순위를
절반 섞으면 정답을 밀어내는 경우가 생김 — 실험 1의 "융합이 손해였다"와
같은 현상이지만 방향이 다름: **한쪽이 압도적으로 강하면 RRF 같은 균등
융합은 그 강점을 오히려 희석시킬 수 있음.** (가중치를 준 융합이 다음
실험 후보.)

**결론**: 실험 1의 미채택은 기술의 한계가 아니라 코퍼스가 이 기술의
강점(같은 개체를 다루는 문장이 여러 개, 개체 중심 사실 조회)을 담을 만큼
크지 않았기 때문. 그래프가 원 코퍼스로 돌아오려면 정답 그래프가 아니라
여전히 LLM 추출에 의존해야 한다는 제약은 남지만, "이 기술이 언제 값을
하는가"를 실측으로 답할 수 있게 됨 — 채용 공고가 요구한 것도 결국
"Graph RAG를 써봤다"가 아니라 "언제 쓰고 언제 안 쓰는지 판단할 수 있다"
쪽이었을 것.

재현: `python src/ingest_klue.py`(다운로드 + 인덱스·그래프·평가셋 생성,
수 분) → `python eval/eval_klue_retrieval.py`(비교, LLM 없이 수 초).
단위 테스트(`tests/test_klue_re.py`)는 문장 병합·질문 생성·조사 처리 등
결정적 로직을, 실제 HF 다운로드 없이 가짜 데이터로 검증(7개).

### SEED_MATCH_RATIO 스윕 — 도입 당시 미룬 민감도 분석을 완료

시드 판정 임계값(`kg.SEED_MATCH_RATIO`)은 도입 당시 "스윕은 안 했고, RRF
융합이 이 실험의 핵심이라 민감도는 후순위로 미룸"이라고 명시적으로 남겨둔
값(0.6). KLUE-RE(120문항, Graph RAG가 실제로 채택된 코퍼스)로
`eval/sweep_seed_match_ratio.py`를 돌려 0.3~0.9를 스윕함:

| ratio | 평균 시드 수 | kg_only@1 | fused@1 | fused@6 |
|---|---|---|---|---|
| 0.3 | 6.19 | 78% | 84% | 99% |
| 0.6 (기존값) | 1.23 | 92% | 83% | 100% |
| **0.7** | **0.97** | **93%** | **85%** | **100%** |
| 0.8 | 0.97 | 93% | 85% | 100% |
| 0.9 | 0.97 | 93% | 85% | 100% |

0.6은 최적이 아니었음 — 0.7로 올리면 평균 시드 수가 1.23→0.97로 줄면서
(느슨한 매칭이 걷어내던 무관 엔티티 감소) kg_only@1·fused@1이 오히려
상승. 0.8·0.9는 0.7과 완전히 같아 그 이상 올릴 이유가 없음 — 0.7이
"더 이상 엄격해져도 결과가 안 바뀌는" elbow. **0.7로 채택.**

## 비정형 문서 확장 — PDF·DOCX·HWPX 파싱

채용 공고(그래파이 등)가 요구한 "비정형 데이터(PDF/DOCX/HWP) 처리"를 실제
코퍼스 확장으로 구현함. `loaders.py`가 PDF(`pypdf`)·DOCX(`python-docx`)·
HWPX(`python-hwpx`)를 텍스트로 뽑아 마크다운과 같은 파이프라인(청킹→임베딩→
인덱싱)에 합류시킴.

**구형 바이너리 `.hwp`는 만들지 않음** — 이 PC·계정 전체를 검색해도 실물
`.hwp` 파일이 0건이라(2026-08 확인), 검증할 실물 없이 파서를 짜면 동작을
아무도 확인할 수 없기 때문. 대신 `.hwpx`(ZIP+XML 기반 신형식, 2026-05-18부터
중앙부처·지자체 공문서 표준으로 의무화)는 지원함 — 개인 소유 실물은
없지만, 국토교통부가 실제로 웹에 공개 배포한 보도자료(2026년 철도의 날
기념행사)를 내려받아 검증. "합성 문서가 아닌 실물로 검증한다"는 원칙을
"내가 쓴 문서"가 아니라 "실재하는 문서"로 지킨 것 — Graph RAG 실험에서
개인 코퍼스가 작아 KLUE-RE라는 공개 벤치마크로 검증 범위를 넓혔던 것과 같은
논리. `python-hwpx`(Apache-2.0)에 위임 — HWPX는 DOCX보다 구조가
복잡해(섹션·트랙체인지 등) 직접 XML을 파싱하는 것보다 안전함.

최초 검증은 실제 문서 3건으로 진행(합성 테스트 문서가 아니었음) —
`segmentation-paper.pdf`(3D 시맨틱 세그멘테이션 논문 발표자료, 21p),
`resume-original.docx`(검증된 정본 이력서), `moltm-railway-day-notice.hwpx`
(국토교통부 실제 보도자료). 뒤의 둘은 테스트 픽스처(`tests/fixtures/`)로만
두고 실제 RAG 코퍼스(`data/docs/`)에는 넣지 않음 — 이유는 아래.

> **정정(2026-08): 뒤의 두 픽스처는 현재 저장소에 없음.** 각각 개인정보와
> 외부 기관 문서라 공개 저장소에 두면 안 되는 파일이어서 히스토리 정리로
> 제거(`.gitignore` 참고). 문제는 그 다음 — 파일이 사라졌는데 테스트는

> 검증하지 않는 상태였음(121 passed → 119 passed + 2 skipped).
> "검증했다"고 문서에 적힌 채 검증만 사라지는 것이 가장 나쁜 조합이라,
> 픽스처를 테스트 시점에 코드로 생성하도록 변경(`tests/test_loaders.py`).

>
> 다만 원래 검증보다 약함. 같은 라이브러리로 쓰고 읽는 왕복이라 다른
> 생산자(한글 등)가 만든 파일의 변형은 못 잡음. 이 프로젝트는 실제로
> "HWPX인 줄 알았는데 OLE 기반 구형 `.hwp`"인 파일을 두 번 만났고 그것은
> 실물이었기에 잡혔음 — 그 커버리지는 이제 없음. 공개 가능한 실물 HWPX를
> 구하면 되돌리는 것이 맞음.

주의: 실제로 검토했지만 의도적으로 제외한 문서가 하나 있음 —
`이윤선_프로젝트상세정보은행_v2.docx`는 2026-08-01 근거 감사에서 이미
삭제·정정됐던 미검증 수치("WhisperX 기반" — 실제 코드는 Faster Whisper,
RTF·CER을 측정치처럼 적었지만 기록 없음)와 `"구체 수치: 내부 기밀"` 같은
미완성 placeholder를 그대로 담고 있었음. 이것을 넣으면 어렵게 정정한 오류를
RAG 지식베이스에 재주입하는 꼴이라 제외 — **문서를 파싱할 수 있다는 것과,
그 문서를 신뢰해도 된다는 것은 다른 문제.**

### DOCX를 코퍼스에 넣었다가 뺀 이야기 — 근중복이 기존 질문을 깬 사례

처음엔 두 문서를 둘 다 코퍼스에 넣었음. `resume-original.docx`는 이미
`resume.md`에 있는 내용과 겹치지만, "DOCX 파서가 뽑은 내용이 이미 검증된
사실과 일치하는가"를 교차 확인하는 용도로 넣을 만하다고 판단.

그런데 기존 51문항 전체 평가(`eval/evaluate.py`)를 다시 돌려보니, 그간
한 번도 틀린 적 없던 "이윤선의 제1저자 논문은 몇 편인가요?"가 "4편"으로
틀림(정답 7편). `results.json`에 저장된 실제 컨텍스트를 열어 원인을 확인:

- top-5 컨텍스트 중 2개가 근중복 — `resume.md`와 `resume-original.docx`의
  "PROFESSIONAL SUMMARY" 도입부가 문장까지 거의 동일. 벡터 검색이 이 둘을
  별개의 강한 신호로 보고 나란히 뽑음.
- 그 바람에 "논문 2편 게재(제1저자, 전체 경력 논문 7편 중 일부)"라는,
  숫자를 명확히 구분해 주는 청크가 top-5의 5번째로 밀림.
- `CONTEXT_ORDER=reversed`(config.py) 하에서 5번째 청크는 프롬프트의
  맨 앞 — 이 프로젝트가 이미 다른 실험 세 번에서 확인한 "모델이 가장
  못 보는 자리". 모델이 그 구분 정보를 놓치고 다른 곳의 "2편"과 잘못
  조합해 "4편"을 생성.

중복 소스를 코퍼스에 추가하면 다양성이 줄어 오히려 손해라는 것이 실측으로
확인됨 — 새 정보가 없는 문서(같은 사실의 다른 포맷)는 top-N 슬롯을
잡아먹기만 함. `resume-original.docx`를 코퍼스(`data/docs/`)에서 빼서
`tests/fixtures/`로 옮기고 파서 검증 전용으로만 유지
(`tests/test_loaders.py`가 TTFB 수치·회사명을 `resume.md`와 대조).
재인제스트 후 재평가에서 "제1저자 논문은 몇 편인가요?" → "이윤선의
제1저자는 7편입니다"로 정답 복구(`eval/results.json` 확인).

### 최종 코퍼스 (PDF만 추가) — 결과

**인제스트 결과** (`python src/ingest.py`): 문서 5개 → 6개, 청크 51개(다이어그램
포함) → 58개. `inspect_data.py`가 새 청크에서 결함 0건 검출 — PDF의
다이어그램 페이지(아키텍처 그림)는 단어가 흩어진 형태로 나오지만, 기존
마크다운 다이어그램 청크와 같은 이유로 유지(수식·모델명 같은 키워드는
살아 있음).

기존 gold 라벨(10문항)이 md5 기반이라 코퍼스 확장에도 깨지지 않음
(recall@1 90%·MRR 0.95 그대로) — 청크 순서가 바뀌어도 내용 해시는 그대로라는
이 프로젝트의 설계가 실제로 값을 한 지점.

새 코퍼스를 겨냥한 질문 4개를 추가해 "파싱됐다"가 아니라 "검색이
되는가"까지 측정함(`eval/eval_retrieval.py`, 총 14문항):

| 질문 | 정답 청크 순위 | 생성 결과 (`evaluate.py`) |
|---|---|---|
| 지원 과제 번호는? | 3위 | PASS |
| 사용한 GPU는? | 5위 | PASS |
| 손실 함수는? | 5위 | PASS |
| 딥러닝 프레임워크는? | **MISS** | FAIL — "Trans-Unet"(모델 아키텍처명)이라 답해 프레임워크(Tensorflow)와 혼동 |

recall@1은 90%→64%로 하락 — PDF 청크가 기존 마크다운보다 검색이 어려움.
원인은 내용이 아니라 형식: `"CPU : AMD EPYC 7742 ... • GPU :
A100 80GB • HDD : 2TB ..."`처럼 발표자료 특유의 불릿 스펙 나열이라,
자연문으로 쓰인 기존 코퍼스·질문과 텍스트 유사도가 잘 맞지 않음.
그런데도 생성까지 가면 4문항 중 3개가 정답 — top-5 안에만 들어오면
(3~5위 포함) GENERATE_TOP_N=5 컨텍스트에 실려 모델이 충분히 답할 수
있었다는 의미. 유일한 실패(프레임워크)는 검색이 아니라 질문의 모호함이
원인 — "프레임워크"를 모델이 "Tensorflow"(구현 도구)가 아니라
"Trans-Unet"(모델 아키텍처명, 문서에 더 두드러지게 등장)으로 해석함.
파싱·인덱싱 파이프라인은 정상 작동.

기존 51문항 + 새 4문항(총 55문항) 전체 평가: 76%(42/55). 핵심 증거는
DOCX 제거 전후 대조 — 제거 전엔 신뢰도 높던 "제1저자 논문은 몇 편인가요?"가
"4편"으로 틀렸고, 제거 후 재평가에서 "7편"으로 정답 복구를 직접 확인함.
남은 실패(comparison 0/2, aggregation 3/6, trap 1/2)는 이 프로젝트가 이미
문서화해 온 취약 유형(위 "시도했으나 채택하지 않은 것들" 절)과 동일한
자리에서 발생 — 코퍼스 확장이 새로운 실패 유형을 만들지는 않았음.

**결론**: 이번 확장에서 가장 값진 결과는 PDF 파싱 성공이 아니라 "코퍼스를
넓히는 것은 공짜가 아니다"를 실측으로 증명하고, 실제로 사고를 내고, 고친
것 — 새 정보가 없는 중복 문서는 top-N 슬롯 경쟁에서 기존 질문의 정답률을
깎을 수 있음. 채용 공고가 원한 것도 "PDF를 파싱할 수 있다"가 아니라
"코퍼스를 늘릴 때 무엇을 조심해야 하는지 안다" 쪽이었을 것.

재현: `python src/ingest.py`(코퍼스 재구축) → `python eval/eval_retrieval.py`
(검색 평가) → `python eval/evaluate.py`(전체 평가, 당시 55문항 · 현재
100문항). 단위 테스트(`tests/test_loaders.py`, 5개)는 PDF는 실물
(`data/docs/segmentation-paper.pdf`)로, DOCX·HWPX는 테스트 시점에 각 규격
라이브러리로 생성한 진짜 파일로 검증 — 픽스처 제거 경위와 그 한계는
위 정정 상자 참고.

## BM25 토크나이저 교체 — 정규식+bigram → Kiwi 형태소 분석

한국어 전처리를 재점검하며 웹서치로 "요즘 추세"를 확인하니, 한국어 BM25는
형태소 분석기(Kiwi 등)를 쓰는 것이 표준이고 정규식 기반 방식은 형태소
경계를 몰라 근본적인 한계가 있다는 지적이 반복해서 나옴. 이 프로젝트는
지금까지 자체 규칙(문자 종류별 런 분해 + 한글 bigram, "### 4. BM25
토크나이저 결함")으로 이 문제를 근사해 옴 — bigram은 형태소 경계를
모르는 근사치라 노이즈가 섞이고("회사들을" → '사들'·'들을' 같은 의미 없는
조각까지 토큰화), 진짜 복합명사 분해("화자분할" → "화자"+"분할")는 불가.

**Kiwi(kiwipiepy) 실측**: 조사(JX/JKO 등)를 실제로 인식해 분리하고
("Throughput은"→'throughput'+조사, "Throughput:"→'throughput'+기호,
둘 다 'throughput' 하나로 겹침), 복합명사를 형태소 경계로 정확히 분해
("화자분할"·"화자 분할" 둘 다 ['화자','분할']로 동일). "10-2538225-0000"
같은 일련번호는 W_SERIAL 태그로 오히려 더 정확히 통째로 인식.
JVM이 불필요해(Mecab·Kkma·Okt와 달리 순수 C++ 바인딩) 이 프로젝트의
"서버 없이 파일 하나로 끝난다" 원칙에도 부합. 체언(N*)·용언 어간(V*)·
부사(MA*)·어근(XR)·외국어(SL)·한자(SH)·숫자(SN)·URL/일련번호(W_*) 태그만
남기고 조사·어미·순수 기호는 제거.

검색 단독 지표는 미묘하게 갈림. `eval_retrieval.py`(14문항):

| 지표 | 정규식+bigram | Kiwi |
|---|---|---|
| recall@1 | 64% | 50% |
| recall@3 | 79% | 79% |
| recall@6 | 93% | 93% |
| MRR | 0.731 | 0.669 |

recall@1이 떨어진 두 문항("등록된 특허 번호를 알려주세요.", "이윤선이
근무한 회사들을 알려주세요.")을 직접 진단하니 정답 청크가 1위→2위로
한 칸 밀린 것(둘 다 recall@3에서는 그대로 적중) — bigram이 만들던
많은 노이즈 토큰이 사라지면서 BM25의 문서 길이 정규화 기준이 바뀌어,
근소한 차이로 순위가 갈리는 문항에서 순서가 뒤집힌 것으로 보임.

**그런데 전체 파이프라인(LLM 포함) 정확도는 오히려 상승.**
`GENERATE_TOP_N=5`라 순위가 1위든 2위든 LLM 컨텍스트에는 똑같이 들어감 —
그래서 recall@1의 하락이 실제 답변에는 반영되지 않음. 같은 55문항
`evaluate.py`를 정규식+bigram(스태시로 되돌려 재현: 76%, 42/55)과
Kiwi(80%, 44/55)로 각각 직접 실행해 비교:

| 지표 | 정규식+bigram | Kiwi |
|---|---|---|
| Answer Accuracy | 76% (42/55) | 80% (44/55) |
| Rewrite Rate | 67% | 76% |

유형별로도 fact(77%→86%)·enumeration(78%→67%, -1문항)·comparison(0%→50%)
등 방향이 엇갈리지만, 순수 노이즈였던 bigram 조각이 사라지고 복합명사가
정확히 분해된 효과가 recall@1의 근소한 순위 뒤집힘보다 더 크게 작용한
것으로 판단해 채택. 검색 단독 지표만 보고 판단했다면 이 개선을 놓쳤을 것 —
**전체 파이프라인으로 검증해야 하는 이유.**

재현: `git stash`로 `src/graph.py`·`requirements.txt`를 되돌린 뒤
`eval/evaluate.py` 실행(정규식+bigram), `git stash pop` 후 재실행(Kiwi).

### RRF_K 스윕 — "표준값"이라 실측 안 했던 상수 검증

`hybrid_search`·`fused_search`가 공유하는 RRF 완충 상수(K=60, score =
Σ 1/(K+rank))는 도입 당시 "표준값"이라는 이유로 스윕 없이 사용.
`eval/sweep_rrf_k.py`로 처음 측정함.

원 코퍼스(14문항)에서는 K=1이 recall@1 57%로 K=60(50%)보다 높아 보였지만,
14문항에서 7%p는 질문 1개가 뒤집힌 것뿐. KLUE-RE(120문항, 통계적으로
더 믿을 만한 표본)로 재확인하니 결과가 반대:

| RRF_K | recall@1 | recall@3 | recall@6 | MRR |
|---|---|---|---|---|
| 1 | 70% | 88% | 96% | 0.792 |
| 5~200 (전 구간 동일) | 73% | 88% | 96% | 0.812 |

K=5부터 200까지 지표가 완전히 평평하고, K=1만 오히려 더 낮음 — 작은
표본의 신호와 방향이 정반대. 60은 "실측 없이 관행값을 썼다"가 아니라
실측으로도 평평한 최적 구간 안에 있는 값으로 확인됨. 바꿀 이유가 없어
그대로 유지 — 이 실험의 산출물은 상수 변경이 아니라 "안 바꿔도 되는 이유".

### NEIGHBOR_WINDOW 재측정 — "반복해서 다시 재라"고 남긴 TODO 닫기

`config.py`에 "반복을 늘려 다시 재는 것이 다음 순서"로 명시해 둔 미완 항목.
예전 측정은 `GENERATE_TOP_N=3` 시절 값이라, 현재 조건(`TOP_N=5`,
TYPE_ROUTING은 전역값 스윕을 덮지 않도록 끔)에서 55문항 × 2회로
재측정함(`eval/ab_neighbor_window.py`).

전체 정답률은 이번에도 동률 — W=0 78%(86/110) vs W=1 77%(85/110).
그러나 유형별 분해는 예전보다 훨씬 선명하게 갈림:

| 유형 | W=0 | W=1 | |
|---|---|---|---|
| enumeration | 12/18 | **18/18** | 만점 — 가장 큰 이득 |
| comparison | 1/4 | **3/4** | |
| aggregation | 5/12 | 6/12 | |
| fact | **40/44** | 33/44 | 가장 큰 손해 |
| refusal | **20/20** | 18/20 | 환각 저항이 무너짐 |
| temporal | **6/8** | 5/8 | |

지연도 2.9s → 4.6s(1.6배)로 증가. **전역 기본값은 계속 0이 맞음** —
fact가 전체 문항의 40%라 전역으로 켜면 손해가 이득을 덮음. "컨텍스트를
키우면 환각 저항이 먼저 무너진다"는 이 저장소의 반복 관찰(§9)이 refusal
20/20 → 18/20으로 다시 한 번 재현됨.

이 측정의 값어치는 기본값 변경이 아니라 유형별 라우팅을 정당화한 것 —
하나의 전역값으로는 enumeration(+6)과 fact(−7)를 동시에 만족시킬 수
없다는 것이 수치로 확인됨.

### 라우팅 내용 자체를 겨루다 — 그리고 우연히 얻은 대조군

위 결과는 곧바로 다음 질문으로 이어짐: enumeration이 W=1에서 만점을
냈는데, 정작 `route.ROUTES`는 enumeration에 `sandwich`만 주고 W는 주지
않음. 그럼 `sandwich + W=1`이 최선인가? — 그런데 그 조합은 아무도 안
재본 조합. route.py 주석이 경고하는 바로 그 함정("처음엔 W=1만
얹었더니 미측정 조합이 됐고 … 실측으로 확인")이라 가정하지 않고
`eval/ab_route_variants.py`로 직접 대조함.

첫 시도(2회 반복)는 결론을 못 냈는데, 실패 자체가 유용했음. 세 조합
모두 aggregation 오버라이드는 완전히 동일한데도 결과가 5/12 → 7/12 →
8/12로 흔들림. 즉 이 열은 의도치 않게 대조군(control group) 역할을
했고, 잔류 노이즈가 25%p나 된다는 것을 드러냄 — 그 상태로는 어떤 조합이
나은지 말할 수 없음.

반복을 5회로 올리자 신호와 노이즈가 갈림:

| 조합 | aggregation (대조군, 설정 동일) | enumeration (변수) |
|---|---|---|
| current (`sandwich`) | 16/30 | 31/45 |
| **`NEIGHBOR_WINDOW=1`, 역순** | 17/30 | **38/45** |

대조군이 +3%p로 잠잠한데 변수는 +16%p로 이동 — 효과가 노이즈보다 확실히
큼. 구제된 문항도 애매하지 않음("인프라 모니터링에 사용한 도구들을
알려주세요" 0/5 → 5/5). enumeration에는 sandwich보다 이웃 확장이 낫다는
결론으로 `ROUTES`를 변경(sandwich 제거, W=1 추가).

단, 55문항 전체 평가(1회)로는 이 개선이 보이지 않았음 — 82%(45/55) →
80%(44/55)로 오히려 1문항 낮음.

> **정정(2026-08): 위 문장의 원인 설명이 틀렸었음.** 원래 여기에 "검정력
> 문제(전체 평가 1회는 enumeration 관측이 9개뿐이라 16%p 효과를 검출할 수
> 없다)"라고 적었는데, 진짜 이유는 더 단순하고 더 나빴음 — 당시
> `evaluate.py`는 `graph.invoke()`를 직접 불러 유형별 라우팅을 아예
> 거치지 않았음. enumeration 오버라이드를 무엇으로 바꾸든 이 평가에는
> 반영될 수 없었고, 82%↔80%는 같은 코드를 두 번 잰 노이즈였음. 배선을
> `graph.run()`으로 모아 수정(회귀 테스트 `test_run_applies_type_routing_
> overrides`). 검정력 이야기 자체는 여전히 맞지만 이 수치의 원인은
> 아니었음 — 틀린 설명으로 맞는 결론을 방어하고 있었던 셈이라 남겨 둠.

판단 근거는 관측 45개짜리 타겟 실험(`ab_route_variants.py`, `ask()` 경로라
라우팅이 실제로 걸림)이며, 배선을 고친 뒤의 전체 재측정은 "배선과 3B 재현"
절과 100문항 기준선으로 이어짐.

교훈은 수치보다 방법 — 설정이 같아야 하는 열을 실험에 함께 두면 그 열이
그대로 노이즈 측정기가 됨. "3B 런 간 편차 ±6%p"라고 적어만 두는 것보다,
매 실험이 자기 노이즈를 스스로 보고하게 만드는 편이 나음.

### targeted 프롬프트 — 반복 횟수가 결론을 두 번 뒤집은 사례 (미채택)

`GENERATE_PROMPT_VARIANT=targeted`는 실측된 두 실패(열거 첫 항목만 답함,
같은 대상의 숫자 여러 개일 때 범위 혼동)를 겨냥한 지시 두 줄을 더한
프롬프트. 만들어 두고 전체 평가셋 대조는 없었음.

**1차(2회 반복): 채택할 뻔함.** base 75%(83/110) vs targeted
80%(88/110) — +5%p. 하지만 이 저장소가 문서화해 온 편차가 ±6%p라 그
안쪽. 바로 반영하지 않고 반복을 늘림.

**2차(4회 반복): 완전 동률.** base 78%(171/220) vs targeted
78%(171/220). +5%p는 통째로 노이즈였음.

다만 동률의 내역이 무효과가 아니라 상쇄로 보임 — aggregation
10/24 → 13/24(개선), fact 76/88 → 71/88(악화, 긴 프롬프트가 단순 조회를
방해). 특히 "한국자동차공학회에 게재한 논문은 몇 편?"이 0/4 → 4/4로
구제됐는데 이것은 targeted 두 번째 규칙이 정확히 겨냥한 실패.
그렇다면 `NEIGHBOR_WINDOW`처럼 aggregation에만 라우팅하면 되겠다는
가설이 성립.

**3차(라우팅 가설, 15문항 × 5회): 기각.** aggregation은 14/30 →
17/30(+10%p)이지만 대조군(enumeration — 두 조합의 설정이 동일)이
40/45 → 38/45(−4.4%p)로 함께 흔들려 효과가 노이즈의 2배 남짓.
결정적으로 구제 근거였던 바로 그 문항이 여기서는 0/5 대 0/5.
거의 같은 조건에서 `0/4→4/4`와 `0/5→0/5`가 갈렸다면 그 "구제"는
재현되지 않는 노이즈였다는 의미. 근거가 무너졌으므로 전역 기본도
라우팅도 넣지 않음.

이 항목이 남긴 것은 기능이 아니라 기준 — 개선처럼 보이는 수치를
만나면 (1) 반복을 늘리고, (2) 설정이 같아야 하는 대조군을 붙이고,
(3) 근거로 삼은 개별 문항이 다른 실험에서도 같은 방향인지 확인할 것.
이번엔 세 단계 모두에서 후보가 탈락함.

### corrective 루프 자체를 재측정했다 — 이 코퍼스에서는 비용만 쓴다

이 저장소의 이름이 Corrective-RAG인데, 정작 그 루프의 근거가 서로
엇갈려 있었음: 10문항 A/B는 50% → 60%로 ON 우세, 14문항 층화표본은
81% → 69%로 ON 열세. 둘 다 표본이 작고 `graph.invoke`를 직접 불러
라우팅을 건너뛴 조건. 배선을 고친 김에 75문항 × 3회를 프로덕션과 같은
`run()` 경로로 재측정함.

대조군은 "ON에서 실제로 재작성이 일어났는가"로 나뉨. grade가
"충분하다"고 통과시킨 문항은 generate가 받는 문서가 OFF와 같아 사실상
같은 경로:

| 구분 | OFF → ON | |
|---|---|---|
| 변수 (실제 재작성된 60문항) | 137/180 → 139/180 | +2판정 |
| 대조군 (재작성 0회 15문항) | 39/45 → 38/45 | −1판정 = 노이즈 |
| 지연 중앙값 | 1s → 3s | **3배** |

효과(+2/180 ≈ 1%p)가 대조군 노이즈와 같은 크기이고, 구제 9 / 악화 11로
방향성도 없음. **정확도 이득 0에 지연 3배.**

같은 조건으로 14문항 층화표본도 다시 돌리니 부호가 뒤집힘 —
변수 27/39 → 24/39(−3판정). 네 번의 측정을 모으면:

| 측정 | 표본(변수 판정 수) | 변수 변화 |
|---|---|---|
| 10문항 A/B (구 경로) | 30 | +10%p |
| 14문항 층화 (구 경로) | 42 | −12%p |
| **75문항 (프로덕션 경로)** | **180** | **+1.1%p** |
| 14문항 층화 (프로덕션 경로) | 39 | −7.7%p |

부호가 계속 뒤집힘. 표본이 가장 큰 75문항(변수 판정 180개)이 +1.1%p로
사실상 0이고, 작은 표본들이 양쪽으로 크게 튐 — 효과가 없을 때 나오는
전형적인 모양. (층화표본은 14문항 중 13문항이 재작성돼 대조군이
1문항뿐이라 자체 노이즈 측정도 안 됨 — 작은 표본의 또 다른 한계.)

원인은 리랭커와 동일 — 이 코퍼스는 `satisfied@6`이 97~100%라 검색이 이미
답을 top-6 안에 올려놓음. 고칠 것이 없는데 고치는 단계를 돌리는 셈.
재작성률이 76%나 되는데 정답률이 안 오르는 것이 그 증거: grade가 "부족"
이라고 판정한 76% 중 대부분은 실제로 부족하지 않았음.

**그럼에도 기본값은 `MAX_REWRITES=1`로 유지.** 이것은 측정이 아니라 제품
판단 — 이 저장소의 주제가 Corrective-RAG이고 루프를 끄면 시연 대상
자체가 사라짐. 대신 "이 코퍼스에서는 비용만 쓴다"를 숨기지 않고 기록.
끄려면 `MAX_REWRITES=0`이면 되고, 검색이 실제로 실패하는 코퍼스에서
다시 재는 것이 이 손잡이의 다음 순서.

리랭커·팀 라우팅·corrective 루프가 전부 같은 결론에 도달한 것이 이 절의
진짜 내용 — 세 기능 모두 "검색이 실패할 때" 값을 하는 장치인데, 이
코퍼스에서는 검색이 실패하지 않음. 기능이 나쁜 것이 아니라 문제가 없는
것이고, 그것을 구분하는 것이 이 실험들의 성과.

## HyDE — 어휘 격차의 표적은 맞혔지만 미채택

한계 절에 "HyDE나 동의어 확장이 정공법이지만 둘 다 미측정"으로 남겨 뒀던
항목을 실측함(`eval/ab_hyde.py`). 표적은 명확했음 — 검색이 유일하게
구조적으로 실패하는 문항 "세그멘테이션 모델 구현에 사용한 딥러닝
프레임워크는?"의 정답 청크는 `• Tensorflow 2.8.0`뿐이라 질의와 겹치는
토큰이 0개이고, 임베딩도 하드웨어 스펙 나열이라 질문 의미와 붙지 않음.

**구현**: `hybrid_search`가 LLM이 쓴 "가상 답변 단락"으로 검색한 순위
목록을 RRF에 추가함(질의 목록을 대체하지 않음 — 이미 잘 찾던 문항의
두 표는 유지). 질의당 LLM 호출 1회가 추가됨.

**1차(full 모드 — 단락 전체로 벡터+BM25): 표적을 못 맞힘.** 그런데
실패가 두 메커니즘으로 깨끗하게 분해됨. 저장해 둔 가상 단락을 열어 보니:

- **틀린 추측이 임베딩을 오염시킴** — GPU 문항의 가상 단락이 "Tesla
  V100, RTX 계열"을 추측(실제 정답은 A100). 그 임베딩이 엉뚱한 청크들을
  끌어올려 멀쩡히 rank 5던 gold가 top-6 밖으로 밀림.
- **맞는 추측은 BM25에서 희석됨** — 프레임워크 문항의 가상 단락에는
  'TensorFlow'가 실제로 있었음. 그런데 단락의 흔한 토큰 20여 개
  (세그멘테이션·모델·구현…)가 긴 산문 청크들과 잔뜩 매치되면서, 다리가
  될 유일한 토큰의 신호가 묻힘. gold는 bm25(가상단락) top-6에도 못 들어감.

여기서 비대칭이 확인됨. 틀린 추측은 임베딩에는 독이지만 BM25에서는 무해함 —
코퍼스에 없는 토큰('v100')은 아무 문서와도 매치되지 않아 0점일 뿐.
그래서 2차 변형을 제작함.

**2차(terms 모드 — 질의에 없는 영숫자 토큰만 BM25로): 표적을 정확히
맞힘.** 어휘 격차의 실체가 "프레임워크"(한국어 일반명사)와
"Tensorflow"(영문 기술 명칭) 사이의 골이므로, 가상 단락에서 그 다리가
되는 영숫자 토큰만 남기고 벡터 쪽은 제거함:

| | off | full | terms |
|---|---|---|---|
| 프레임워크 문항 gold | MISS | MISS | **rank 3** |
| satisfied@5 (커버리지 65문항) | 88% | 89% | **91%** |
| satisfied@6 | 94% | 92% | 92% |

실효 컷오프(k=5, generate가 받는 범위)에서는 잃은 문항이 0이었고, 표적
문항을 단독 검증하니 엔드투엔드 0/3 → 3/3 — "Tensorflow 2.8.0과
Keras 2.8.0입니다"라는 정답이 세 번 다 나옴. 여기까지 보면 채택.

**그런데 75문항 전체 A/B가 뒤집음.** Kiwi 토크나이저 때 배운 "검색
지표만 보고 판단하지 말 것"대로 전체 파이프라인(× 2회)을 돌렸고, 실행
사고(타임아웃으로 죽은 줄 알았던 1차 실행이 실제로는 완주) 덕에 같은
측정이 독립적으로 두 번 존재하게 됨:

| 실행 | off | terms | 델타 |
|---|---|---|---|
| 1차 (75×2) | 116/150 (77%) | 106/150 (71%) | **−10판정** |
| 2차 (75×2) | 115/150 (77%) | 105/150 (70%) | **−10판정** |

두 실행이 정확히 같은 크기로 짐 — ±6%p 편차로 설명될 모양이 아님.
문항별로 갈라 보면 방향도 일치: 표적 프레임워크 문항은 양쪽 모두
0/2 → 2/2로 구제됐지만, GPU·손실 함수·CER·"확장 전 채널 수" 같은 fact
문항들이 양쪽 모두에서 2/2 → 0/2로 깨짐.

원인 분석 — 커버리지 @5에서 gold를 잃은 문항은 0인데 정답률이 하락함.
terms 토큰(tensorflow·keras·nvidia…)이 PDF 스펙 청크들을 전반적으로
끌어올리면서, gold가 rank 4~5에 있던 문항들의 컨텍스트 구성과 배치가
바뀐 것. 근거가 여전히 top-5 안에 있어도 함께 실리는 이웃과 위치가
바뀌면 소형 모델의 답이 흔들림 — 이 저장소가 반복 관찰해 온 "근거를
컨텍스트에 넣는 것과 모델이 그것을 쓰는 것은 다른 문제"의 새 변주.
이번엔 넣는 데 성공하고도 주변을 바꿔서 잃음.

**판정: 미채택(기본 꺼둠), 손잡이 유지(`HYDE=1 HYDE_MODE=terms`).**
어휘 격차 1문항 구제 < 흔들린 fact 여러 문항 + 지연 +37%(질의당 LLM
1회). 리랭커·corrective 루프와 결이 같음 — 이 코퍼스는 검색 실패가
사실상 1문항뿐이라 고칠 대상이 너무 작고, 개입의 부작용이 그 이득을
덮음. 어휘 격차 문항이 여럿인 코퍼스라면 결론이 달라질 수 있고,
그때 재는 것이 이 손잡이의 다음 순서.

재현: `python eval/ab_hyde.py`(검색 층 3조건, 가상 단락 원문까지 결과에
저장) → `python eval/ab_hyde.py --generate --repeat 2`(전체 파이프라인).
단위 테스트는 정리 함수·RRF 융합·terms 추출 같은 결정적 로직만 커버.

## 기본 모델 3B → 7B (2026-08-11)

"왜 CPU만 쓰냐"는 질문이 계기. 아래 한계 절에 기록된 GPU 크래시
(ggml-cuda 0xC0000005)를 재확인하니 Ollama 0.32.6에서 이미 해소돼
있었음 — 3b·7b·bge-m3 전부 100% GPU 적재, 7b 동시 적재 시 VRAM
5.8/8.2GB. 즉 "CPU라 느려서 3b"라는 기본값의 전제가 낡은 기록이었음.

전제가 사라졌으므로 같은 프로덕션 `run()` 경로·같은 채점기로 재측정:

| | 3b (같은 날 기준선) | 7b |
|---|---|---|
| 정답률 (75문항×2회) | 77% (115·116/150) | **85% (64/75 두 패스 동일)** |
| 재작성률 | 67~76% | **16%** |
| 지연 중앙값 | 4.3~4.6s | 4.7s (동급) |

**+8%p를 지연 비용 없이 획득** — GPU에서는 모델 크기의 시간 비용이
사실상 사라져 3b를 고를 이유가 남지 않음. 재작성률 급감은 검색이
좋아진 것이 아니라 grade 오탐이 줄어든 것(corrective 루프 재측정 때
"재작성 76%의 대부분은 실제로 부족하지 않았다"고 확인한 그 오탐).
두 패스가 64/75로 정확히 같은 것도 3b(±6%p)와 다른 점 — 편차가 작아져
이후 A/B 해상도도 좋아짐.

기본값을 7b로 올리며 두 가지를 함께 기록함. (1) 이 문서의 기존 A/B
수치는 전부 3b 기준 — 유형별 라우팅·top-N 같은 채택 근거가 7b에서
같은 방향인지는 다시 재야 하고, 이후 A/B는 7b 기준선으로 새로 측정
(유형별 라우팅은 7b 재검증 완료 — "최근 추가" 절). (2) TEAM_ROUTING
(+18%p)은 14b에서만 검증됐고 3b에서 0이었음 — 7b 재측정 결과는
"7b 재측정" 절 참고(`results_75q_7b_run1/2.json`).

교훈은 모델보다 기록에 있음 — "한 번 확인한 장애"는 버전이 바뀌면 낡음.
크래시를 재현까지 해서 적어 둔 기록이 오랫동안 기본값을 잘못 묶어 두고
있었음.

## 한계

- **정답률에는 "근거 없이 맞은" 문항이 섞여 있음.** `audit_coverage.py`가
  1건을 지목 — "인프라 모니터링에 사용한 도구들을 알려주세요"는 PASS인데,
  실제로 프롬프트에 들어간 청크 어디에도 정답 패턴(`Prometheus`·
  `Grafana`)이 없음. 검색이 근거를 못 가져왔는데 모델이 파라미터 지식으로
  맞힌 것(둘 다 흔한 모니터링 도구). 라벨 문제가 아니라 검색 문제이고,
  이런 PASS는 정답률을 그만큼 부풀림. 감사는 이 상황을 "라벨 누락"
  (근거는 회수됐는데 라벨에 경로가 없음)과 다른 이름으로 보고함 —
  한 메시지로 묶여 있을 때는 고칠 곳이 라벨인지 검색인지 구분되지 않았음.
- **평가셋 크기가 시기마다 다름(51 → 55 → 63 → 71 → 75 → 100).** 위 각
  실험의 수치는 그 시점의 표본에서 잰 것이라 서로 직접 비교 불가 —
  특히 55문항 표기가 붙은 실험들(Kiwi 토크나이저·NEIGHBOR_WINDOW·RERANK·
  targeted 프롬프트)은 PDF 4문항까지만 있던 표본이고, 71문항 표기가 붙은
  것들(trap 재설계·팀 라우팅·모델 크기 스윕)은 그 뒤 확장된 표본.
  두 갈래를 병합한 표본이 75문항, 현재는 100문항. 옛 결론들 중 100문항에서
  재측정된 것은 일부(유형별 라우팅·verify 심판)뿐임.

  유형별 수치는 방향성 참고용(확장 전 5~23보다는 나음).

## 최근 추가 (표시 없으면 A/B 전 — 기본 꺼짐)

- **grade 구조화 출력** — `judge_relevance()`가 자유 문장 정규식 파싱 대신
  `ChatOllama.with_structured_output()`으로 `GradeVerdict(relevant: bool)`을
  강제함. eval_grade.py가 잰 오탐 20%, 그리고 corrective 루프 A/B
  재검증(51문항 층화 표본)에서 그 오탐이 실제로 정답률을 깎는 것까지
  확인한 뒤 교체. 파싱 버그 클래스 자체가 구조적으로 사라짐.
- **리랭커** (`config.RERANK`) — ❌ **실측 후 미채택(2026-08).** RRF 순위를
  로컬 LLM 1회 호출로 다시 매김(listwise, 구조화 출력). cross-encoder 등
  새 의존성 없이 diagnose.py가 지목한 병목(검색O·정답X)을 겨냥함.
  `eval/ab_rerank.py`(55문항 × 2회)로 처음 재보니 정확도는 완전히
  동률(78%, 86/110 대 86/110)인데 지연만 2.6s → 5.1s로 2배. 뒤집힌
  8문항도 상승 4 / 하락 4로 방향성 없음. 켤 이유가 없어 기본 꺼둠 —
  이제는 "안 재봐서 꺼둔 것"이 아니라 "재봤더니 값을 못 해서".
- **유형별 라우팅** (`config.TYPE_ROUTING`, `src/route.py`) — ✅ **채택,
  기본 켜짐(2026-08).** 규칙 기반으로 질문 유형을 분류해 aggregation은
  `NEIGHBOR_WINDOW=1`+`GENERATE_TOP_N=3`, enumeration은
  `NEIGHBOR_WINDOW=1`을 그때만 적용(enumeration은 원래 sandwich였다가
  후속 실험에서 이웃 확장으로 교체 — "라우팅 내용 자체를 겨루다" 절).
  두 손잡이 다 "전역으로 켜면 어떤 유형은 좋아지고 어떤 유형은
  나빠진다"로 끝났던 것의 절충안. 재검증(`eval/ab_type_routing.py`,
  aggregation·enumeration 15문항 × 3회, Kiwi 토크나이저·
  SEED_MATCH_RATIO=0.7 반영 후): OFF 69% → ON 78%, 구제 2 / 악화 0 /
  변화없음 13 — 악화가 하나도 없어 트레이드오프가 아니라 순개선이라
  기본을 켬.
  > **정정(2026-08)** — 원래 여기에 "55문항 전체 재평가로도 같은 방향 확인:
  > 80%(44/55) → 82%(45/55)"라고 적었는데 그것은 근거가 아니었음. 당시
  > `evaluate.py`는 `graph.invoke()`를 직접 불러 `_type_routing`을 건너뛰고
  > 있었음 — 즉 "켠 전"과 "켠 후"가 같은 코드 경로였고 2%p 차이는 순수
  > 노이즈. 실측으로 확인함(aggregation 질문 실행 중 관측된
  > `(NEIGHBOR_WINDOW, GENERATE_TOP_N)`이 invoke 직접 호출은 `(0,5)`,
  > 라우팅 적용 시 `(1,3)`). 배선을 `graph.run()` 하나로 모아 수정했고,
  > 채택 근거는 `ab_type_routing.py`(ask() 경로를 쓰므로 라우팅이 실제로
  > 걸림) 하나뿐이었음.
  >
  > **75문항·배선 수정 후 재측정(2026-08)** — 헤드라인만 보면 71% → 71%
  > 동률이라 채택을 뒤집을 뻔했는데, 갈라 보니 반대. 라벨이
  > aggregation·enumeration이어도 분류기가 fact로 폴백하면(리콜 5/9)
  > ON/OFF가 같은 코드 경로:
  >
  > | 구분 | OFF → ON | |
  > |---|---|---|
  > | 변수 (실제 라우팅된 12문항) | 23/36 → 27/36 | **+4판정, 악화 0** |
  > | 대조군 (폴백 4문항, 코드 동일) | 11/12 → 7/12 | −4판정 = 노이즈 |
  >
  > "악화 2건"으로 잡혔던 문항은 둘 다 폴백 문항. 대조군 노이즈가
  > 작지 않아(−4/12) +4를 확정적 개선이라 하긴 어렵지만, 손해 근거는 두
  > 번의 측정 모두 없었음 — 기본 켠 상태 유지. 이 경험으로
  > `ab_type_routing.py`가 변수와 대조군을 나눠 보고하도록 수정(섞은
  > 합계는 참고용으로만 유지).
  >
  > **7b·100문항 재검증(2026-08-12, agg·enum 26문항×3회)** — 3b 시절
  > 채택한 손잡이가 7b에서도 값을 하는지 재측정(팀 라우팅처럼 뒤집힐 수
  > 있으므로). 결과는 반대로 이 저장소에서 가장 깨끗한 A/B가 됨:
  >
  > | 구분 | OFF → ON | |
  > |---|---|---|
  > | 변수 (실제 라우팅 19문항×3회) | 34/57 → 45/57 | **+11판정 (60%→79%)** |
  > | 대조군 (폴백 7문항, 코드 동일) | 15/21 → 15/21 | **±0 — 노이즈 0** |
  >
  > 대조군이 완전히 평평한 첫 실행이라 +19%p가 온전히 라우팅 효과.
  > 구제 5문항(배포 자동화·모니터링 열거 0/3→3/3, 학회별 집계 3건) 대
  > 악화 1문항(한국자동차공학회 집계 3/3→0/3 — aggregation 오버라이드의
  > `TOP_N=3`이 이 문항에는 좁음). "손해 근거 없음"이던 채택 근거가
  > 확정적 순개선으로 올라섬 — 7b가 라우팅이 주는 좁은 컨텍스트를
  > 3b보다 잘 쓰는 것으로 보임(팀 라우팅과 반대 방향의 모델 크기 의존성).
- **`/ask/stream`** — SSE 토큰 스트리밍. generate 노드만 필터링해
  송출(`stream_mode=["messages","values"]`), grade의 구조화 출력 토큰은
  섞이지 않음.
- **질의 트레이스** (`src/tracelog.py`) — api.py·cli.py 실사용 경계에서만
  JSONL로 기록. eval 스크립트의 합성 트래픽은 섞지 않음.
- **응답 캐시** (`src/cache.py`) — 마찬가지로 api.py 서빙 경계 전용.
- **groundedness 검증** (`config.VERIFY_GROUNDING`, `graph.verify`) — generate
  직후 답변이 근거 문서에 실제로 기반하는지 구조화 출력으로 재확인하는
  관측 노드. grade·rewrite와 같은 fail-open 정책. 그래프에 항상 붙어
  있지만(스트리밍 이벤트 필터링을 단순하게 유지하려는 목적) 꺼져 있으면
  LLM을 아예 부르지 않음.
  > **verify 판정기 실측(2026-08-11, `eval/eval_verify.py`)** — grade는
  > eval_grade.py로 쟀으면서 verify는 안 잰 채 "A/B 전"으로 남아 있던
  > 부채를 닫음. 라벨을 새로 붙이지 않고 evaluate.py가 저장한 7b 답변
  > 75건(질문·답변·실제 컨텍스트·패턴 채점)에 verify 체인만 다시 돌려
  > 대조. 결과: 실질 오경보 1/54(2%) · 실질 오답 검출 2/6(33%) ·
  > 파싱 실패 0 · +1.4s/질의. 정밀도는 좋으나 재현율이 낮아 상수
  > 심판("항상 grounded") 대비 +2검출/−1오경보 — 기본은 계속 꺼둠.
  >
  > **후속(100문항 확장 후 재측정)** — 처음 측정은 실질 오답이 6건뿐이라
  > 검출률의 분모가 없다는 것이 한계였음. 확장으로 분모가 생긴 뒤 두 런에
  > 다시 돌려 세 측정을 합산하면(200판정): 오경보 5/144(3.5%), 검출
  > 7/20(35%) — 세 번 모두 같은 그림(검출 33·33·36%). "오답의 1/3을
  > 오경보 3.5%로 잡는 심판"이라는 특성은 이제 반복 재현된 사실이고,
  > 상수 심판 대비 순증 +2/200이라 기본 꺼둠 판정도 그대로.
  > 표본이 준 것은 결론의 변경이 아니라 결론의 자격.
  >
  > 측정기 결함을 한 번 고쳐서 얻은 숫자. 1차 실행은 "정답인 거부"
  > (코퍼스에 답이 없어 거부가 정답인 문항)를 정답 버킷에 섞어 세서
  > 오경보가 12.5%(8/64)로 읽혔음 — 심판이 그 7건에 "문서에 그런
  > 정보가 없다"는 맞는 말을 하면서 grounded=False를 낸 것이라, 환각
  > 오경보가 아니라 거부 답변에서는 grounded 의미 자체가 정의되지 않는
  > 것. 버킷을 넷(정답/오답 × 실질/거부)으로 갈라 재니 실질 오경보는
  > 1건. 버킷 하나가 결론을 "심판이 시끄럽다"에서 "심판은 정확하나
  > 낮게 잡는다"로 바꿈 — 켠다면 거부 답변 skip 가드가 필수라는 설계
  > 요건도 이 측정으로 확정됨.
- **시맨틱 청킹** (`src/semantic_chunk.py`, `src/ingest_semantic.py`) —
  고정 800자 대신 문장 임베딩 유사도가 급락하는 지점(주제 전환)에서
  자름. `langchain_experimental` 없이 bge-m3 임베딩 + numpy로 직접
  구현(핵심 breakpoint 로직은 순수 함수라 Ollama 없이 테스트됨). 실측
  결과 — base(90%/100%/100%, MRR 0.95)가 시맨틱(80%/90%/100%, MRR 0.87)을
  recall@1·@3·MRR 전부 앞섬(`compare_semantic.py`, 10문항 앵커 기준).
  청크가 51→34개로 줄며(중앙값 813자) 정밀도가 떨어진 것으로 보임 —
  문장 분리 정규식이 표나 목록 같은 비정형 구조를 잘 못 쪼개는 것도
  원인 후보. parent-child 초기 실험과 같은 패턴("직관적으로 더 정교한
  방법이 첫 시도에서 튜닝된 단순한 기본값을 못 이긴다")이라 채택 보류.

**다음 순서 — Ollama NUM_PARALLEL** — `llm-bench` 프로젝트에서 같은 Ollama
서버에 이 설정으로 TTFT p50 12.4s → 0.93s를 실측함. 이 저장소는 아직
`OLLAMA_NUM_PARALLEL`을 건드리지 않음(환경변수 미설정 확인 — 기본값으로
동작 중). 서버 재시작이 필요해 다른 백그라운드 작업과 충돌할 수 있어
검증을 미뤄 둠. 코드 변경 없이 서버 설정만 바꾸는 문제라 다음으로
검증하기 가장 저렴함.
