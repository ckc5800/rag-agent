# TTS 엔진 정리·보고

## 요약

| 항목 | 내용 |
|---|---|
| **무엇** | LLM 기반(Qwen3-TTS) 자체 GPU TTS **엔진** — 텍스트를 음성으로 합성 |
| **범위** | 순수 TTS 엔진. 백엔드(예: Chatcall)에 **API로 음성을 공급**. 범용 서비스 플랫폼이 아님 |
| **사용 방식** | 서버-서버 **API 위주**. 1개 서비스 전담(1:1), 멀티테넌트는 확장 대비만 |
| **현황** | 단일 GPU 서버 + 4개 컨테이너로 경량 운영 중 |

---

## 1. 목적과 범위

- **목적**: 텍스트를 자연스러운 한국어·다국어 음성으로 합성하여, 호출하는 백엔드 서비스에 API로 공급한다.
- **범위 정의**
  - **순수 TTS 엔진**이다. 음성 합성·발음 교정·스트리밍이 본질이다.
  - **API 위주(서버-서버)**로 사용한다. 사람이 직접 쓰는 화면은 관리자 운영용 보조이다.
  - **1:1 전담**이다. 현재 단일 서비스를 대응한다(`org_id=default`). 멀티테넌트는 코드 훅만 두고 사용하지 않는다.
- **명확히 범위 밖(현재)**: 다수 외부 고객 셀프서비스, 멀티테넌트 과금·격리, 일반 사용자 대상 웹서비스. → 확장 시점에 검토한다.

> 그동안 용도가 확정되지 않아 "혹시 범용으로 쓸 수도 있다"는 가정으로 부가 기능(다중 인증 모드, 사용자 관리 UI, 멀티테넌트 스캐폴딩)을 미리 반영하였다. **범위를 위와 같이 확정하면 해당 기능들은 현재 범위 밖이 되어 경량화 대상**이 된다(4절). 지금 인프라가 커 보이는 원인이 이 부분이다.

## 2. 모델 가능범위

엔진은 `Qwen3-TTS-12Hz-0.6B-Base`를 사용한다. Base 변형의 능력 경계는 다음과 같다.

| 항목 | 가능 여부 |
|---|---|
| 화자 복제 (ICL, 약 5초 레퍼런스) | **O** — 임의 화자의 음색을 복제 |
| 다국어 | **O** — 한·영·중·일·독·불·러·포·스·이 (Supertonic으로 추가 다국어 보강) |
| 발음 교정 가능 구조 | **O** — 외부 사전·규칙으로 교정(3절) |
| **감정·말투 지시(instruction)** | **✕ — Base는 미지원** |

- Base 모델은 `instructions`(감정·말투 지시) 파라미터를 보내도 **설계상 무시**한다(화자 임베딩만 반영). 모델 카드 및 자체 청취 테스트로 확인 완료.
- 감정·스타일 제어는 별도 변형(**CustomVoice·VoiceDesign**)이 담당하나, 이 변형들은 **임의 화자 복제를 지원하지 않는다**.
- 즉 **모델 한 개로 "특정 화자 복제 + 감정 표현"은 동시에 불가**하다. 모델 구조상의 트레이드오프이며, 화자별·감정별 재등록은 비효율적이라 현 단계에서는 채택하지 않는다.

## 3. 오발화 대응 / 보완 방법

합성이 틀리거나 어색할 때의 대응 수단은 다음과 같다.

| 증상 | 대응 수단 | 방식 |
|---|---|---|
| 숫자·단위·약어 오독 | **ITN 도메인 규칙** | 업종별(금융·의료 등) 변환, 관리자 실시간 편집 |
| 고유명사·브랜드 오발음 | **발음사전** | 전역 단어 치환, DB 저장, 관리자 실시간 등록 — **재시작 불필요** |
| 긴 문장 환각·잘림 | 문장 분할 + 무음/길이 가드 | 비정상 출력 자동 차단 |
| 감정·말투 부적합 | **현재 수단 없음** | 모델 한계(2절). 필요 시 CustomVoice 검토(단 화자 복제 포기 감수) |
| GPU 장애·과부하 | **Supertonic(CPU) 자동 전환** | 무중단 fallback |

- 발음 문제는 **발견 → 사전·규칙 등록 → 즉시 반영** 루프로 운영 중 교정이 가능하다.
- 감정 표현만은 모델 차원의 한계로 코드로 해결할 수 없다(2절 참조).

## 4. 현재 구성과 경량화

### 현재: 4개 컨테이너

| 컨테이너 | 역할 |
|---|---|
| **tts-api** | API 서버 + SQLite(내장 파일) — 라우팅·발음교정·인증·DB |
| **tts-vllm-a** | vLLM GPU 엔진 (주력 합성) |
| **tts-fast-a** | Supertonic CPU 엔진 (GPU 장애 fallback + 다국어) |
| **tts-redis** | Redis (멀티 워커 공유 상태: 캐시·락·rate limit) |

표준 Enterprise 구성 대비 **nginx·PostgreSQL 2개 컨테이너는 이미 제거**하였다(nginx → Secret 자체 인증, PostgreSQL → SQLite 내장).

### 범위 확정에 따른 추가 경량화

"1:1 전담 · API 위주"로 범위를 확정하면, 다음은 현재 미사용 기능이므로 보류·축소 대상이다.

| 대상 | 현재 범위에서의 위치 | 조치 |
|---|---|---|
| 다중 인증 모드(public/team/solo/secret) | API 위주이므로 1개면 충분 | Secret 또는 API 키 1개로 단순화 |
| 일반 사용자 UI·회원/역할 관리 | 사용자 직접 사용 없음 | 관리자 운영 UI만 유지 |
| org_id 멀티테넌트 스캐폴딩 | 1:1이라 미적용 | 코드 훅만 유지, 운영 미적용 |
| Redis | 단일 워커면 불필요 | 멀티 워커 필요 시에만 |
| Supertonic | GPU 단일 장애 감수 시 불필요 | 무중단 요구 시에만 |

→ 최소 동작 구성은 **API + vLLM 2개 컨테이너**까지 축소 가능하다.

### 방향

급히 서비스가 필요하면 **최소 동작 구성(API + vLLM)으로 먼저 시작**하고, 트래픽·무중단·멀티테넌트 요구가 생기는 시점에 Supertonic·Redis·테넌트 격리를 **단계적으로 확장**한다.
