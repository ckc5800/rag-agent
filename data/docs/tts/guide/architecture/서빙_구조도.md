# Qwen3-TTS 서빙 구조도

> **기준**: 현재 배포 형상 — `TTS_AUTH__MODE=secret`, `DEPLOY_EDITION=2`(Internal), 단일 L40S GPU  
> 수치 출처는 각 항목에 `(출처: file:line)` 표기. 일반 아키텍처 개요는 [`시스템_개요.md`](./시스템_개요.md) 참고.

---

## 0. 핵심 요약 (3줄)

1. **텍스트 → 음성 변환**은 두 모델이 직렬로 처리한다. LLM(Talker)이 텍스트를 "codec token 악보"로 바꾸고, Vocoder(Code2Wav)가 악보를 실제 파형으로 연주한다.
2. **API 서버 4개 프로세스**는 모두 같은 코드를 실행하지만 서로 메모리를 공유하지 않는다. 공유가 필요한 모든 상태(세마포어·캐시·카운터)는 Redis 한 곳에 집중한다.
3. **GPU는 vLLM 컨테이너 혼자 독점한다.** API 서버와 Supertonic 워커는 GPU를 전혀 쓰지 않는다. 이 분리 덕에 vLLM이 죽어도 API는 살아 있고, Supertonic으로 자동 폴백된다.

### 왜 이 구조인가 — 핵심 의사결정

| 결정 | 선택 | 대안 | 이유 |
|---|---|---|---|
| 엔진 분리 | 컨테이너 분리 | 단일 프로세스 내 공존 | GPU 독점·독립 재배포·장애 격리 |
| API 워커 수 | uvicorn ×4 (멀티프로세스) | 스레드 기반 1프로세스 | Python GIL 우회, 진짜 병렬 실행 |
| 공유 상태 | Redis | 공유 메모리 / DB | 프로세스 경계를 넘는 원자적 연산, sub-ms 속도 |
| Supertonic 위치 | CPU 전용 컨테이너 | GPU 공유 | vLLM에 GPU 전용, 폴백 경로 격리 |
| 2-Stage 실행기 | 0.24 네이티브 (uni 제거) | `uni` / `mp` | uni 는 0.24 에서 hang · mp 는 native 와 동급 실측 — 0.24 기본 실행기 유지 |

## 3. 모델 상세

### 3.1 Qwen3-TTS-0.6B-Base — vLLM 2-Stage 파이프라인

#### codec token이란?

일반 LLM이 텍스트를 단어 단위 token으로 표현하듯, Qwen3-TTS는 오디오를 **codec token**이라는 이산(discrete) 값으로 표현한다.

```
오디오 파형 → [Neural Codec 인코더] → codec token 시퀀스 → [Neural Codec 디코더] → 오디오 파형
             (연속 파형을 이산 정수로 압축)                  (이산 정수를 연속 파형으로 복원)
```

- **12Hz**: 1초 오디오 = 12개 codec frame. 10초 발화 = 120 token (텍스트 LLM보다 훨씬 짧음)
- **Stage 0(Talker)**: 텍스트를 읽고 codec token을 순서대로 생성 (다음 token이 이전 token에 의존 = 자기회귀)
- **Stage 1(Code2Wav)**: 완성된 codec token을 한꺼번에 파형으로 디코딩 (단방향, AR 아님)

#### 파이프라인

```
입력 텍스트 (+ ref_audio ICL prefix)
         │
         ▼
┌────────────────────────────────────────────┐
│  Stage 0: Talker (AR — autoregressive LLM) │   GPU 0, gpu_memory_utilization=0.40
│                                            │   enforce_eager=false (CUDA graph ON)
│  text tokens → codec tokens (12Hz)        │   max_model_len=4096
│  "다음 codec frame은 무엇인가?" 반복        │   (출처: stage_config_qwen3_single_024.yaml)
└─────────────────┬──────────────────────────┘
                  │ codec chunks (공유메모리)
                  │   codec_chunk_frames=25 쌓이면 Stage 1로 (initial=2 · ICF=2 확정 07-28 → TTFB 단축)
                  │   async_chunk=true, codec_streaming=true → TTFB 단축
                  ▼
┌────────────────────────────────────────────┐
│  Stage 1: Code2Wav (Vocoder)               │   GPU 0, gpu_memory_utilization=0.52
│                                            │   enforce_eager=false (Code2Wav CUDAGraphDecoderWrapper)
│  codec tokens → PCM waveform (24kHz)      │   max_model_len=65536
│  단방향 변환, 결정론적                    │   (출처: stage_config_qwen3_single_024.yaml)
└─────────────────┬──────────────────────────┘
                  │ PCM chunks (24,000Hz)
                  ▼
         API httpx 스트림 수신
```

#### GPU 메모리 분배 (GPU 0 총 0.80, 출처: `stage_config_qwen3_single_024.yaml` 스테이지별 합산)

```
전체 VRAM (L40S 48GB)
├── Stage 0 Talker    ▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░  35%  (~16.8GB)
├── Stage 1 Code2Wav  ░░░░░░░░░░░░░░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░  45%  (~21.6GB)
└── 여유(OS·단편화)   ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  20%  ( ~9.6GB)
```
> `.env.prod` 의 `VLLM_A_GPU_MEM_UTIL`(현행 0.92)은 deploy.sh 가 총량으로 받아 스테이지별 값(0.40+0.52)으로 재기록한다 (07-28) — 실제 적용은 stage yaml 의 스테이지별 값.

#### distributed_executor_backend — 0.24는 uni 제거 (네이티브 executor)

| 방식 | 동작 | 상태 |
|---|---|---|
| `mp` (멀티프로세스) | Stage 0·1을 별도 프로세스로 분리, IPC로 통신 | 스테이지 간 pickle 직렬화 오버헤드 |
| `uni` (단일 실행기) | Stage 0·1을 한 프로세스에서 실행 | **0.24에서 제거** — 네이티브 executor가 이미 uni급 + uni는 0.24서 "sr concat" hang 유발 |

0.22 시절 `uni` 전환이 0.68 → 1.41 rps (~×2.1)로 알려졌으나(`fp8-talker-quantization` 메모리), **0.24 재분석에선 uni 자체 효과 ~+6%**이고 상승분 대부분은 0.24 네이티브 파이프라인(Code2Wav CUDA-graph 배칭·2-stage 스케줄링)에서 온다. 배포 config `stage_config_qwen3_single_024.yaml`은 uni를 **주석 처리(제거 유지)**. 현행 천장 ≈3.1 rps.

#### ICL (In-Context Learning) 음성 복제

```
ref_audio (최대 11초 — vLLM-Omni 0.22+ ref overflow 수정으로 완화)
    │
    ▼ codec 인코딩 → prefix token 주입
Stage 0 Talker가 prefix 뒤부터 텍스트 생성
    │
    ▼
Stage 1 전체 디코딩
    │
    ▼
ref_audio_duration_ms 이전 PCM 폐기 → 나머지만 반환
```

> ⚠️ **Base 모델 제약**: 자연어 감정 지시(instruction)는 설계상 거의 무시됨.  
> 음성 복제(ICL)와 감정 동시 제어 불가. Supertonic 요청에는 ICL 자체가 비활성화됨(`use_icl=False`).  
> 참고: [[qwen3-tts-base-no-emotion]]

### 3.2 Supertonic-3 ONNX INT8 — CPU 워커

```
입력 텍스트 (최대 150자 권장)
         │
         ▼
┌────────────────────────────────────────────┐
│  Supertonic-3 (ONNX Runtime, INT8)         │   tts-fast-a 컨테이너 (CPU 전용)
│                                            │   MAX_CONCURRENCY=N (deploy.sh 자동 산출)
│  텍스트 → Mel spectrogram → Waveform      │   OMP_NUM_THREADS / INTRA_OP_THREADS
│  Diffusion 기반 (steps=6 기본)            │   deploy.sh가 호스트 CPU/RAM 실측 → 자동 산출
│                                            │
│  스타일 프리셋:                            │
│    남성: M1~M5  여성: F1~F5              │
│  샘플레이트: 44,100Hz                    │
└─────────────────┬──────────────────────────┘
                  │ PCM (44.1kHz)
                  ▼
         API httpx 수신 → 리샘플링 없이 반환
```

INT8 양자화로 메모리·속도 개선. 보코더 구조(conv)이므로 fp8 추가 양자화는 음질 열화로 미적용.

## 4. 다중 워커 구조

### uvicorn 멀티프로세스 + asyncio 이벤트 루프

```
tts-api 컨테이너 (단일 컨테이너, 단일 IP)
│
└── uvicorn master process  (supervisor 역할, 요청 처리 안 함)
      │    TTS_WORKERS=4  (출처: tts_config.py)
      │    SO_REUSEPORT로 :11100 소켓 공유 → OS가 자동 분산
      │
      ├──► Worker 0  ─── OS 프로세스 (독립 메모리 공간)
      │         └── asyncio Event Loop (메인 스레드)
      │               ├── FastAPI 요청 처리 (coroutine, non-blocking)
      │               ├── httpx → vLLM/Supertonic (비동기 HTTP)
      │               ├── redis.asyncio (비동기 Redis)
      │               └── ThreadPoolExecutor (ITN·DSP·SQLite)
      │
      ├──► Worker 1  ─── 동일 구조 (독립 메모리)
      ├──► Worker 2  ─── 동일 구조 (독립 메모리)
      └──► Worker 3  ─── 동일 구조 (독립 메모리)

공유 상태: 없음 (각 Worker는 서로의 변수를 볼 수 없음)
공유 수단: Redis (4개 Worker가 동일 Redis에 원자적 읽기·쓰기)
공유 파일: tts-api-data 볼륨 (read-only 접근)
```

**asyncio란?**: Python의 비동기 I/O 모델. 하나의 스레드(이벤트 루프)가 여러 요청을 동시에 처리한다. 요청 A가 vLLM 응답을 기다리는 동안(I/O 대기) 같은 스레드에서 요청 B를 처리하는 식이다. 스레드를 추가하지 않아도 수십 개 동시 요청이 가능하다.

**왜 4개 uvicorn 프로세스인가?**

| 목적 | 설명 |
|---|---|
| GIL 우회 | Python은 스레드 여러 개를 만들어도 GIL로 인해 CPU 코어 하나만 쓴다. 프로세스로 분리하면 4코어 실제 병렬 실행 |
| 요청 분산 | nginx 없이 OS 소켓 공유(SO_REUSEPORT)로 자동 로드밸런싱 |
| 장애 격리 | Worker 1개 크래시 → uvicorn master가 재시작, 다른 Worker는 무영향 |
| 수평 확장 | Worker 수 늘려도 Redis가 공유 상태를 담당하므로 로직 변경 불필요 |

**왜 Redis로 공유하는가?**

4개 Worker는 별도 OS 프로세스이므로 인메모리 변수를 공유할 수 없다. 그렇다고 SQLite를 쓰면 동시 쓰기에 락이 걸려 느리다. Redis의 `INCR`/`DECR`/`SET NX` 명령은 원자적이고 sub-ms 속도라 분산 카운터·세마포어·캐시 전용으로 적합하다.

### LAC (Least-Active-Connection) — vLLM 인스턴스 선택

```
Worker N이 요청 받음
  │
  ├── Redis HGETALL vllm:active:*     (0.2s 스냅샷 캐시)
  │     {"http://tts-vllm-a:8400": 3, "http://tts-vllm-b:8400": 1}  (vllm-b 있을 때)
  │
  ├── 가장 낮은 카운터 인스턴스 선택
  │
  ├── 합성 시작: INCR vllm:active:{addr}
  └── 합성 완료: DECR vllm:active:{addr}   (finally 블록, 실패해도 실행)

현재: vLLM 1개 → 항상 tts-vllm-a 선택 (단락 경로)
확장: ADDRS_CSV에 tts-vllm-b 추가하면 자동 분산 (코드 변경 없음)
```

## 5. 프로세스 · 스레드 관리 구조

```
호스트 OS (Linux)
│
├── [컨테이너] tts-redis
│     └── redis-server (단일 프로세스, epoll I/O 멀티플렉싱)
│
├── [컨테이너] tts-vllm-a   [nvidia runtime, CUDA_VISIBLE_DEVICES=0]
│     └── python vllm_serve.py
│           ├── distributed_executor_backend: 0.24 네이티브 (uni 제거)
│           │     → 0.24 executor가 이미 uni급 + uni는 0.24서 hang 유발
│           │     → 처리량 상승분 대부분은 0.24 네이티브 파이프라인
│           ├── Stage 0 Talker   ← CUDA 스트림 0  (AR 토큰 생성)
│           └── Stage 1 Code2Wav ← CUDA 스트림 1  (파형 디코딩)
│                 codec_streaming: 두 스트림이 파이프라인 오버랩
│                 → Stage 0이 frame 5~8 생성 중에 Stage 1이 frame 1~4 디코딩
│
├── [컨테이너] tts-fast-a   [runc, GPU 없음]
│     └── python supertonic_worker.py
│           ├── SUPERTONIC_WORKERS=1
│           ├── ONNX Runtime InferenceSession (CPU ExecutionProvider)
│           ├── INTRA_OP_THREADS=N   (연산 내부 병렬, deploy.sh 자동 산출)
│           └── MAX_CONCURRENCY=N   (deploy.sh 자동 산출 · 초과 시 503+Retry-After)
│
└── [컨테이너] tts-api   [nvidia runtime, GPU 연산 없음]
      └── uvicorn master
            ├── Worker 0  (OS 프로세스)
            │     └── asyncio Event Loop  ← 메인 스레드 1개
            │           ├── FastAPI 라우터 (coroutine)      I/O 대기 중 다른 코루틴 실행
            │           ├── httpx AsyncClient               비동기, max_connections=100
            │           ├── redis.asyncio                   비동기
            │           └── ThreadPoolExecutor              블로킹 CPU 작업 전용
            │                 ├── ITN normalize_for_tts()   (동기 regex, GIL 점유)
            │                 ├── DSP / numpy PCM 처리       (동기, CPU)
            │                 └── SQLite 쿼리               (동기 I/O, asyncio.to_thread)
            │
            ├── Worker 1, 2, 3  (동일 구조)
```

**스레드 사용 원칙**:

| 작업 | 실행 방식 | 이유 |
|---|---|---|
| HTTP 요청 처리 (라우터) | asyncio coroutine | 순수 I/O 대기, 스레드 불필요 |
| httpx → 엔진 통신 | asyncio (비동기) | 네트워크 I/O, 대기 중 다른 코루틴 실행 |
| Redis 읽기·쓰기 | asyncio (비동기) | 동일 |
| ITN 정규화 (regex) | `asyncio.to_thread` / ThreadPool | CPU 바운드 — 이벤트 루프 차단 방지 |
| PCM DSP (numpy) | ThreadPool | CPU 바운드 |
| SQLite 쿼리 | `asyncio.to_thread` | 동기 I/O |
| ONNX 추론 | Supertonic 별도 프로세스 | API 프로세스에서 완전 분리 |
| CUDA 추론 | vLLM 별도 컨테이너 | API 프로세스에서 완전 분리 |

## 6. 서빙 로직 흐름도

### 한 문장 흐름 요약

```
요청 → [미들웨어: 점검·크기·배압] → [Rate Limit] → [엔진 결정] → [ITN 텍스트 정규화]
    → [Redis 캐시 조회] → [세마포어 획득] → [엔진 HTTP 호출] → [DSP 후처리] → 응답
```

### E2E 상세 (배치 기준)

```
클라이언트
    │  POST /v1/tts/synthesize
    ▼
[미들웨어 체인] ─────────────────────────────────────────────────
 ① MaintenanceMiddleware    점검 모드? → 503 (super_admin 예외: `tts_access` 쿠키 또는 `X-Access-Secret` 헤더)
 ② PayloadLimitMiddleware   요청 크기 > 5MB? → 413
 ③ BackpressureMiddleware   /v1/tts/* 경로만:
      · 워밍업 완료? 디스크 > 1GB? RAM/VRAM 한도?
      · active_channels ≥ 40 → circuit_breaker:open (Redis TTL 300s)
        (출처: core/middlewares.py:347-350)
      · CB OPEN + FALLBACK_ENABLED=true → 503 없이 통과 (폴백 처리)
      · CB OPEN + FALLBACK_ENABLED=false → 503

[라우터 — batch.py] ──────────────────────────────────────────────
 ④ Rate Limit              300건/시간 초과 → 429 + Retry-After
                           (출처: tts_config.py:324)
 ⑤ resolve_engine()        엔진 결정 우선순위:
      1. body.engine 명시 → 그대로
      2. voice_id 'supertonic_*' → Supertonic
      3. 언어가 vLLM 지원 10개 밖 → Supertonic (silent swap, WARNING)
      4. vllm:fallback_open 키 있음 + FALLBACK_ENABLED → Supertonic
      5. 기본 → vLLM (DB default_engine)
      (출처: services/tts/common.py:203-225)
 ⑥ load_synth_settings()   body 파라미터 우선, 미명시 → DB 기본값

[텍스트 파이프라인] ──────────────────────────────────────────────
 ⑦ TextProcessor            (asyncio.to_thread — 이벤트 루프 차단 방지)
      quick_split() → 1차 문장 분리
      process_and_split_async():
        UnicodeNorm → SymbolFilter → CustomRule → ITN → PronDict
 ⑧ ensure_terminal_punct    끝 마침표 자동 보강
 ⑨ EOS suffix 적용          끝 `.` 제거 → ` ().` 추가
      (모델이 문장 끝을 인식하는 특수 suffix)

[합성 루프 (문장별)] ─────────────────────────────────────────────
 ⑩ Redis 캐시 조회          키: sha256(text+voice+speed+temp+top_p)
      HIT → PCM 즉시 사용 (TTL 3600s)
      MISS → 합성 진행
 ⑪ sem.acquire(timeout=5s)  batch_sem (Redis 글로벌, 한도 24)
      (출처: .env.prod TTS_BATCH_CONCURRENCY_LIMIT=24)
      실패 → 429 Retry-After:5
 ⑫ incr_active_channels     텔레메트리 카운터 (백프레셔 판단 기준)
 ⑬ engine._pick_addr()      LAC: Redis vllm:active:{addr} 최솟값
 ⑭ engine.batch()           httpx POST {addr}/v1/audio/speech
      timeout 300s, connect 5s, max_retries 2
      무음 붕괴(0byte 응답) 시 최대 3회 재시도 (temperature 0.1 상향)
      4xx → CB 트립·재시도 제외 (클라 입력 오류, 엔진 문제 아님)

[오디오 후처리] ──────────────────────────────────────────────────
 ⑮ 무음 가드               RMS 임계, max_silence_ms=700
 ⑯ ICL ref 구간 폐기        ref_audio_duration_ms 이전 PCM 폐기
 ⑰ trailing/leading 패딩   trailing=250ms, leading=200ms
 ⑱ micro_fade              청크 경계 팝음 제거
 ⑲ high_fidelity DSP        옵션시 주파수 보간
 ⑳ stitch_wav_chunk         문장별 PCM 병합 (inter_sentence_padding=120ms)
 ㉑ 포맷 변환               WAV → MP3/OGG/FLAC (ffmpeg, 필요시)

[응답] ──────────────────────────────────────────────────────────
 ㉒ 단일 파일 반환 + 감사 로그 + 캐시 저장
 ㉓ finally: sem.release + decr_active_channels + _release_addr
      (예외·타임아웃에도 반드시 해제 — 슬롯 누수 방지)
```

## 7. 동시성 계층 다이어그램

```
요청 수  →  미들웨어 (BackpressureMiddleware)
                    │
                    ▼
         active_channels ≥ 40?                     [계층 A: 시스템 차단]
                    │
         YES ──────► circuit_breaker:open (TTL 300s) → 폴백 또는 503
         NO  ──────►
                    │
                    ▼
             Rate Limit 300건/시간/사용자             [계층 E: 사용자 속도]
                    │
                    ▼
             Semaphore 획득 (Redis 글로벌)            [계층 B: API 동시 처리]
         ┌──────────────────────────────────┐
         │  Stream: limit:stream  한도 24   │
         │  Batch:  limit:batch   한도 24   │
         │  Supertonic: 별도 큐    한도  1  │  [계층 C: Supertonic 슬롯]
         └──────────────────────────────────┘
                    │ 동시 처리 슬롯 24개
                    ▼
             vLLM GPU 배치                           [계층 D: GPU 배치]
         ┌──────────────────────────────────┐
         │  MAX_NUM_SEQS = 48               │
         │  (vLLM 내부 동시 시퀀스 수)       │
         └──────────────────────────────────┘
```

**계층별 한도 요약**:

| 계층 | 항목 | 값 | 출처 |
|---|---|---|---|
| A | 시스템 차단 (CB OPEN) | active_channels ≥ 40 | `core/middlewares.py:347-350` |
| B | API 동시 처리 (세마포어) | 스트림 36 · 배치 16 (07-28 확정) | `.env.prod` |
| C | Supertonic 슬롯 | deploy.sh 호스트 자원 기반 자동 산출 (예: 8코어 → 4) | `TTS_SUPERTONIC__MAX_CONCURRENCY` |
| D | GPU 배치 (vLLM) | MAX_NUM_SEQS=48 (+VOC 페어) | `.env.prod` |
| E | 사용자 속도 | 300건/시간 | `tts_config.py:324` |

**실용 처리 한계 (0.6B burst 실측 · 07-28 확정)**:
- TTFB p95 ≤500ms → 동시 15 · ≤1000ms → 동시 30 · 수용 한계 36 (RTF 실링 ~40, 초과분 429 보호)
- 상세: [`동시성_TTFB_스윕_결과`](../../reports/동시성_TTFB_스윕_결과_2026-07-27.md)
- *(구판 "동시 150 접속 100% 성공(102초)" 은 순차 수용큐 기준 옛 실측 — SLA 무관 수치라 폐기)*

## 8. 서킷브레이커 & 폴백

```
정상 상태:
  클라이언트 → tts-api → tts-vllm-a (GPU 24kHz)

CB 동작 (2종, 독립적):

  [부하 기반 CB]                      [장애 기반 CB]
  active_channels ≥ 40               vLLM 연결 실패 / 스트림 중단 / 재시도 소진
  Redis: circuit_breaker:open         Redis: vllm:fallback_open
  TTL: 300s                           TTL: 30s (자동 만료)
  active ≤ 30이면 즉시 해제           (출처: engines/vllm_stream.py:195-303)
         │                                  │
         └──────────────┬───────────────────┘
                        ▼
              FALLBACK_ENABLED=true?
                        │
                 YES ───┤  voice_id를 supertonic_* 로 swap
                        ▼  → tts-fast-a (CPU 44.1kHz)
                           응답 헤더: X-Engine-Fallback: true
                           CRITICAL 로그 (음색 변경 가능성)
                        │
                 NO  ───► 503 Service Unavailable

왜 CB를 2개로 분리?
  부하 CB는 active=0이면 자동 해제 → 정상 동작.
  그런데 vLLM이 진짜 죽으면 active=0이라 부하 CB가 닫혀버림.
  장애를 감지하지 못하는 맹점 → 30s TTL 단기 장애 CB 별도 필요.
```

## 10. 튜닝 레버 (운영자 참고)

처리량·지연에 영향을 주는 실질적 레버 정리.

| 레버 | 위치 | 기본값 | 방향 | 효과 · 주의 |
|---|---|---|---|---|
| `TTS_BATCH_CONCURRENCY_LIMIT` | `.env.prod` | **16** (0.24) | — | deploy.sh `_VLLM_COUNT×16`. DB seed 0→env 위임(admin 설정 시 DB 우선). 배치는 워커 횡단 글로벌 순차 게이트. 현재 conc16 ≈2.66 rps. *(0.22 시절 06-17 A/B에선 24가 천장이었으나 0.24 파이프라인이 상향)* |
| `TTS_STREAM_CONCURRENCY_LIMIT` | `.env.prod` | **36** (0.6B·07-28) | — | deploy.sh `_VLLM_COUNT×36`. RTF 실링(~40)에 마진 1티어로 정합시킨 가드 — 상향 시 수용분 전원 RTF>1 붕괴 실측 |
| `MAX_NUM_SEQS` | `.env.prod` | 48 (+VOC 페어) | — | vLLM 내부 GPU 배치. 하향(8~32)은 큐잉 악화 실측 — 48 유지 |
| `VLLM_A_GPU_MEM_UTIL` (스테이지별) | `stage_config_qwen3_single_024.yaml` | 0.40+0.52 (T=0.92) | ↑ | deploy.sh가 총량 입력(0.92)에서 스테이지별 재기록 (07-28) |
| `codec_left_context_frames` (CLC) | `stage_config_qwen3_single_024.yaml` | **25** (07-28) | — | 보코더 left-context 재디코드 낭비율 50%로 절감 — 최대 성능 레버(실링 33→~40). capture 목록 정합 필수 |
| `distributed_executor_backend` | `stage_config_qwen3_single_024.yaml` | `uni` **제거** | — | 0.24 네이티브 executor가 uni급 + uni는 0.24서 hang 유발 → 제거 유지 |
| `fp8 quantization` | `stage_config_qwen3_single_024.yaml` | **적용됨** | — | Talker에만 가능 (보코더=conv, fp8 불가). 단건지연 ~15%↓ 실측(피크 불변). 양자화 변경 시 캐시 flush 필수 |
| `TTS_WORKERS` | `.env.prod` | 4 | ↑ | API uvicorn 프로세스 수. 코어 수 이상 늘려도 효과 없음 |
| `supertonic_default_total_steps` | DB 설정 | 6 | ↓ | Supertonic diffusion 스텝. 낮출수록 빠르지만 음질↓ |
| `inter_sentence_padding_ms` | DB 설정 | 120ms | ↓ | 문장 사이 정적 시간 |
| `default_silence_padding_ms` | DB 설정 | 200ms | ↓ | 발화 앞 무음 |

> ⚠️ **동시성 천장 최신 결론 (07-28 확정)**: 0.6B+fp8 전환·CLC=25 채택으로 burst 기준 **≤500ms N15 · ≤1000ms N30 · 수용 36 (RTF 실링 ~40)**. 병목은 GPU FLOPs 가 아니라 **엔진 서빙 경로**(스텝 오버헤드+보코더 고정비 — vLLM-Omni 공식 블로그·계측으로 확정)라, knob 16종·모델 크기로는 더 못 올림. 남은 레버는 **스케일아웃(서버 추가)·vLLM-Omni 0.26 평가(chunk ramp-up·디코더 최적화)** 뿐. 정본: [`동시성_TTFB_스윕_결과`](../../reports/동시성_TTFB_스윕_결과_2026-07-27.md) · [`TTFB_최적화_0.6B`](../../reports/TTFB_최적화_0.6B_2026-07-28.md). *(구판 "~3.1 rps 구조적 천장" 서술은 1.7B·CLC=72 시절 기준.)*

**배포 시 주의**: `deploy.sh`는 `.env.prod`를 기본값으로 재생성한다.  
레버 값을 변경했다면 `deploy.sh roll` 이후 `.env.prod`에서 재확인 필요.  
api 컨테이너만 재생성(`docker compose up -d --no-deps --force-recreate api`)하면 `.env.prod` 재생성 없이 반영 가능.
