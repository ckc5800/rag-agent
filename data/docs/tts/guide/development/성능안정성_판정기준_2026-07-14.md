# 대시보드 "성능 안정성" 판정 기준 정리 (2026-07-14)

관리자 대시보드의 성능 안정성(V5 Expert) 패널이 정상 운영 중에도 상시 빨간불이 켜지는
문제를 분석·수정한 기록. 커밋 `bcaaad7`.

## 문제 — 임계값이 아니라 분류의 오류

기존 REGRESSION 판정은 "길이 비례가 아닌 단계 중 하나라도 P95 > 2초"였는데,
**대기·부하 비례 단계들이 판정 대상에 포함**되어 있었다:

| 단계 | 왜 오탐인가 |
|---|---|
| `step_queue_wait` | `batch_concurrency_limit=1`은 음질 위해 **의도된 직렬화** — 동시 배치 2~3건이면 수 초 대기가 정상 |
| `step_engine_queue` | vLLM 큐+Prefill 합산 — 부하 시 2초+가 자연스러운 부하 지표 |
| `step_dedup_lock` | 동일 요청 캐시 완성 대기가 목적인 단계 |
| `step_cer_measure` | Whisper ASR 재인식 — 원래 수 초 걸리는 검증 작업 |
| `step_sentence` | WS 문장 단위 전체 — 문장 길이 비례 |

또한 행별 빨간 바(`baseline×1.2 초과`)가 길이 비례 단계(prefill/decode/ITN)에 걸려 있어
긴 문장 합성만으로 위험색이 표시됐고, REGRESSION 칩 툴팁은 실제 로직과 다른 설명이었다.

## 수정 (bcaaad7)

- `core/telemetry.py`: `_WAIT_OR_HEAVY_STEPS` 제외 목록 신설 — 회귀 감시는
  **순수 처리 단계**(cache 조회·엔진 연결·voice_prep·라우터 등)만 대상
- `AdminPage.tsx`: 길이 비례 3종은 참조선만 표시(빨간 판정 제거),
  `step_decode_jitter` 행 추가 — 길이 무관한 진짜 스트리밍 안정성 지표(기준 100ms)로
  유일하게 빨간 판정 유지
- 툴팁·범례를 실제 로직에 맞게 교정

## 남은 한계 (알고 수용한 것)

1. **2초 고정 임계** — 자기 과거 대비 상대 비교가 아니라, "평소 100ms → 800ms" 같은
   완만한 회귀는 못 잡음 (미탐 가능)
2. **히스토그램 1시간 TTL 누적** — 일시 스파이크의 알람 잔상이 최대 1시간 유지
3. **baseline 4개는 하드코딩 추정치** — 실측 학습 아님
4. **제외 목록이 백엔드(`telemetry.py`)·프론트(`AdminPage.tsx` REF_ONLY) 이중 하드코딩**
   — 새 step 추가 시 두 곳 동기화 필요

## 에스컬레이션 기준

현 수정으로 운영하다가 아래 중 하나가 발생하면 근본 재설계로 전환:

- **오탐 재발**: 정상 운영인데 REGRESSION 칩이 다시 상시 점등
- **미탐 확인**: 실제 성능 저하를 겪었는데 알람이 안 켜졌던 사례 발생

재설계 방향 (그때 적용, 지금은 과설계로 판단):
- 시간 윈도우 히스토그램 (5분 버킷 롤링) — 스파이크 잔상 제거
- 자기 baseline 상대 비교 (지난 24h 중앙값 대비 N배) — 절대 임계 폐지
- 알람 히스테리시스 (연속 M회 초과 시에만 점등)
